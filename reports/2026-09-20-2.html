Cloudflare 开源 security-audit-skill：发现者不许定案，验证者不许自报——用对抗验证把 AI 安全审计做成可信流水线

2026 年 9 月 20 日，cloudflare/security-audit-skill 登上 GitHub Trending（GitHub 的开源项目热度榜）今日第一（单日 +3,162 stars，数据截至 2026-09-20）。它是一个面向 coding agent（编码智能体：能在终端或 IDE（Integrated Development Environment，集成开发环境，集代码编写、调试、运行于一体的工具，如 VS Code）里自主读写代码、执行命令的 AI 程序，如 Claude Code、Codex CLI）的 skill（技能：以自然语言文档打包的操作手册，放进 agent 环境即可被按需加载执行），让 agent 对任意代码库跑一遍结构化的安全审计：六个阶段、一份覆盖账本、三态机器可读产出，外加两个零依赖验证器把关。项目 2026-06-18 随 Cloudflare 博客《Build your own vulnerability harness》开源，MIT 协议，截至 2026-09-20 累计 15,815 stars、862 forks。

真正值得精读的是它背后的工程哲学：AI 找漏洞这件事，难点从来不是“找不到”，而是“找到了你敢信吗”。Cloudflare 的答案是把安全审计拆成互相制衡的两套系统——发现系统（VDH）只负责找，验证系统（VVS）只负责定案，发现者不许给自己盖章，验证者不许自己报漏洞；再用“覆盖账本”逼着 agent 交代“哪些地方没查”。配套博客披露了这套 harness（包裹模型、使其能力可被使用的执行环境）机群运行的一手数据：20,799 条原始候选如何逐级过滤成 7,245 条可行动结论，初验拒绝率如何从 40% 降到 11%。本文的能力描述均来自仓库 README 与 Cloudflare 官方博客，未包含作者实测数据。

先给结论值得精读的三个理由：一、这是“对抗验证”从论文概念落成开源工程实物的样本——checker（检查者）永远不能是 finder（发现者），这套制衡结构可以平移到任何“AI 产出判断”的场景；二、覆盖账本 + 三态 findings + schema 校验，示范了如何把非确定性的 LLM（Large Language Model，大语言模型）输出契约化、可审计化；三、Cloudflare 把内部数据摊得很开：Semgrep 接入一个月被 agent 零调用、Wishlist 被 128 个仓库写了 25,472 次，这些反直觉数字本身就是 agent 工程的一手观察。

01 / Decision brief

TL;DR（太长不看）：一个 skill 约束不了模型能力，但能约束产出纪律

01 / WHAT

发生了什么

Cloudflare 开源的 security-audit-skill 冲上 GitHub Trending 今日第一（+3,162 stars/日）。它是一份装给 coding agent 的审计手册：六阶段流程（侦察→覆盖驱动狩猎→候选验证→结构化输出→独立记录验证→目标中立报告）+ 覆盖账本 + 三态 findings + 两个零依赖 Node 验证器 + 10 类攻击知识库。

02 / WHY

解决谁的问题

让 agent 找代码漏洞容易，让产出可信难：LLM 会把“看起来可疑”包装成“确认漏洞”，且说不清自己查过什么、漏了什么。安全团队拿到这种报告既不敢信、也没法核对。这个 skill 把“可信”拆成三件可执行的事：对抗验证、覆盖可审计、产出可机器校验。

03 / HOW

怎么做到的

流程上把审计切成六个阶段，每阶段有明确产物；纪律上立五条规则：检查者≠发现者、只确认已建立的边界失效、严重性=可能性×影响、纵深防御缺口不算漏洞、单次运行默认只找得到多轮的一半；工程上用 coverage-ledger.json 记录查了什么没查什么，findings.json 按三态（confirmed/needs_validation/rejected）落地，schema 验证器拒绝不合格产出。

04 / SHIP

生产判断

接入门槛不低：要支持工具与并行子代理的 coding agent、Node.js，外加 OS 级沙箱（隔离的执行环境）——审计过程本身会读遍你的代码，没有沙箱等于请人进门翻箱倒柜。Cloudflare 内部数据是 30k 行仓库约 100 findings/3-4 小时、80 个 distinct bug；该数字来自其内部仓库，外部泛化需要自行验证。

02 / Background

背景与问题：AI 审计的可信缺口——结论、过程、产出三处断线

先看需求侧的火有多旺。OpenRouter（聚合数十家模型厂商 API 的路由平台）应用消费榜前十全部是 agent 与 coding 工具（数据截至 2026-09-18）：Hermes Agent 日消费 1.68 万亿 token 居首，Claude Code 8,800 亿 token 第二。coding agent 已经是 token 消费主力，让它们顺手做安全审计是自然延伸——问题在于产出质量基本没有契约。

A传统方案的困境

安全审计的三个既有选项各有短板：人工渗透测试贵且慢，覆盖面受制于审计师个人经验；静态分析工具（如 Semgrep、CodeQL：按预写规则扫描已知漏洞模式的工具）误报多、规则维护成本高，且只能查规则覆盖过的模式；LLM 直接扫代码看似灵活，实际产出三类毛病：幻觉——把理论风险报告成确认漏洞；无过程记录——说不清哪些文件查了、哪些没查；自由文本——报告没法进 CI（Continuous Integration，持续集成：每次代码提交后自动执行构建、测试与检查的工程实践）流水线做机器处理。

BCloudflare 的起点：一个 450 行的 skill

Cloudflare 在 2026-06-18 的博客《Build your own vulnerability harness》（Project Glasswing 系列第二篇）里复盘了这条路：起点不是宏大架构，而是一个约 450 行的 skill——本质是给 coding agent 的一份详细审计操作手册。六周之内，这个 skill 演化成横扫内部 128 个仓库的 fleet（机群：按统一调度批量运行的实例集合）扫描器，分水岭在于引入了第二套验证系统。博客末段声明该 skill 随博文一并发布，仓库创建于同日。

核心问题的重新表述。这个项目把“AI 审计不可信”拆成了三个可分别攻克的子问题：①结论可信——一个模型既当运动员又当裁判，判定必然向自身倾斜，所以要拆成发现与验证两套系统；②过程可信——没有“查过什么”的记录，就没法判断“漏了什么”，所以要覆盖账本；③产出可信——自由文本无法对接下游工具链，所以要用 schema（结构化数据格式定义）约束成机器可校验的 JSON（JavaScript Object Notation，一种以键值对表达结构化数据的轻量文本格式）。三件事对应三件工程物：VDH/VVS 双系统、coverage-ledger.json、findings.json + 验证器。

03 / How it works

审计原理：六阶段流水线，每一步都留下一份可核对的文件

skill 本体是一组 Markdown 文档与 JSON schema，装进 agent 环境后，一句“security audit this codebase”即可触发。完整流程分六个阶段，前五个阶段有独立文档（SKILL.md、RECONNAISSANCE.md、HUNTING.md、VALIDATION-AND-REPORTING.md 及攻击类文档），每个阶段的产物都会落成文件，供下一阶段和最终验证器消费：

PHASE 1侦察（Reconnaissance）清点代码库：入口点、依赖、信任边界（trust boundary：系统中“受信任”与“不受信任”部分的分界线）与技术栈，产出威胁模型的原料。
PHASE 2覆盖驱动狩猎（Hunting）按 10 个攻击类文档逐类排查，同时维护 coverage-ledger.json——计划查什么、实际查了什么、哪些区域明确放弃及原因，全部记录在案。
PHASE 3候选验证（Validation）每个候选漏洞要过“已建立的边界失效”检验：只有当代码确实在特定输入下越过安全边界时才算数，纯理论风险不进 confirmed。
PHASE 4结构化输出（Output）按 report-schema.json 把结论写进 findings.json，产出即跑 validate-findings.cjs 做 schema 校验；每条带三态标记：confirmed（已证实）、needs_validation（待复核）、rejected（已排除）——被排除的也要留下“为什么排除”。
PHASE 5独立记录验证（Verify）validate-coverage-ledger.cjs 贯穿全程：从 Phase 1 建账起，覆盖账本每次更新都会触发校验，Phase 5 做最终总检，追查“声称查过但没有对应记录”的窟窿。
PHASE 6目标中立报告（Report）按消费方需求输出报告，措辞不迎合“让结果看起来更严重”的倾向；每条 finding 的严重性按“可能性 × 影响”计算，缺任何一个维度都不允许给高分。

两个关键产物的设计细节

coverage-ledger.json（覆盖账本）是整个流程里最有“会计思维”的设计：agent 必须把每个攻击类在每个代码区域的排查情况登记入账——查了、没查、查不了（比如缺上下文）都要有明确记录。验证器会比对“计划 vs 实际”，发现“声称查了但没有对应记录”直接判不合格。它的价值在事后：审计报告的使用者可以拿着账本核对“这个仓库的供应链攻击类查过吗”，而不是对着一份自由文本猜测审计范围。

findings.json 的三态值得单独说：多数审计工具只有“报/不报”两种状态，被过滤掉的候选直接消失。这里要求 agent 把拿不准的标记为 needs_validation、主动排除的标记为 rejected 并写明理由——这既给人工复核留了工作清单，也让“agent 当时是怎么想的”变成可追溯的记录。

五条纪律原则（README 原文要点）。①对抗验证：检查者永远不能是发现者；②只确认已建立的边界失效——"代码允许坏事发生“不等于”坏事会发生"，没有证据不落 confirmed；③严重性需要影响——可能性与影响缺一不给分；④纵深防御缺口不是漏洞——"这里少了一层防护"属于加固建议，不是可报告漏洞；⑤多次运行提升覆盖——单次运行默认只找得到多轮运行总量的一半左右，官方明确建议对重要目标多跑几遍。

04 / Innovation

创新点：双系统制衡、防造假三招，以及两个反直觉的生态观察

skill 文档约束的是单次审计的纪律；Cloudflare 博客披露的 harness 架构，则展示了这套纪律如何被规模化执行。两层创新值得分开看。

第一层：VDH + VVS 双系统制衡

内部 fleet 的核心架构是两套独立系统：VDH（Vulnerability Discovery Harness，漏洞发现系统）负责找，由 8 个专职 agent 组成——Recon（侦察）、Hunt（狩猎）、Validate（初验）、Gapfill（补漏）、Dedup（去重）、Trace（追踪）、Feedback（反馈）、Report（报告）；VVS（Vulnerability Validation System，漏洞验证系统）负责定案。两套系统用不同模型独立运行，VDH 的产出进 VVS 的池子重新验证，互相校验对方的结论。工程上每个 agent 的上下文控制在 25% 以下，全部中间状态落 SQLite（嵌入式单文件数据库）持久化，以 run_id/repo/stage 为键——单个 agent 崩溃可以从任意阶段恢复。

第二层：防造假三招

模型造假 finding（编一个“看起来专业”的漏洞报告）是 agent 审计最阴险的失败模式。博客披露的三条硬规则：①威胁模型前置——必须先声明针对该仓库的威胁模型（列出资产与攻击面）才有资格提交 finding，杜绝“先编结论再找理由”；②PoC（Proof of Concept，概念验证：能实际触发漏洞的最小代码）必须针对原始代码——在 agent 自己改写的代码上“复现”漏洞不算数；③Validator 不得自报 finding——验证系统自己发现的漏洞不能直接进入产出，必须绕回发现流程走完整链路。三条规则合起来堵死了模型自证自明的通道。

A反直觉观察一：Semgrep 被零调用

Cloudflare 给 Hunter 集成了 Semgrep（开源静态分析工具）作为工具选项，一个月后的统计：Hunter 调用次数为零。agent 宁愿自己读代码也不调用规则引擎。这组数字对“给 agent 塞工具就能提效”的直觉是有力反证（本文推断：至少在这套 fleet 的观察里，工具箱的丰富度不等于使用率，agent 实际伸手拿什么工具由任务语境驱动）。

B反直觉观察二：Wishlist 写了 25,472 次

当 agent 遇到能力缺口，正确动作不是硬编造工具，而是把需求写进 Wishlist（愿望清单：agent 表达“我需要什么工具”的登记机制）。128 个仓库累计写入 25,472 次——平均每个仓库约 199 条工具需求。Cloudflare 把这个清单当作 harness 演进的需求池，也当作观察 agent 行为的窗口。sibling forking（兄弟分叉：让子 agent 从同一父状态分叉出并行分支）覆盖了其中 9%-20% 的任务。

本文推断：这个 skill 的真正产品定位是“纪律约束层”。README 反复强调它不绑定特定模型、不承诺发现率上限——一个 skill 文档不可能提升模型智力，它能做的是把模型的自由发挥关进结构化流程：该查的类别列全了、该留的记录留了、该排除的写清理由、产出过 schema 校验。也就是说，同一个人用同一个模型，装不装这个 skill 的差别不在“能不能找到漏洞”，而在“找到的东西能不能被信任和使用”。

运行环境与成本结构

06 / Production view

工程化视角：接入生产系统要过的三道关

这套东西要进生产环境，绕不开三个问题。以下分析结合 README 的接入要求与 Cloudflare 博客的运行数据展开。

一、接入生产需要考虑哪些环节？

  • agent 选型：README 要求宿主 agent 支持工具调用与并行子代理——六阶段流水线要靠子代理分工才能跑顺，单线程的轻量 agent 只能跑降级版流程；Node.js 是验证器的运行依赖。
  • 沙箱是硬前提：审计 agent 会读遍整个代码库并执行验证代码，OS 级隔离（容器或虚拟机）必须先行；Cloudflare 内部用 unshare 命名空间隔离 Hunter，开源用户需要自己配等效方案。
  • 预算与调度：官方口径按仓库设预算、50-200 workers 并行、最差 run 14 小时以上——接入 CI 需要评估这笔开销放在哪个环节（每日定时 or 发布前触发），以及超时策略。
  • 结果消费流程：三态 findings 需要配套人工复核队列处理 needs_validation，confirmed 进工单系统，rejected 留档——没有下游流程，三态设计就退化成一堆 JSON。

二、对现有 LLM 应用架构有什么影响？

它示范的“双系统制衡”是一种可复用的架构模式：任何 LLM 判断类任务（内容审核、代码审查、数据质量校验）都可以拆成“生成判断”与“独立复核”两个模型角色，用不同模型交叉验证。这类架构对现有系统的影响是增加了一次模型调用的成本与延迟，换来判定可信度的结构化提升；同时覆盖账本模式（计划 vs 实际的强制对账）可以移植到一切“过程不可见”的 agent 任务里。对安全团队而言，findings.json 的 schema 化产出意味着 agent 审计结果可以第一次以机器可读形式进 SIEM（Security Information and Event Management，安全信息与事件管理平台）与工单系统，而不是以 PDF 报告的形式躺在邮箱里。

三、从 Demo 到生产可用，主要差距在哪里？

Demo（本地对一个开源仓库跑一遍，拿到一份 findings.json）与生产的差距按 Cloudflare 自己的数据体现在三处：①重复运行的收敛——单次运行只找得到多轮的一半左右，生产必须设计多轮运行与去重合并策略；②防造假的执行——skill 文档写“validator 不得自报”，但开源版没有独立的 VVS 运行时强制它，生产要自建第二模型验证层；③成本控制——从单仓库到 fleet 规模，预算上限、worker 调度、SQLite 状态恢复都要自己搭。Cloudflare 用六周走完了这段路，其轨迹本身是可信的参考路径。

07 / Risk & Limits

局限与风险：纪律约束能力下限，约束不了发现上限

数据外推风险 高

漏斗数据、拒绝率、单仓库成本全部来自 Cloudflare 内部仓库——代码风格、技术栈分布、威胁面都与其业务高度相关。博客未提供外部基准上的对比数据，80 bug/30k 行的外推需要自行验证。

发现上限受模型约束 高

skill 是文档层约束，不能提升模型的安全直觉。模型看不出某段代码的漏洞模式时，覆盖账本只会诚实地记录“查了没发现”。对抗验证能压低假阳性，对假阴性（漏报）没有对称机制。

接入门槛 中

需要强 coding agent（工具 + 并行子代理）+ Node.js + OS 级沙箱三件套。沙箱缺失时，审计 agent 全库读取本身就是攻击面；企业内落地先要过安全合规关——用一个 AI 读遍全库代码，这件事本身就要安全团队审批。

覆盖账本的边界 中

账本保证“查过的都有记录”，不保证“记录查过=真的查懂了”。agent 可以在账本上登记完成而实际排查流于形式——对抗验证拦结论造假，拦不住过程敷衍。多轮运行策略是官方给出的部分对冲。

热度与成熟度的错位 中

14 个 commits、6 月中旬以来最后推送为 2026-09-14，仓库本身处于早期。星数曲线（3 个月 15,815 stars、今日 +3,162）反映的是对“可信 AI 审计”的需求热度，与 skill 的实际效果没有直接关系（本文推断）。

三态产出的运营负担 低

needs_validation 与 rejected 都需要下游有人接。没有复核队列的团队会看到“待复核”条目堆积，反而放大信任问题——三态设计的前提是消费端有处置流程。

08 / What's next

未来方向：harness 本体、skill 分发生态，以及制衡范式的外溢

  • harness 本体开源的承诺：博客结尾明确表示扫描器系统“希望很快跟进”。若 VDH/VVS 运行时真正开源，社区将首次拿到完整的多 agent 对抗验证参考实现；在此之前，复刻者只能按博客文字自行拼装调度层。
  • skills 分发标准化：安装走 npx skills add（skills.sh 生态的统一命令），security-audit-skill 是该生态里第一批带 schema 验证器的“重度” skill。skill 从“一段提示词”进化为“文档 + schema + 验证器的软件包”，分发标准化会反过来抬高 skill 的工程基线（本文推断）。
  • 对抗验证范式外溢：checker≠finder 的制衡结构不专属于安全审计。内容审核、事实核查、代码合并判定、自动化测试结论判定——一切“LLM 产出判断”的场景都适用同一结构。security-audit-skill 的意义在于把它做成了可安装、可校验的实物（本文推断）。
  • 安全审计的岗位变化：审计工作从“逐行读代码”转向“设计威胁模型 + 复核 needs_validation + 消费机器可读产出”。覆盖账本让审计范围的谈判（"这轮查了什么"）第一次有了客观对账依据（本文推断）。
09 / Takeaways

工程师可以借鉴：五条可以直接搬走的工程手法

对抗验证：checker 永远不能是 finder

任何 LLM 判断类任务，把“下结论”和“找候选”拆给两个独立模型/系统，能结构性压低假阳性。成本是双倍调用，换来的是判定可信度——这个交换在安全、审核类场景几乎总是划算的。

覆盖账本：给非确定性过程配一本"对账单"

让 agent 强制登记“计划做什么 vs 实际做了什么 vs 放弃了什么及原因”，再用脚本比对差距。这个模式可以移植到检索、调研、测试等多数过程不可见的 agent 任务。

三态产出：不要强迫模型给二元答案

confirmed / needs_validation / rejected 三态加“排除理由”，把“拿不准”变成一等公民。对下游而言，"待复核清单"远比一个被硬压成二值的不可信答案有用。

Wishlist：给 agent 的能力缺口建登记机制

agent 遇到缺工具时，让它写愿望清单而不是现场硬造。25,472 条记录既是 harness 迭代的需求池，也是观察 agent 行为偏好的数据集。

上下文预算 + 状态外置：长任务的结构解法

每个 agent 上下文控制在 25% 以内、全部中间状态以 (run_id, repo, stage) 为键落 SQLite，单点崩溃可从任意阶段恢复。这套组合是长程 agent 任务的标准工程形态。
