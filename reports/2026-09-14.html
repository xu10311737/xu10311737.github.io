背景与问题：为什么通用 Agent 不够稳定

代码审查不是简单的“把 diff 发给模型”。一个生产审查器至少要同时处理四件事：完整覆盖变更文件，拿到跨文件上下文，判断意见是否真的是缺陷，并把意见准确地落在 Pull Request（拉取请求，PR）的正确行上。任何一项出错，都会转化为漏报、误报或开发者对工具失去信任。

来源事实OpenCodeReview 的 README 将通用 Agent + Skill 的问题概括为覆盖不全、位置漂移和质量不稳定，并把原因归结为纯语言驱动架构缺少对审查流程的硬约束。[README]

本文判断这不是说通用 Agent 没有代码理解能力，而是说“让模型同时决定看什么、怎么查、审什么、评论放哪儿”会把太多控制权放进一个概率性循环。提示词再长，也不能替代可验证的状态、范围和输出协议。

核心原理：把 Agent loop 拆成控制面和决策面

OpenCodeReview 的核心设计可以理解为一条“有硬边界的 Agent loop（智能体循环）”。它没有试图消灭模型的不确定性，而是把不确定性放在相对合适的位置。

  1. 01确定审查范围读取 diff，筛选目标文件
  2. 02规则与分组匹配规则，合并相关上下文
  3. 03Agent 取上下文读完整文件，搜索仓库
  4. 04语义判断模型判断真实缺陷与严重度
  5. 05反思与定位校验内容与评论行位置
  6. 06结构化输出JSON、会话、CI 评论

控制面：必须可重复

文件选择、过滤、相关文件打包、规则匹配和评论定位属于控制面。README 明确将这些职责交给工程逻辑，并说明大变更可按审查单元拆成隔离的子 Agent。

决策面：需要语义理解

Agent 读取完整文件、搜索代码库、查看其他变更文件，再判断某个变化是否构成真实缺陷。这些步骤需要动态选择上下文，适合保留模型能力。

结果面：可恢复、可接入

CLI 支持会话列表和恢复、JSON 文件输出；GitHub Action 还提供超时、Token（模型处理的文本单元）预算、增量评论、摘要评论和检查产物等配置。

一个具体的边界例子

假设 PR 同时修改了 Java 服务、配置文件和测试。模型可以判断“配置缺失会不会导致生产错误”，但不应该自行决定“只审服务文件”。前者是语义判断，后者属于审查范围，应由程序根据 Git 状态、路径规则和配置先确定。

# OCR 负责范围、规则和输出；Agent 负责语义审查
ocr review --from main --to feature-branch
ocr review --format json --output result.json
ocr review --resume <session-id>
ocr scan --path internal/agent

本文判断这更像“代码审查编译器”的前端加一个受约束的语义执行器：先把输入、规则和边界规整成模型可消费的任务，再把模型输出收敛成可发布的结果。这里的“编译器”是帮助理解的工程类比，不是项目的官方命名。

真正的创新在哪里

  1. 不是再写一份更长的审查提示词。项目将“必须正确”的步骤从自然语言中抽出来，形成可观察的程序模块。
  2. 上下文组装成为一等能力。相关文件被绑定到一个审查单元中，既避免逐文件审查丢失关系，又可以把超大变更拆分并发执行。上下文窗口不再只是模型参数，而成为需要设计、测试和计费的工程资源。
  3. 定位与判断分离。模型负责指出风险，独立模块负责把评论放在正确位置。对于 PR 工具，这比单纯提高回答文采更接近用户真正感知的可靠性。
  4. 支持两种执行模式。默认模式由 OCR（OpenCodeReview 的命令行工具名）调用配置好的 LLM；委托模式由宿主编程 Agent 执行模型循环，OCR 负责范围选择、规则解析和上下文收集。[README]

9 月 7-14 日的发布和主分支细节也印证了这个方向：输出原子性、MCP 关闭超时、预览与执行一致性、增量评论、会话比较和评论绑定到被审查提交，都属于“让循环可以被恢复和审计”的基础设施，而不是模型能力展示。

来源事实v1.12.0 对分组契约的具体改动是：过去让模型在 JSON 中回写完整路径，大变更时响应体会随路径总长度增长，截断后可能解析失败并退化为逐文件调度；现在由程序给文件编号，模型只返回整数索引，再由程序映射回 diff，并跳过越界和重复索引。会话查看器负责把索引还原为路径，旧会话格式不变。[分组契约提交]

证据边界：基准图的最近一次公开提交是 2026-08-05，图中工具版本是 OCR v1.3.1，而 npm registry 元数据显示当前包版本是 v1.12.0（2026-09-12）。这是项目方公开基准，不是 v1.12.0 的独立复测，也不是跨供应商完全相同配置的对照实验。最稳妥的结论是“专用流水线可能显著降低噪声和成本”，而不是“生产效果必然达到某个比例”。

来源事实公开评测框架把数据加载、审查执行和评估编排成一条管线，支持固定随机种子、每次运行独立目录、路径/侧别/行号/语义四阶段匹配，并允许多轮评估；但公开基准图没有给出本次运行的重复次数、完整配置和波动范围。[评测框架说明]

本文判断这个基准最值得借鉴的地方不是排名，而是指标组合：准确率、召回率、F1、平均耗时和平均 Token 同时出现。代码审查产品如果只展示“发现了多少问题”，就无法判断它是在提高质量，还是在制造更多需要人工筛选的噪声。

结论不是“哪一个全面胜出”：最可靠的生产组合通常是确定性扫描负责硬门禁，专用 Agent 负责跨文件语义问题，人工负责高风险和争议项。

工程化视角：从 Demo 到生产要补哪些环节

接入时应把 OpenCodeReview 看成审查控制面，而不是一个“调用模型并发评论”的黑盒。目标是能回答：审了哪些输入、使用了哪个模型和规则、花了多少 Token、哪里失败、哪些意见被人接受。

建立自己的黄金集

从真实 PR 中抽取安全、缺陷、性能、可维护性和测试问题，保存 Git SHA（提交对象标识）、模型、规则版本及人工结论。先用 50-100 个代表性 PR 做基线，数字是实施建议，不是项目方门槛。

固定运行输入

明确合并基准（merge-base）、PR head（提交端点）、路径排除、语言和审查规则；固定 ocr_version 与模型端点，避免今天的结果由隐含的分支范围或自动升级造成。

先接建议模式

GitHub Action 提供 review_task_timeout、max_tokens_budget、sticky_summary、incremental、upload_artifacts 等输入。初期让结果进入 PR 摘要或独立报告，不直接阻断合并。

设计失败路径

为模型超时、限流、JSON 无法解析、评论定位失败、GitHub API 失败和部分文件失败分别定义重试、降级、人工接管和退出码。能恢复会话不代表可以静默丢失结果。

接入遥测与反馈

至少记录 PR 标识、两个 Git SHA、规则和模型版本、审查单元、工具调用次数、输入输出 Token、耗时、失败原因、评论状态及人工接受/忽略结果。

按风险分层启用

低风险变更可先给提示，高风险目录可提高审查强度并保留人工复核；只有在自己的召回、误报、延迟和故障数据稳定后，才考虑局部门禁。

它会怎样改变现有 LLM 应用架构

原来的最小架构

PR 事件进入队列，拼接 diff 和提示词，启动一个通用模型循环，再把文本解析成评论。问题、范围、成本和恢复往往混在一次调用里。

增加审查控制面后

事件先经过范围与规则解析，再进入分组任务；每个任务拥有隔离上下文和预算，结果经过结构校验、评论定位、发布策略和遥测后才回到 PR。

部署边界的变化

代码不只经过模型端点，还会经过 CI 日志、缓存、会话文件和评论系统。数据流、密钥、权限和保留周期必须进入架构评审。

执行安全：项目做了什么，团队仍要验证什么

来源事实项目的 Security Assurance Case 自述了几个安全边界：外部命令限制为 Git 的显式参数；文件路径在仓库根目录内校验；API 通信使用 HTTPS（安全超文本传输协议）；密钥从环境变量读取且不写入输出；模型响应做 JSON 结构和行号范围校验；本地查看器默认限制在回环地址；CI 运行 go vet、govulncheck 和竞争检测。[Assurance Case]

安全判断：这是一份项目自述的设计保证，不等同于第三方安全审计。它降低了命令注入、路径穿越和凭据泄露的实现风险，但不能证明模型不会被恶意代码 diff 诱导，也不能替团队完成供应商、网络和 CI 权限审查。
  • 把 PR diff 当作不可信输入。注释、字符串和测试数据都可能包含“请忽略上面规则”的提示注入，模型只能在受控系统指令和工具权限内工作。
  • 对外发代码做逐层确认：模型端点、CI 日志、上传产物、会话查看器和 PR 评论都可能成为新的数据出口。
  • 使用 fork PR 时验证权限和 checkout 策略。公开的 GitHub Action 文件说明它先 checkout 受信任的 base，再获取 PR head 的 Git 对象，避免把不可信 head 直接物化到工作区；团队仍需在自己的权限策略中复核。
  • 把模型评论当作未验证建议。即使行号经过边界检查，评论的事实、严重度和修复建议仍需测试与人工确认。

局限与风险

  • 召回率取舍。项目明确承认其基准中的 Recall 低于通用 Agent，目标是减少噪声。对安全审查或高风险变更，低噪声不是全部目标，需要单独的高召回策略。
  • 基准的时间与版本错位。公开基准图在 8 月 5 日更新，图中 OCR 是 v1.3.1；当前 release 是 v1.12.0。中间的版本变化可能影响结果，不能把图表当作今天版本的性能承诺。
  • 项目方数据不能替代复测。AACR-Bench 有跨语言、仓库级上下文和专家标注等优点，但样本来自开源 PR，不能直接代表企业私有仓库、内部规范或不同 PR 分布。
  • 模型端点仍是外部依赖。项目不捆绑自托管模型；延迟、价格、数据留存和模型升级由端点供应商共同决定。[路线图]
  • 静态规则不会消失。审查 Agent 适合语义和跨文件判断，但确定性扫描更适合做稳定的硬门禁。两者应互补，而不是用 Agent 覆盖所有规则。

未来方向：官方路线图与本文推断

来源事实路线图将 JetBrains 插件、委托模式和更高召回的 Ultra Mode 列为 2026 年下半年计划，把领域特定长期记忆列为 2027 年上半年计划；同时明确暂不计划自动修复、通用编码助手和捆绑自托管模型。[ROADMAP.md]

本文判断如果这些方向落地，最重要的工程问题会从“模型能不能发现问题”转向“记忆和策略是否可追溯”：每条持久化经验都要有来源、版本、适用范围和撤销机制；Ultra Mode 也应以风险分层启用，而不是全量增加 Token。

更长期看，代码审查 Agent 可能会形成三层结构：确定性规则负责硬约束，专用 Agent 负责语义检索和判断，长期记忆负责项目规范与历史决策。能否生产化，取决于三层之间的版本管理和评测闭环，而不是单次演示的评论数量。

工程师可以借鉴什么

  1. 把“模型判断”和“流程控制”拆开。凡是需要完整覆盖、固定顺序、权限边界或可恢复的步骤，都不应只写在提示词里。
  2. 把上下文组装当作产品能力。文件分组、检索范围、上下文隔离和预算控制会直接决定质量和成本。
  3. 用准确率、召回率、F1、延迟、Token 和人工接受率一起评估。单一榜单或单一“发现数”无法指导生产决策。
  4. 让结果结构化、可恢复、可审计。模型输出不是最终产品，定位、校验、发布和遥测才是可运维系统的一部分。
  5. 从非阻断试点开始。先在自己的 PR 分布和安全边界上建立数据，再按目录、风险和置信度逐步扩大权限。
最终判断：OpenCodeReview v1.12.0 当前最值得学习的不是“它比某个 Agent 快多少”，而是它展示了一个通用原则：当概率模型进入确定性工程流程时，应把模型放在语义判断的位置，把范围、协议、预算、恢复和安全交还给程序。
