Jev：放弃生成文本、专做结构化决策的模型，把 AI 判断做成 70 毫秒级的"智能 if 语句"

前 OpenAI 研究员 Diogo Almeida 创办的 TypeSafe AI，在隐身研发两年后，于 2026 年 9 月 16 日发布了新的模型类别 System One Models，以及其中第一个模型 Jev。Jev 不生成文字。你把要判断的内容发给它，它直接返回一组决策结果，每个结果都带概率和把握程度。从发出请求到拿到结果，只要 70–500 毫秒。价格为每百万 token（模型处理文本的最小单位，约四分之三个英文单词）输入 0.042 美元，输出免费。

官方评测显示：Jev 在四项任务上平均准确率 67.8%，每个案例 0.0004 美元、0.4 秒，准确率和 Claude Sonnet 5 相当。发布 24 小时内，这个话题在技术社区 Hacker News 攒到 1699 分、459 条评论。争论集中在两点：官方说的"不能幻觉"（幻觉：模型一本正经编造内容）到底指什么；厂商自己做的评测可不可信。同一天，开源社区复刻出了同类原型。

先给结论它是什么：一个不生成文字、只输出决策和概率的模型。有什么用：把分类、路由、评分这类智能 if 语句的判断直接嵌进业务代码——延迟 70–500 毫秒、不用解析、输出免费。优点：输出格式由构造保证不会错；概率经校准训练，报 90% 把握就应在约 90% 的情况下真的对；自带"会说不知道"的置信度。缺点：闭源、单一供应商；评测是厂商自建；复杂内容理解有硬上限（发票处理比 Claude opus 5 低 16.6 个百分点）；生态接入工具几乎为零。客观评价：能不能进生产，要用自己的数据说话；但"让接口返回概率、用拆解问题替代长提示词、用置信度分级放行"这三件事，不换模型也能用。

01 / Decision brief

TL;DR（太长不看）：一个为"if 语句"重新发明的模型

01 / WHAT

发生了什么

TypeSafe AI 在 2026 年 9 月 16 日发布 System One Models 和首个模型 Jev。System One 这个名字取自心理学的"快思考"：不假思索、一秒钟内做判断。Jev 不输出文字，只输出决策结果，一共三种：Choice（从固定选项里选一个）、Score（在你定义的等级上打分）、Noul（"这件事是否为真"的概率）。每个结果都带校准概率（报 90% 把握，就应在约 90% 的情况下真的对）和置信度。早期访问已开放。

02 / WHY

解决谁的问题

要把 AI 判断接进业务代码的工程师。用 LLM 做分类、路由、评分，要等 3–329 秒；输出要解析校验；模型自报的置信度不可信。Jev 把这三件事都换掉：70–500 毫秒、不用解析、训练目标就是校准概率。这样，AI 判断就能放进对延迟要求高的实时流程，包括 Agent（能自主调用工具、多步完成任务的 AI 程序）执行过程中的审查。

03 / HOW

核心机制

一次请求 = 一段状态 + 一批问题。三种问题的答案并行返回，不是逐字生成。新训练方法 RLCD（校准决策强化学习）把"概率要对得上真实结果"当作训练目标；现有 LLM 的训练只奖励"说法讨人喜欢"或"答案正确"，不管概率准不准。置信度从概率分布算出，代码按阈值分级放行。单次请求预算约 3.2 万 token，多问问题几乎不增加延迟和成本。

04 / SHIP

生产判断

官方评测里 Jev 平均 67.8% 准确率、每案例 0.0004 美元、0.4 秒。这追平了 Claude Sonnet 5，但明显低于 opus 5（73.1%）和 sol（74.1%）；发票处理一项只有 61.8%（opus 5 为 78.4%）。评测是厂商自建，参考答案是 GPT-6 Astra 与 Claude Fable 5.1 的平均，官方自认偏向 OpenAI/Anthropic；OpenRouter（第三方模型 API 聚合网关）、vLLM 和 Ollama（最常用的两种自己跑模型的开源工具）生态都没有接入（来源 06）。替换现有流程前，必须用自己的数据复测。

来源事实发布信息、三种原语、RLCD 描述、定价与延迟、评测数据，均来自 TypeSafe 官方博客、文档与评测站（数据截至 2026-09-17）；争议与社区反应来自 Hacker News 讨论帖（1699 分/459 评论，数据截至 2026-09-17）与 Reddit r/LocalLLaMA 讨论帖。本文推断"专用决策模型会成为一个独立类别"和"护城河在校准质量而非架构"是本文判断；判断依据在各章节内标注。
02 / Background

背景与问题：聊天早就很强，自动化却一直没跟上

System One Models 的出发点是一个反问："模型聊天早就强了，那自动化在哪？"提问的人是 Diogo Almeida。他曾在 OpenAI 参与让模型学会听从指令、与人对话的方法研究，这些研究后来成了 ChatGPT 的底子。他当年的判断是：聊天模型通向通用智能。两年隐身研发后，他给出的答案相反：要自动化，先得有一种软件能直接依赖的模型。

ALLM 进代码的三笔税

把 LLM 的判断接进业务代码，工程师一直在替"生成式"付代价：

  • 速度税：LLM 是逐字生成——一个 token（模型处理文本的最小单位，约四分之三个英文单词）接一个 token 往下写，前沿模型一次回答要 3–329 秒（来源 01 引用的公开基准）。人可以等，代码里的判断等不起。
  • 可靠税：输出是自由文本，用之前要解析、要校验。再聪明的模型也会输出 schema（预先定义的数据结构）之外的值。在有延迟承诺、多层依赖的系统里，这是致命故障。
  • 置信税：让 LLM 自报"我有几成把握"，它倾向于过度自信、前后不一。一个 95% 时间正确的模型，说不清自己什么时候在错的那 5%，这 5% 就足以让任务无法自动化。

B市场的空白地带

现有方案各解决一角，没有一个全解决：

  • 约束解码（限制模型只能输出符合预设格式的内容）解决了格式，不解决速度和校准。
  • 小模型分类器便宜、快，但只能干少数几种活。
  • 读 logits（模型内部对每个候选答案打的原始分数）需要供应商开放接口，而且概率本身没经过校准训练。
  • 大厂的结构化输出接口仍是"先生成、再修剪"。

市场缺的是：把"决策"当作原生输出、从头训练的模型。TypeSafe 选的名字就来自这里——System One：专做"快思考"式的一秒内直觉判断，不和慢速推理模型抢活。

命名即战略：Jev 取自经济学家杰文斯（William Stanley Jevons）。他发现一个规律：蒸汽机效率提升后，煤的消耗不降反增（杰文斯悖论）。TypeSafe 把它读成 AI 版：智能的成本每降一个数量级，解锁的用例就多一个数量级。70–500 毫秒、0.0004 美元一次的判断，会出现在 3 秒、0.1 美元一次的判断永远进不去的地方。（来源事实：命名出处与定价来自官方博客；把杰文斯悖论读成 AI 成本曲线是官方声明。）

03 / Mechanism

核心原理：一次请求，状态进、类型化决策出

Jev 的接口只有一个动作：把一段"状态"（state，通常是一份 JSON 文档）和一组"问题"（questions）发过去，拿回每个问题对应的答案。没有对话历史，没有思维链，没有文字生成。所有答案的概率在一次请求里并行算出。

01 / STATE组装状态把要判断的原始内容装进一份 JSON 文档。字段名就是含义的边界，代码按字段名取值。
02 / QUESTIONS定义问题每个问题只问一个判断：是否为真（Noul）、选哪个（Choice）、打几分（Score）。
03 / PARALLEL并行出概率所有问题的答案概率一次算完，不是逐字生成。多问几个问题几乎不增加延迟，成本只按问题的字数算。
04 / CONFIDENCE派生置信度每个答案的概率分布由模型给出；置信度由分布的形状算出——概率越集中在某一个选项上，模型越自信。
05 / COMPOSE代码做决策按阈值放行、走 if 分支、加权合成、转人工。组合逻辑全在代码里，改权重不用改提示词。
70–500 毫秒端到端延迟（来源 01）。对比前沿 LLM 的 3–329 秒。官方博客称同等智能水平下快 40–200 倍（发布宣传口径曾写成 20–200 倍，见争议 02）。
输入 0.042 美元 / 百万 token输出免费。对比 LLM 输入 0.2–10 美元/百万 token，输出约为输入的 5 倍（来源 01）。
约 32,000 token / 请求状态和问题共享的预算上限，约合 15 万英文字符（来源 02）。问题数量只受预算限制。

三种原语：把"判断"定型成三种可执行形状

文档把问题收敛为三种，每种返回固定结构的答案（来源 02）。Noul 回答"是否为真"，返回 0 到 1 之间的概率。0.5 表示模型认为对错各半，不是"程度中等"。Choice 回答"是哪一个"，返回选中的项、全部选项的概率分布和置信度。官方称最多支持 255 个选项；选项很多时，官方建议用"先评分、再选择"的两段式。Score 回答"在哪个级别"，沿你自己定义的有序等级返回位置、分布和置信度。

置信度怎么算出来的：不是自我感觉，是分布形状

置信度看似仍是模型自评，机制上却不是自我打分：它由概率分布的形状算出，三个选项时近似等于 (3 × 最大概率 − 1) / 2——概率全集中在一个选项上，置信度 1.0；摊平到各选项，接近 0。注意 Noul 不带置信度，只返回概率值；官方接口同时返回完整概率分布，并明说"你不必用我们的定义"，使用者可以按自己的算法另算（来源 09）。

概率本身仍是模型自报的，承诺靠训练与验证兜底：RLCD 在训练里惩罚报不准的概率；官方同时明确，校准描述的是成组预测的命中率，不保证任何单个答案，阈值要用使用者自己的数据测（来源 02、10）。"模型自报概率、训练约束诚实、自建统计验证"三层合起来才是置信度的完整用法，单看任何一层都不够。

RLCD：把校准从技巧变成训练目标

现有 LLM 的训练方法有两个代表。RLHF（基于人类反馈的强化学习）奖励"人类更喜欢的说法"；RLVR（基于可验证答案的强化学习）奖励"答案正确"。两者都不训练模型报准概率——RLVR 的奖励作用于整条回答，不管"这题我有八成把握"报得准不准。

TypeSafe 的 RLCD（校准决策强化学习）不同。官方描述是"为校准的决策而训练，概率对照真实结果优化"。通俗说：模型报 90% 把握时，应当在约 90% 的情况下真的对。校准（报出的概率和实际命中率吻合的程度）由训练保证——概率报不准，模型在训练里直接受罚，不靠事后技巧。

官方把三种训练路径摆在同一张图上：聊天模型、推理模型、决策模型从同一个起点（预训练语言模型）出发，各自选定优化方向（来源 10）。选 RLHF 这条路的代价官方写得直白：奖励的是"人类更喜欢的说法"，模型学会讨好——包括自信地编造，因为自信的说法听起来更可信。TypeSafe 赌的是另一个方向：机器原生智能（Machine Native Intelligence）——未来模型交互的绝大多数将发生在机器与机器之间，输出必须像软件一样可预测（来源 10）。

官方未公开架构和训练细节。社区对"并行输出怎么实现"存在猜测，截至发稿未见官方证实（来源 05）。

一次把问题问全，反而更便宜：官方鼓励把"可能需要"的问题一次全问。每个问题按字数计价、并行评估、几乎不增加延迟，答案用不用由代码决定。官方 cookbook（示例代码集）的数据：13 个问题合并为一次调用，比 13 次单独调用便宜 11.5 倍、快 9.6 倍，答案不变（来源 02）。这和传统"少问省 token"的 prompt（提示词）直觉完全相反。

大小模型协同不新，新的是把任务适配成本打到接近零

"大模型管生成、小模型管判断"的协同格局早就存在：路由和分类一直是小模型的活。以前的做法是给每个场景专门训练一个小分类模型——标数据、训练、评估、上线、维护，一整套流程；场景一变（新意图、新标签）、喂进去的数据一变，都得重训；N 个场景就是 N 套模型资产。这套投入只对够大、够稳的场景划算，窄、碎、多变的场景要么直接调 LLM、要么硬编码。所以协同喊了很多年，小模型的实际地盘一直很窄，工程意义有限。

Jev 引起反响，不是因为它发明了协同，而是它把这个格局里最贵的一环拿掉了：任务适配。传统小模型换任务靠重训，Jev 换任务靠改问题文本——新任务是新的选项列表、新的等级标尺，一次请求里定义完，不存在训练环节（来源 02）。适配成本从"一个机器学习团队的训练周期"压到"写问题定义的几分钟"；一个模型同时覆盖分类、路由、评分、是否四类判断，不用每类各训一个。加上 0.0004 美元一次的判断成本（来源 03），"小模型的价格、大模型的通用"这个组合第一次成立。

它能通用而传统小模型不能，机制上是起点不同：传统小模型从头训练，只认识训练数据里见过的模式；Jev 从预训练语言模型后训练而来，继承了底座的语言理解，任务靠语言描述传达——没专门训过的场景，也能靠语言理解接住（来源 10；"通用性来自底座继承"是本文推断）。

把反响大的原因收成一句话：它把"判断"从机器学习团队的项目制资产，变成每个工程师账上的一个 API 调用，可用人群扩大了一个数量级——HN 的 1699 分、459 条评论，是这个扩大面的直接读数（来源 04；此为本文归纳）。

官方博客配了两个演示（来源 01）。一个是 Doom 实时游玩：把游戏状态实时转成结构化文本描述喂给 Jev，模型按帧循环查询、输出下一步行动。另一个是 Wikiracing（维基百科词条链接竞速）：给定起点和目标词条，模型每步从当前页面的众多链接中做一次 Choice。两个演示说的是同一件事：把亚秒级判断放进高频循环里当"反应"用，而不是当一次性的长回答。

路线怎么得到结构化概率速度/成本校准性与 Jev 的差距
LLM + 约束解码
（限制输出必须符合预设格式）		解码时限制 token 只能来自合法集合，保证格式匹配仍是逐字生成：格式合法但照样慢；选项多时逐字试错概率来自 RLHF/RLVR 模型，没经过校准训练，过度自信依旧只解决了格式和可靠两项，速度和置信照旧。HN 讨论认为 Jev 若只是约束解码不会有这个速度（来源 04）
LLM + logits/logprobs
（模型对每个候选答案的原始分数）		读模型最后一层原始分数拼置信度一次生成，比约束解码快，但仍受输出长度拖累RLHF 之后"概率不等于置信"已是共识；主流 API 也不开放 logits，社区归因于怕被拿去训练小模型（防蒸馏）社区称"Qwen 4B 加抓 logits 几乎就是 Jev"。差距在两点：校准是不是训练目标、接口开不开放（来源 05）
编码器分类器
（GLiNER 这类现成工具）		编码器对"文本-标签"对直接打分输出概率快且便宜，接近 Jev面向打标签任务设计，不是通用判断Reddit 把它列为"现成等价物"，但覆盖任务窄：自由提问、等级打分、255 选项都做不到，接口也不成体系（来源 05）
小 LLM 做分类路由
（deepseek v4 flash、haiku 4.5 等）		提示词要求输出类别，或配合约束解码秒级；官方评测中 DS v4 flash 客服任务 76.8%，反而高于 Jev 的 76.0%（来源 03）没有原生置信度；HN 讨论认为分类任务"非前沿模型加一点手艺也已极好"已是很强的存量方案：Jev 的增量在延迟（0.4 秒 vs 34.6 秒）和成本（约 30 倍差距），不在准确率
开源复刻
（openjev 等）		Qwen 4B（约 40 亿参数）级开源模型加 logits 输出层，发布 24 小时内出现，带浏览器可玩 demo宣称复刻 Jev 的交互形态没有 RLCD 训练，校准性未经验证说明接口形态容易被复制；本文据此推断 Jev 的护城河更可能在校准质量和产品化，不在架构本身（来源 05）

差异点说清楚：把五条路线摆在一起看："结构化输出"不新（约束解码就做到了）、"读概率"不新（logits 就做到了）、"快分类"不新（编码器和小模型都快）。Jev 的差异点是把三件事同时做成默认形态：格式由构造保证、概率由训练校准、延迟由并行采样压进一秒内——并且配齐了 SDK（软件开发工具包）、置信度语义、请求预算这些生产接口。单点都能被替代，组合体目前没有第二个供应商。（前半句是来源事实归纳；最后一句是本文推断：OpenRouter 无上架、vLLM/Ollama 无支持是证据。）

06 / Use cases

典型应用场景与任务边界：一把尺子、九个坑

哪些判断交给 Jev、哪些别交给它，官方给了两个答案：一把正向的尺子，和一份反向的自曝清单（来源 07、11）。

官方的分工尺子

一段判断该不该给 Jev，官方文档的标准是一句话：把完整资料摆在一个内行面前，他几秒钟内凭直觉能做出的判断，就适合 Jev；需要展开多步推理、或者要同时权衡多个独立因素的，要么拆成多个问题交给代码组合，要么直接用推理模型（来源 07）。官方给自家定位的原话是"Building prod, not God"（做生产零件，不做全能的神）——不追求什么都会，只把一类判断做到又快又准（来源 07）。

典型应用场景：判断跑在高频循环里

A四类基础场景

官方文档与评测划出的直接落位（来源 01、03）：

  • 分类与路由：客服问题分派、工单分类、请求入口的意图识别。
  • 守门与审查：给 LLM 的输出做事实核查与合规审查；Agent（能自主调用工具、多步完成任务的 AI 程序）每步执行后跑一批问题做检查。
  • 大批量处理：发票、安全事件这类一次进一批的结构化判断。
  • 实时应用：对延迟敏感的流程内判断，替代原来的硬编码规则或人工抽查。

官方评测用的四项任务（安全事件分类、Agent 轨迹审查、发票处理、客服分类），本身就是这份场景清单的量化版（来源 03）。

B三个进阶形态

  • 高频循环当"反应"用：官方两个 demo——Doom 把游戏状态逐帧喂给模型、按循环取下一步行动；Wikiracing（维基百科词条链接竞速）每步从当前页面的链接里做一次 Choice（来源 01）。
  • Agent 监督层：社区讨论中最被看好的落位——长跑 Agent 每步之间用亚秒级判断守门（来源 04，属讨论中的使用构想）。
  • 意图路由：官方使用模式：入口用 Jev 把请求分类，再路由到确定性代码、专家 LLM 或人工（来源 07）。

三个形态的共同点：判断不是一次性长回答，而是嵌在循环里的高频动作。

官方自曝的九种失败模式

比官方宣传更值得看的是这份自曝清单——Jev 1.13 已知会失手的九类情况，连同官方给的替代做法（来源 11，数据截至 2026-09-17）：

表格较宽，可左右滑动查看

失败模式表现官方替代做法
1 · 字面化理解你写什么字它答什么字，不揣摩意图；限定词、否定、隐含条件都按字面读把精确条件写进问题定义，边界情况写进判定标准；需要解释的地方拆成两个字面问题，用代码组合
2 · 数学和数字不是计算器：数数不可靠、数值精度差、用色值判断不如用颜色名算术全放代码；数值先在代码里转换成结果或命名区间，再传给模型
3 · 日期时间比较日期被当文本读，先后、间隔、时间窗判断不可靠抽取交给模型（月份、日期都是封闭选项），拼装和比较全放代码
4 · 多层间接推理双重否定、属性套属性、多跳推理，准确率下降指令写直白，用字段名直接指向要判断的内容，减少跳数
5 · 大状态无关细节无关内容是干扰项，状态越大准确率越降；官方称此为上下文腐烂（context rot，塞进无关内容损耗准确率）代码先过滤，只发问题需要的字段；没法过滤时先用一个是否题筛相关性
6 · 对抗性内容状态被默认当数据，不防提示注入（藏在数据里、企图操纵判断的指令）判定标准写明确，上线前把边界情况测透
7 · 矛盾指令与标准问题定义和判定标准要求不一致时，模型被夹在中间，表现变差把判定标准当问题定义的延伸，两者用清晰精确的语言对齐
8 · 结构不变量不保证直觉上应成立的数量关系会破：官方实测正问概率 0.72、反问 0.47，加起来 1.19 不是 1；同一问题换题型问，数值对不上别依赖想象中应成立的数量关系；一种题型调好的阈值别搬到另一种题型
9 · 生成任务没训练过生成文本，强行用链式选择拼文字，又慢又糟答案空间有限时把抽取做成选项让模型选；真要生成文字，用生成模型

官方四条使用铁律：代码能精确算的，别问模型；一个问题里别藏多个判断；System Two（慢思考：需要多步展开推理的任务）的活别给它；别塞超出问题需要的内容。最后一条的代价有名字：上下文腐烂——无关材料混进状态，准确率跟着往下掉（来源 11）。

所以"难任务交给 Jev 靠不靠谱"这个问题，官方自己的回答是：不靠谱，而且他们把不靠谱的方式列成了清单。数据也一致：发票处理 61.8%，比 opus 5 低 16.6 个百分点（来源 03）。正确姿势不是挑一个更聪明的模型，而是把难任务拆成一串简单判断、让代码做组装——评测里所有模型的 workflow 模式（拆解多问题加代码组合）都比单条提示词更准、更便宜、更快，正是这条路线的量化证据（来源 03）。

来源事实分工尺子与意图路由模式来自官方文档（来源 07，数据截至 2026-09-20）；九种失败模式、四条铁律、正反问概率漂移实测来自官方已知缺陷页（来源 11，数据截至 2026-09-17）。本文推断"监督层"落位来自社区讨论倾向；"拆解加代码组装是难任务的正解"是本文基于官方评测数据的方法论归纳。
07 / Engineering

工程化视角：从 Demo 到生产，隔着五件事

Jev 的接口设计已经带着生产味：阈值、置信度语义、请求预算都有。但把它接进真实系统，下面五个环节一个都绕不开。

接入生产系统要考虑的环节

部署形态：纯云 API，本地零资源

接入入口只有官方云 API：密钥在官方控制台申请；可以先在官方 Playground（在线试验场）网页上把问题试通，再写代码接入。官方提供 Python 和 JavaScript 两个 SDK，Python 版要求 3.10 以上（来源 08）；另有 agent skill（教 agent 一次批量提问的能力包）安装方式（来源 02）。

没有自托管或私有化选项（截至 2026-09-20 官方文档未见）。本地资源需求约等于一个网络请求客户端——不用 GPU、不用内存配额，真正的约束是单请求约 3.2 万 token 预算和网络可达性。推理与校准全部在官方服务端完成，这既是它快的原因，也是闭源锁定的起点。

问题设计是新的提示词工程，而且责任更重

官方文档要求每个问题只问一个维度（来源 02）。一个问题里混进两三个判断，概率就不准了，置信度会掉，分数失去意义。

和提示词工程相比，这里的错误更贵：模型不会替你把问题猜对，它只会诚实地返回低置信。问题写得好不好，直接决定这套系统好不好用——每个问题都是一份要长期维护的 schema。

置信度分级放行：官方给了可直接照抄的三段式

三段式：高置信自动执行；中置信走确认（问用户、标记审核、补信息）；低置信不动作，转人工或换系统。

地板值官方示例取 0.5。高风险动作再叠加第二道阈值：把握大于 0.9 才免确认。读操作低门槛、写操作高门槛——风险容忍度写进代码，不写进提示词（来源 02）。

校准漂移监控必须自建

校准是 Jev 的核心承诺，但官方文档只说"先用保守阈值、用自己的数据测"（来源 02）。

下面这些 MLOps（机器学习运维）基本功一样都不能少：用 ECE（期望校准误差：报出的概率和实际命中率差多少）监控校准漂移、对数据分布变化告警、给问题做版本管理。供应商保证了"类型不会错"，没保证"概率一直准"。

供应商与定价锁定风险

Jev 处于早期访问：闭源、单一供应商，"输出免费"的定价也不寻常。官方 FAQ 直言"无法证明定价没有补贴，需要长期证明可持续，我们预期它会降而不是涨"（来源 01）。

接入后，这家公司必须活得比你的业务久，系统才稳。问题格式全在它家标准上，迁移成本随问题库增长。

对现有 LLM 应用架构的影响

最直接的影响是分工：LLM 继续负责"生成"（写作、代码、总结、对话），决策模型接走"判断"（分类、路由、评分、守门）。HN 讨论中最被看好的落位，是给 coding agent（能自主写代码的 AI 程序）当"监督层"：agent 每步执行后跑一批问题做检查，用亚秒级判断给长时间运行的 agent 加护栏（来源 04，这是讨论中的使用构想）。官方文档也点名"coding agent 容易一次只问一个问题"，并发布了配套 agent skill 来纠正这个习惯（来源 02）。

第二个影响藏在官方评测里、容易被忽略：workflow 模式对 LLM 也成立。评测里每个模型都跑两种模式：把任务拆成多个问题、用代码组合答案（workflow），或者一整段提示词直答（prompt）。四项任务、所有模型、无一例外，workflow 模式更准、更便宜、更快：opus 5 从 64.8% 提到 73.1%，haiku 4.5 从 18.1% 提到 53.6%（来源 03）。"拆问题加代码组合"本身就是一条与 Jev 无关的方法论，今天就可以用在现有 LLM 的路由和分类逻辑上。

从 Demo 到生产可用，主要差距在哪里

差距一：评测公信力。参考答案是 GPT-6 Astra 和 Claude Fable 5.1 两个最强模型的平均，官方自己承认"偏向 OpenAI 与 Anthropic 的模型、可能低估自家与 DeepSeek"（来源 01、03）。而且方法假设"工作流代码本身正确"——真实系统里，工作流是要维护、要测试的活代码。

差距二：能力边界没有摸清。四项任务里，Jev 发票处理只有 61.8%（opus 5 为 78.4%），Agent 轨迹审查 71.6%（低于 luna 的 76.1% 和 sol 的 76.6%；luna 与 sol 是评测站列出的对比模型）。"接近前沿智能"在部分任务上并不成立，选型必须逐任务实测。

差距三：生态为零。OpenRouter 未上架（来源 06），vLLM 和 Ollama 没有对应接口，没有第三方基准，Reddit 社区明确呼吁 vLLM 支持这类推理接口（来源 05）。可观测、灰度、回滚、私有化部署，全部自己搭。

来源事实三段式阈值与示例、agent skill、32K 预算、评测数字与自评偏向声明，均来自官方文档与评测站（来源 02、03）；部署形态与接入方式来自官方快速开始文档（来源 08）。本文推断"分工架构"和"监督层"落位综合自 HN/Reddit 讨论倾向；ECE 监控自建的必要性是本文工程判断。
08 / Critique

局限与风险：发布 24 小时内被争透了的六件事

HN 帖子的 459 条评论几乎把这项发布拆解了一遍，官方联合创始人也在场逐条回应（来源 04）。下面六点是争论的实质内容，判断留给读者。

争议 01 · 强度：高

"不能幻觉"是个被压缩的定义

官方语境：不会输出 schema（预设数据结构）之外的值，类型错误在数学上不可能。批评语境：自信地给出类型正确但事实错误的值，同样是幻觉。官方在 HN 承认"类型安全不等于事实正确"，也主张"随机森林（一种传统机器学习模型）不像 LLM 那样幻觉"——但博客宣传图用 0% 幻觉对比 LLM 的实测数字，这个视觉修辞已经越过了它自己承认的边界。

争议 02 · 强度：高

标题在发布一小时内被修改过

原帖标题"Jev: New frontier model 40-400x cheaper and 20-200x faster"（倍数是发布方宣传口径，与官方博客"快 40–200 倍"不完全一致）被指出误导后，一小时内改为现标题。"frontier model"（前沿模型）的称谓也被质疑：它放弃了文字生成，就不能再按通用模型的尺子量。准确的说法是：它在"结构化决策"这个子任务上，做到了又快又好又便宜。

争议 03 · 强度：高

对比基准不对等

LLM 参与对比时，要把类型名、格式文本一个字一个字生成出来；Jev 直接输出数字。更公平的对比是让 LLM 也只输出原始数值。官方回应称这是让 LLM 以"最准确的决策模式"参赛，但也承认该模式比 LLM 平常用法更慢更贵。

争议 04 · 强度：中

模型规模与能力上限成谜

官方未公布参数量和架构。HN 有评论按"没有长上下文、Choice 选项有限"推测它的规模不大；官方博客强调 Jev"不是小 LLM"，但没给出可验证的证据。可以确认的是：Jev 在发票任务上和 opus 5 差了 16.6 个百分点（61.8% vs 78.4%，来源 03），复杂内容的理解仍有硬上限。

争议 05

单题校准 ≠ 组合校准

每个答案的概率是校准的。但把十几个答案的置信度组合成一次业务决策时，组合结果是否仍然校准，官方没有给方法。HN 评论指出：一个不该放行的操作，完全可能在其他判断维度上得分很高。组合层的校准验证，最终落在使用者头上。

争议 06

Demo 的输入不是你以为的输入

Doom 实时游玩 demo 喂给模型的不是游戏画面，而是游戏状态的结构化文本描述（官方在博客中自注）；Wikiracing 对比的是各模型的非推理模式。两个 demo 都合法，但都应该按"结构化状态输入下的判断速度"来理解，不是"模型看画面打游戏"。

诚实边界声明：本文对 Jev 的全部能力描述均来自官方博客、文档、评测站和公开社区讨论（来源 01–05），未包含作者实测数据。官方声称中，可独立验证的（速度、定价、类型安全）和不可独立验证的（智能水平、校准质量）已在上文分开标注；引用的评测均为厂商自建，采信前应以自有数据复测。

09 / Outlook

未来方向：决策模型会不会成为下一个品类

以下是本文推断，依据的来源事实在各条内标注。

A品类分化已成趋势

模型市场正在从"一个 LLM 干所有事"，走向按任务分工：对话模型、推理模型、决策模型各占一档。Jev 发布 24 小时内 HN 1699 分、459 条评论，Reddit 当天出现复刻讨论帖（来源 04、05）——一个新品类的关注度门槛已经跨过。按官方声明的杰文斯逻辑，亚秒级、微美元级的判断一旦普及，"决策模型"可能成为独立采购项。

B生态与标准的三个观察点

一，推理栈支持：vLLM/Ollama 还没有这类接口，Reddit 已出现明确呼声（来源 05）——若 vLLM 落地"概率输出"接口，开源复刻潮会真正开始。

二，聚合渠道：OpenRouter 未上架 TypeSafe（来源 06），说明它仍在早期访问阶段，规模化信号未到。

三，大厂跟进：现有结构化输出接口离"校准概率"只差一步训练目标——RLCD 思路被证明后，主流 API 把概率做成默认输出的门槛不高。

更远一层的想象（本文推断，无来源佐证，置信度自评：中低）：Agent 架构可能长出"双系统"形态——LLM 负责慢速规划和生成，决策模型负责每一步之间的快判断（审查、守门、路由）。这类需求正在两个方向同时增长：Agent 要连续跑数小时，每一步都需要有人守着；Agent 越自主，对它行为的审查要求就越高。两个方向最终指向同一种能力——亚秒级、可校准、可组合的判断。

10 / Takeaways

工程师可以借鉴：不换模型也能带走的五件事

以下五条是本文从这则发布中归纳的经验，和是否选用 Jev 无关。引文和数据来源随条标注。

让接口直接返回概率

logits 被主流 API 藏起来是产品决策——社区归因于防蒸馏（防止别人拿你的模型输出训练小模型，来源 05）——不是技术做不到。内部模型服务完全可以把"每个输出带概率"做成默认形态：下游拿到的不是一次赌注，而是可设阈值、可分级的信号。

问题分解优于长提示词，且对所有模型成立

官方评测里，所有模型的 workflow 模式都比单条提示词更准、更便宜、更快（opus 5：64.8%→73.1%）。把一大段要求拆成带类型的问题加代码规则，是今天就能在现有 LLM 上用的方法（来源 03）。

三段式置信放行可以直接抄

低置信不动作、中置信走确认、高置信自动执行；地板 0.5，写操作再叠 0.9。这套阈值结构（来源 02）适用于任何能输出概率的模型，风险容忍度明确写进代码。

给系统装一个"会说不知道"的部件

官方文档的立场值得记住："一个智能系统——无论人还是机器——若不能表达诚实的不确定，就不值得信任"（来源 02）。自建判断类功能时先问一句：它敢在什么时候说"我不知道"？说不知道的路径不存在，校准就无从谈起。

把厂商的"不能"还原成精确定义再做决策

"不能幻觉"实际指"不能输出预设格式之外的值"；"前沿智能"实际指"结构化决策子任务上的性价比领先"。采购任何 AI 能力时，把宣传语逐条还原成可验证的说法——这个审查习惯，比任何单一选型结论都值钱。
