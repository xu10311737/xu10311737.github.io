pi：把"不做什么"刻进设计的 10 万星开源 Coding Agent

Earendil 开源的极简 coding agent（能在终端里读代码、改文件、跑命令、连续多步完成编程任务的 AI 程序）pi，在 GitHub 攒到约 10.56 万 star，跻身 OpenRouter（模型 API 聚合网关，按其路由的 token 用量发布应用排行）应用用量榜前五。

它的差异化不在功能多，而在功能少得有纪律：系统提示加工具定义合计不到 1000 token；MCP（Model Context Protocol，外部工具挂载协议）、子代理（主代理派生的独立实例）、权限弹窗、计划模式、内置待办、后台任务六件事被官方明确写进"我们不做什么"，每件都给出文件、tmux（终端复用器，可同屏管理多个终端会话）或扩展原语的替代路径——"让 pi 适应你的工作流，而不是反过来"。

先给结论pi 押注的判断是：2026 年的前沿模型经过强化学习（RL，用奖励信号训练模型行为）已经"天生会当 coding agent"，harness（本义"挽具"，指包裹模型、供其调用工具并循环执行的运行环境）的价值从"替模型操心"转向"给工程师控制权"。对做 Agent 系统的工程师，值得抄的不是它的功能清单，而是它的三张账单：上下文账（什么进上下文、占多少 token）、安全账（弹窗是剧场、边界在环境）、治理账（依赖最小信任、会话数据全公开）。
TL;DR（太长不看）背景与问题核心原理创新与差异竞品对比工程化视角局限与风险未来方向工程师可以借鉴数据源
01 / Decision brief

TL;DR（太长不看）：一个靠"负空间"取胜的开源 Harness

01 / WHAT

发生了什么

libGDX 游戏框架作者 Mario Zechner 发起的 coding agent pi（GitHub 仓库 earendil-works/pi，MIT 许可证）数据截至 2026-09-16 约 10.56 万 star、单日新增 437；OpenRouter 应用用量榜第五，约 2570 亿 token。2025 年 11 月它还是个人仓库 badlogic/pi-mono，如今由 Earendil Inc. 主导开发。

02 / WHY

解决谁的问题

主流 harness 功能持续膨胀、系统提示与工具定义随版本漂移、上下文在用户看不见的地方被注入、会话细节不可检查。pi 面向的是"想要一个稳定、可完全控制、可观测的执行环境"的工程师，而不是要开箱即用全家桶的用户。

03 / HOW

核心机制

极简核心：系统提示加四个工具（read、write、edit、bash）不到 1000 token；六个"不做"全部配替代路径；缺的功能用 TypeScript 扩展实现（官方维护 50 多个示例），甚至可以让 pi 边运行边改自己，/reload 热加载。

04 / SHIP

生产判断

pi 默认无权限确认（作者称 YOLO 模式，跳过一切确认直通执行），接入生产前必须先解决隔离：官方给出 Docker、Gondolin 扩展（本地微型虚拟机）、OpenShell 三条容器化路径。token 与成本统计为尽力而为口径，不可直接当计费依据；第三方扩展截至发稿未见强制安全扫描，安装前人工审查责任在使用者。

来源事实star 与用量数据来自 GitHub Trending、GitHub 仓库页与 OpenRouter 排行页（数据截至 2026-09-16）；系统提示原文、六不原则、供应链策略、基准结果均转写自 pi.dev 官网与作者公开博文（来源 01–04）。本文推断"极简路线如今可行"依赖一个前提——模型侧的 agentic 能力已被训练内化；若该前提变化，"负空间"设计不会自动失效，但竞争力会向扩展生态倾斜。
02 / Background

背景与问题：Harness 军备竞赛的另一面，是失控的上下文

2025 年起，coding agent harness 成为开发者日常工具：Claude Code、Codex、Cursor、Amp、opencode、Droid 相继成为主流选择。竞争的主流打法是加法——更多内置功能、更长的系统提示、更重的流程管控。pi 的作者 Mario Zechner 是这场军备竞赛的深度参与者（游戏框架 libGDX 的作者，二十余年开源老兵），他的结论却相反：加法正在伤害这类工具的核心用户。

A加法 harness 的四个痛点

作者在公开长文里逐条列出了他弃用 Claude Code 转而自建的理由（来源 03），每一条都指向"控制权"：功能膨胀——"它变成了飞船，80% 的功能我用不上"；版本漂移——系统提示与工具定义每次发布都在变，既破坏用户工作流，也改变模型行为；上下文黑箱——harness 在用户看不见的地方注入内容，"真正的上下文工程（context engineering，精确控制进入上下文窗口的内容）在现有工具里做不到或极难做到"；可观测性缺失——"我想检查与模型交互的每一个细节，基本没有 harness 允许"。此外，依赖 Vercel AI SDK（SDK，软件开发工具包）这类高层抽象的工具（如 opencode）对自托管模型的支持不佳，工具调用经常出问题。

B为什么此时出现 pi

pi 的成立依赖两个条件先后成熟。模型侧：作者观察，前沿模型经过大规模 RL 训练后"天然理解 coding agent 是什么"，不需要上万 token 的系统提示来教（来源 03）——harness 里大量"替模型操心"的指令变成了冗余。工程侧：与 pi 同在 Earendil 的 Flask 作者 Armin Ronacher 在同期文章（来源 04）给出独立佐证：高层 SDK 抽象在真实工具调用场景下会破裂（Anthropic 的网页搜索工具经 Vercel SDK 会破坏消息历史），"构建 agent 时直接对接各厂商原生 SDK 才能保持完全控制"——Earendil 已经放弃了 Vercel AI SDK 路线。2025-11-30 作者发文公布 pi，2026 年 9 月项目已由个人仓库迁入 earendil-works 组织，star 突破 10 万（来源 01、02、06）。

判断边界：本文不评测"pi 干活好不好用"——那需要长期实测；本文回答的是"它把 harness 的设计重心从功能移到了哪里，哪些决策可以迁移到你自己的系统里"。全部能力描述来自官方文档、仓库页面与作者公开博文，未包含作者实测数据。

03 / Mechanism

核心原理：四层解耦的最小骨架，每层只做一件事

pi 不是单个 CLI（命令行程序），而是一个 monorepo（单仓库多包）里的六个可独立使用的包。coding agent 的完整链路被切成了职责分明的四层，另有两个横向配套——这种解耦意味着各层都能脱离 pi 单独复用。

01 / MODELpi-ai：统一模型 API直连四类原生 API（OpenAI Completions/Responses、Anthropic Messages、Google GenAI）及任意 OpenAI 兼容端点；处理各供应商差异；跨供应商上下文交接；全链路可中断；token 与成本追踪。
02 / LOOPpi-agent-core：Agent 循环处理工具执行、参数校验、事件流与消息排队；循环不设步数上限——跑到模型自己说完成；可经传输抽象直跑或走代理。
03 / RENDERpi-tui：终端渲染保留原生滚动与搜索的"追加式"终端界面；组件级缓存加差分渲染，配合同步输出转义序列，把闪烁压到近零。
04 / AGENTpi-coding-agent：CLI 组装会话树、四运行模式、扩展系统、skills（能力包）、主题、AGENTS.md 项目上下文加载——把前三层拼成一个产品。
05 / SIDEchord + telemetry 配套chord 是独立的应用组合运行时（服务、复制状态、RPC 即远程调用、插件）；pi-telemetry 定义厂商中立的遥测契约。

01pi-ai：把"统一 API"做在供应商怪癖之上

统一 LLM API 的难点从来不是接口签名，而是供应商差异。pi-ai 的做法是直连原生 API 并显式吸收怪癖：Cerebras、xAI、Mistral 等不接受 store 字段、不认 developer 角色；有的用 max_tokens、有的只认 max_completion_tokens；推理轨迹在不同供应商返回的字段名不同（来源 03）。三个生产级设计值得注意：全链路可中断——任意环节可 abort，且返回已生成的部分结果而非丢弃；工具结果双通道——工具可同时返回"给模型看的 output"与"给界面渲染的 details"，UI 不必反向解析文本；参数流式渐进解析——模型边生成工具参数边解析，界面能实时流式显示文件改动的 diff。跨供应商切换会话时，Anthropic 的思维链被转写为 <thinking> 标签文本交给下一家模型（来源 03）。

02pi-tui：差分渲染换来的"零闪烁"

终端 UI 有两条路线：全屏接管式（Amp、opencode）要自己重造滚动与搜索；追加式（Claude Code、Codex、pi）保留终端原生能力。pi 选追加式，代价是渲染要精细：组件树缓存已渲染行，更新时找到第一处差异行、只从那里重绘到末尾；用户上滚出视口时整体重绘；所有输出包在同步输出转义序列（终端的标准原子刷新指令）里一次性提交。作者的对照结论：在 Ghostty、iTerm2 上几乎无闪烁，仍优于 Claude Code（来源 03）。

下面是 pi 系统提示的主体——英文原文节选，转写自来源 03。除按项目加载的 AGENTS.md 外，pi 不向上下文注入任何别的内容：

You are an expert coding assistant. You help users with coding
tasks by reading files, executing commands, editing code, and
writing new files.

Available tools:
- read: Read file contents
- bash: Execute bash commands
- edit: Make surgical edits to files
- write: Create or overwrite files

Guidelines:
- Use bash for file operations like ls, grep, find
- Use read to examine files before editing
- Be concise in your responses

这段系统提示与四个工具的定义合计不足 1000 token（来源 03）。

03上下文工程栈：每样东西都明码标价

pi 的上下文组装全部显式：AGENTS.md（业界渐成的项目说明文件约定）从全局目录、父目录、当前目录分层加载；SYSTEM.md 可按项目整体替换或追加默认系统提示；compaction（上下文压缩：接近窗口上限时自动摘要旧消息）通过扩展完全可定制，可换摘要模型、可做代码感知摘要；skills（能力包：指令加工具的组合）按需加载，不破坏前缀缓存（prompt cache：请求开头不变时，服务商可复用已算好的部分，降费提速）；prompt templates 把可复用提示词做成 Markdown，输入 /名称 展开；扩展还能在每个回合前动态注入消息、过滤历史、实现检索或长期记忆（来源 01、03）。

04会话树与四种运行形态

会话存成树而非线性列表：/tree 可回到任意历史节点另起分支，全部分支在一个文件里；/export 导出 HTML，/share 上传 GitHub gist 得到可分享的渲染页（来源 01）。运行形态有四种：交互 TUI；pi -p 打印模式与 JSON 事件流供脚本调用；RPC（Remote Procedure Call，远程过程调用，程序间经管道或网络互相调用接口）模式经标准输入输出跑 JSON 协议，供非 Node 技术栈集成；SDK 模式把 pi 嵌进应用（开源项目 OpenClaw 是官方引用的真实集成案例）。agent 工作中可随时插入消息：Enter 发"转向"消息（当前工具完成后送达、打断剩余工具），Alt+Enter 发"跟进"消息（等 agent 做完再送）——这是对长任务失控感的直接回应。

一个反直觉的取舍：pi 刻意让系统提示"不随模型调整"。直觉上各家模型应在原生 harness 的提示下表现最好，但作者的实测经验是：训练充分的前沿模型不需要模仿某家 harness 的专属提示，稳定不变的短提示反而让行为可预期、让前缀缓存保得住（来源 03）。harness 追着模型版本改提示，本身就是一种不稳定源。

04 / What changed

创新与差异：六个"不做"，每个都有替代路径

pi.dev 官网用专门一节陈列"我们不做什么"——把产品的负空间当成卖点公开承诺。这不是噱头：每个"不做"都有官方替代路径与理由，且大多数给出了可安装或可抄的参考实现。

官方不做替代路径官方理由（来源 01、03）
不内置 MCP带 README 的命令行工具，agent 按需阅读；或用 mcporter 把 MCP 服务器包装成 CLI；或写扩展自行支持流行 MCP 服务器把全部工具描述常驻上下文：Playwright MCP 21 个工具约 13.7k token、Chrome DevTools MCP 26 个约 18k token——开工前先占掉 7–9% 上下文窗口
不内置子代理经 bash 或 tmux 派生新的 pi 实例；或用官方 subagent 扩展示例子代理是"黑箱里的黑箱"：内部过程不可见、上下文交接不可控；会话中段才想起用子代理收集上下文，说明前期规划失败
不内置权限确认弹窗容器化运行；或用官方 permission-gate 扩展示例自建确认流能写代码又能跑代码的 agent，弹窗拦截基本是"安全剧场"——真正有效的边界只有运行环境隔离
不内置计划模式把计划写进 PLAN.md 文件；或用 plan-mode 扩展示例文件式计划跨会话存活、可进版本库、可与 agent 协同编辑，全程可观测——会话内建的临时计划模式三者全无
不内置待办清单TODO.md 文件，checkbox 即状态内置待办给模型引入需要维护的额外状态，出错机会更多；文件状态简单、可见、完全在用户手里
不内置后台任务tmux；agent 可列出、进入、共用同一会话后台进程管理是成熟问题，终端复用器早已解决——作者演示了与 agent 共用一个 LLDB 调试会话互相配合的形态

01原语而非功能：把功能从产品搬进用户空间

"其他工具焊死在产品里的功能，pi 都给原语让你自己搭。"扩展是普通 TypeScript 模块，可触达工具、命令、快捷键、事件与整个 TUI；官方示例库维护着 50 多个参考实现：子代理、计划模式、权限门、路径保护、SSH 执行、沙箱、MCP 集成、自定义状态栏等（来源 01）。扩展、skills、提示模板、主题可打包成 Pi package，经 pi install npm:@foo/pi-tools 或 pi install git:… 安装——复用 npm 这个 JavaScript 生态最大的包分发基础设施，而不是另造市场。

02自我扩展：agent 改写自己的运行环境

pi 最特别的交互形态：缺什么就让 pi 现场写——它可以直接改写自己的配置与扩展，改完 /reload 热加载继续干（来源 01）。"harness 即代码"在这里从口号变成日常操作：你的工作流定制不是配置项，是一段你能读、能审、能进版本库的 TypeScript。官网的展示包括一个运行在 pi 里的 DOOM 扩展——用来说明扩展面已经宽到什么程度。

03供应链与社区治理：把"不信任"写成流程

一个会被 agent 执行任意命令的工具，其自身供应链就是攻击面。pi 的对策是六个可抄进任何 Node 项目的纪律：npm 依赖变更视为需人工审查的代码变更；依赖精确版本固定；lockfile（锁文件，把依赖版本钉死的清单）是唯一事实来源；min-release-age=2——发布不满两天的依赖不装，专门防"新包投毒"；--ignore-scripts——安装时跳过执行包内脚本；生命周期脚本白名单加 CI 里的 npm audit（来源 02）。社区治理同样强硬：新贡献者的 issue 与 PR 默认自动关闭，维护者每天人工复核——这是对 AI 生成低质贡献（slop）泛滥的直接回应。

04会话数据开源：把真实工作流变成公共语料

pi-mono 会话数据经 pi-share 发布到 Hugging Face（badlogicgames/pi-mono 数据集），作者明说动机：用真实世界任务数据改进 coding agent，而不是只靠玩具基准（来源 02、03）。一个 harness 公开自己的完整使用轨迹——包括失败与返工——在同类项目里相当少见，这既是研究资产，也把"我们到底怎么用它干活"变成了可审计的事实。

基准佐证，而非基准崇拜：作者把 pi（配 Claude Opus 4.5）送进 Terminal-Bench 2.0（laude-institute 的终端任务基准），每任务五次完整跑分，完整结果与可复现的结果文件一并公开（来源 03、08）。作者据跑分得出的结论是：极简工具集与专用 harness 的差距远小于直觉。更硬的旁证是同榜的 Terminus 2——只给模型一个 tmux 会话、纯文本交互的极简 agent，同样在榜上站稳。两个结果合起来指向一个判断（本文推断）：工具复杂度与最终成绩的相关性，比功能清单给人的直觉低得多。作者同时诚实记录了基准的局限：美国太平洋时段上线后错误率上升，结果随之变差。

06 / Engineering

工程化视角：三个生产问题

问题一：接入生产系统，要先过哪几关？

第一关是隔离，且不可跳过。pi 默认以你的用户权限运行、无任何确认（来源 02、03），接入生产凭据前必须先画环境边界，官方给出三条路径：普通 Docker；Gondolin 扩展——宿主保留 pi 与供应商密钥，把工具执行与命令路由进本地 Linux 微型虚拟机（micro-VM，进程级轻量隔离）；OpenShell——策略控制的沙箱。第二关是供应链。官方安装命令自带 --ignore-scripts，扩展安装来自 npm 与 git——截至发稿，其公开文档未见对第三方扩展的强制安全扫描与权限声明机制，安装即信任，审查责任在使用者。第三关是集成形态。脚本化用 print/JSON 模式；非 Node 技术栈用 RPC 协议；嵌入产品用 SDK——OpenClaw 是官方引用的完整案例。第四关是计量。各供应商对 token 与缓存读写的上报口径不一（有的在流首、有的在流尾，中断后无法对账），pi 的成本追踪是尽力而为口径（来源 03），适合自用参考，不能直接当计费系统。

问题二：它对现有 LLM 应用架构有什么影响？

最直接的影响是 harness 的解绑（unbundling）：模型 API 层（pi-ai）、循环层（pi-agent-core）、渲染层（pi-tui）各自独立可用——你不必用 pi 的 CLI，可以只拿 pi-ai 做一个与 coding 无关的对话应用。这代表一种架构主张：harness 不该是铁板一块。第二层影响是对"统一 SDK"路线的修正：Earendil 的实战结论（来源 04）是高层抽象在真实工具调用下破裂、显式管理缓存点优于自动管理——Anthropic 的缓存需要手工设点（系统提示后一处、会话头部两处），系统提示与工具因此必须保持静态，动态信息（如当前时间）放到后置消息注入。这条经验对一切自建 agent 循环的团队直接适用。第三层影响是上下文管理的标准化：AGENTS.md 分层加载正在成为项目级约定，pi 的 skills 渐进披露提供了不破坏前缀缓存的扩展模式（来源 01、03）。

问题三：从 Demo 到生产可用，主要差距在哪里？

四个差距。基准不等于生产：作者自己强调 Terminal-Bench 不代表真实表现，且结果随时段漂移（来源 03）——上生产前必须用自己的任务集回归。模型仍是上下文收集短板：作者观察模型被训练得倾向只读文件的局部，常漏掉完成任务所需的关键上下文；pi-mono 的 issue 跟踪器里大量贡献因此被关闭——"我们太信任 agent 了"。对策不是更好的工具，而是工作流：先在独立会话收集上下文、产出可复用的 artifact（工件文件），再开新鲜会话带着 artifact 干活。并行多代理写码是反模式：作者的原话是——除非不在乎代码库退化成垃圾堆（来源 03）。评测仍是行业级未解难题：同司的 Armin 直言测试与评估是他们遇到的最难问题，现有方案没有一个令人满意（来源 04）——这一点 pi 也没解决，它只是把"你看到的就是全部上下文"做实了，让失败可归因。

部署边界提示

官方文档明确：pi 不内置权限系统、以启动用户身份运行，所有安全边界外置给容器化方案（来源 02）。这构成一条清晰的部署纪律：容器先于凭据，凭据先于任务。会话数据方面，树状历史默认落盘本地、可导出可分享——团队引入时要自行决定哪些会话可以离开机器；公开仓库里作者本人把 pi-mono 会话持续发布到 Hugging Face，这是个人选择而非默认行为。Windows 有原生 PowerShell 安装脚本，安装走 pi.dev/install.ps1。

07 / Risks

局限与风险：把控制权交给用户，也把责任交给了用户

高

无确认直通是真实攻击面

pi 可经 curl 读写网络、可执行任何命令、可读任何文件——这些都是提示词注入（prompt injection：把恶意指令藏进模型会读的内容里、诱导其执行）的入口。作者引用的安全论述（来源 03）承认：读数据、执行代码、网络访问三者不可兼得，弹窗也防不住；Simon Willison 的双 LLM 隔离模式同样被其提出者自评为"相当糟"。pi 的答案是诚实的放弃——但"诚实"不降低风险，只把风险移给了懂行的人。

高

扩展供应链无护栏

pi install 直装任意 npm 包或 git 仓库。截至发稿，其公开文档未见类似技能目录的强制扫描、危险操作拦截或权限声明机制。在"扩展可触达工具与整个 TUI"的设计下，一个恶意扩展的权限等同 pi 本体——第三方扩展引入前的人工审查没有替代品。

中

极简是门槛，不是免费午餐

六个"不做"意味着大量开箱即用的便利需要自行组装——或让 pi 现场替你写。对不写 TypeScript 的用户，官方答案是"装一个别人写的包"，这又回到上一条的供应链问题。毛坯房对建筑师是自由，对租客是负担（本文推断）。

中

社区治理限制了贡献增长

新贡献者的 issue 与 PR 默认自动关闭、维护风格自述为"独裁式"、官方给出的分歧出口是"欢迎 fork"（来源 02、03）。这在 slop 泛滥的当下保护了主干质量，代价是外部贡献的持续摩擦——对一个依赖生态繁荣度的原语型项目，这是需要观察的长期张力。

中

统一 API 的泄漏抽象

供应商差异是永远的地心引力：token 计量口径不一、跨供应商思维链交接是有损转写（Anthropic 思维链被改写成普通标签文本）、工具调用流式在个别大厂 API 上仍不支持（来源 03）。任何"统一层"都只能尽力而为——把它当契约而非保证。

中

单公司主导的可持续性

pi 由 Earendil Inc. 主导开发，域名由第三方捐赠，商业化路径未见公开披露（来源 01、02）。原语型 harness 的价值恰恰依赖长期稳定——10 万 star 的社区若与公司战略出现分歧，fork 是官方明示的退出通道，但生态分裂成本已经预付。

安全结论：pi 的部署顺序应当是——先容器（Docker、Gondolin 或 OpenShell 三选一），再凭据，最后才放任务。它对"弹窗派"的批评值得认真对待：确认疲劳让弹窗沦为点击仪式；但它的替代方案要求团队具备容器化运维能力。没有免费的边界，只有画在不同层的边界。

08 / Outlook

未来方向：极简 harness 会把行业带向哪里

能力分发复用 npm 生态

Pi package 经 npm 与 git 分发，意味着 coding agent 的能力市场不需要新建目录与评分体系，直接继承 JavaScript 世界最大的包基础设施（来源 01）。本文推断：当"装一个扩展"与"装一个 npm 包"的心智成本完全一致，团队私有扩展的内部共享会先于公开市场繁荣起来——前者才是这套分发机制的近期价值。

harness 即代码：agent 改写自己的运行环境

pi 让 agent 现场修改自己的配置与扩展、热加载继续工作（来源 01），把"定制 harness"从配置文件升格为日常对话。本文推断："个人 harness"（我的 pi 与你的 pi 长得不一样）与"产品 harness"（所有人的 Claude Code 长得一样）会加速分化，前者靠扩展生态繁荣，后者靠训练协同优化——两条路线的服务对象从一开始就不同。

极简路线正在多点开花

同期证据并非只有 pi：Codex 的工具定义同样极简（来源 03）；Terminal-Bench 团队自研的 Terminus 2 只给模型一个 tmux 会话照样上榜（来源 03、08）；DeepSeek 的开源 harness（约 22.5 万 star）在仓库定位里写明"一切皆插件"（来源 09）。本文推断：行业正收敛向"骨架最小、能力外挂、上下文显式"的共同形态——区别只在外挂的载体是扩展、插件还是技能文件。

公开会话成为研究资产

pi-mono 会话数据持续发布到 Hugging Face（来源 02），加上 pi 的会话树可导出、可分享，真实工作流的"任务—尝试—修正—完成"轨迹首次以 harness 官方身份成为公共语料。本文推断：这类真实任务轨迹对后训练与行为研究的价值将高于又一批新基准——最稀缺的从来不是评测题，是真实失败过程的完整记录。

09 / Takeaways

工程师可以借鉴什么

先给你的系统提示记账，再谈 agent 优化

pi 用不到 1000 token 的系统提示加四个工具，在作者的终端基准对照中不输重型 harness（来源 03）。本文推断：多数 harness 里庞大的"替模型操心"内容，优化的是提供者的安心感而非模型的表现。第一步永远是测量：把进入上下文的每一段内容列出来、标上 token 数，你会发现最大的几块往往没人为它们负责。

用渐进披露替代常驻工具描述

MCP 服务器的 21 个工具 13.7k token、26 个工具 18k token（来源 03）——开工前先烧掉 7–9% 的上下文窗口。带 README 的 CLI 工具让 agent 按需阅读、按需付 token，还天然保住前缀缓存。这个模式不要求你放弃 MCP：把"何时加载什么"从供应商的连接协议夺回到自己的上下文工程里，才是重点。

把状态放进文件，而不是模式里

计划写 PLAN.md、待办写 TODO.md：跨会话存活、可进版本库、人可编辑、agent 可读写、全程可观测。会话内建的临时"计划模式"与"待办面板"把状态锁进了黑盒——文件式状态的所有权在用户手里。这也是 pi 对子代理批评的延伸：看不见的状态就是失控的状态。

构建在原生 API 上，把中断与部分结果设计进去

Earendil 放弃 Vercel AI SDK 的教训（来源 03、04）：高层抽象在真实工具调用下破裂；显式管理缓存点优于自动管理。以及一条常被忽略的生产要求：请求要能全链路中断，中断后要拿得到已生成的部分结果——大多数统一 API 两者都做不到（来源 03）。

供应链纪律可以整包抄走

六条直接可迁移：依赖变更视为代码变更走审查、精确版本固定、lockfile 为唯一事实来源、min-release-age=2 防新包投毒、--ignore-scripts 安装、生命周期脚本白名单。这六条不依赖 pi 的任何代码——任何被 agent 执行命令的工具，都该对照自查一遍。

本文判断如果你正在为团队选型：要开箱即用与厂商协同，全功能派仍是稳妥解；如果你的差异化恰恰在上下文与工作流本身，pi 这类原语派把最大的自由度连同最大的责任一起给你——两者不是替代关系，是光谱两端。无论选哪端，"上下文账、安全账、治理账"三张账单都值得先算。
