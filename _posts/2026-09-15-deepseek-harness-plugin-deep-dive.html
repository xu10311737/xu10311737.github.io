01 / WHAT

它是什么：一个"没有内核"的 harness

先把名词钉死：DeepSeek Harness（命令名 dsh）是 DeepSeek AI 开源的 agent harness——与 Claude Code、Codex CLI、OpenCode 同类。它的仓库自述只有一句话的定位："DeepSeek Harness: Everything is a Plugin"。

Harness（马具/挽具）指围绕 LLM 的那层工程脚手架：工具循环、上下文管理、权限审批、会话持久化。四家 harness 的差异不在"能不能调工具"，而在这些能力的所有权归谁。dsh 的回答最极端：内核里几乎不剩任何不可替换的东西。官方架构文档的原话是——

»
"Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so each is replaceable from configuration. There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads."（产品每个部分都是插件——模型适配器、工具注册表、会话日志、乃至 agent 循环本身——每一个都能从配置替换。没有特权内核可打补丁：扩展 dsh 的方式是把插件挂到别的插件旁边，注册都是插件卸载时会反向解除的副作用。）

这段话三个信息量点，后面逐个展开：① 循环是插件——意味着"换掉整个大脑"是配置层面的操作；② 没有特权内核——官方插件和你的插件走同一条挂载路径，不存在只有官方代码能用的后门；③ 注册即副作用——所有注册（工具、prompt 片段、事件监听）都是可逆的，插件卸载时自动退回，这是热重载和崩溃清理的地基。

底层驱动这一切的是一个叫 Cordis 的插件框架（dsh 文档里称 vendored——以内嵌方式进了仓库），设计思想来自论文《A Programming Paradigm for Spatiotemporal Composability》（arXiv 2608.25512）。Cordis 同时独立发布在 npm 上（4.0.0-rc.10，MIT，周下载约 1.6 万），所以下面的 Demo 可以直接 npm i cordis 跑起来，不需要装整个 dsh。

先泼官方自己的冷水

仓库 README 用加粗标注：项目处于 developer preview，"未来将出现破坏兼容性的变更"；SAFETY.md 明说未经安全审计、不算生产就绪。本文讲的所有 API 形态以 2026-09-15 的 master 分支和 cordis 4.0.0-rc.10 为准——这也是为什么我坚持全部机制实机验证一遍再写。

02 / MECHANISM

"一切皆插件"的五个机械件

Cordis 官方 primer 把范式压缩成五条思想。每一条我都对应到 npm 包源码里验证过的 API 形态——下面这张表不是转述文档，是实跑过的。

件 1 · 插件 = Service 的实现者
插件就是一个对象
三种形态任选：函数（带可选 name/inject/provide 属性字段）、对象（{ name, inject, apply(ctx) }）、类（继承 Service，构造时 super(ctx, '服务名') 即自动注册服务）。dsh 的官方教程从最小插件到 greet 工具插件全是这条路径。
件 2 · ctx = 服务仓库
找服务靠 key，不靠 import
服务声明一个稳定键位（ctx.tools、ctx.llm、ctx.sessions、ctx.systemPrompt），别的插件按 key 取用而不是导入具体实现——依赖是数据不是代码引用。这就是"换模型 = 换一个插件"成立的原理。
件 3 · inject = 依赖声明
加载顺序不用人管
插件声明 inject: ['tools', 'systemPrompt']，框架等这些服务就绪后才挂载它——启动顺序是从需求推导出来的，不是写死的 boot 序列。实测：注册表插件先挂，消费者插件自动等 ctx.tools 出现才执行 apply。
件 4 · 类型化事件 = 通信总线
五种派发模式是契约
事件用 TypeScript declaration merging 声明，派发方式有五种（emit/parallel/serial/bail/waterfall），派发模式本身是事件的公开契约——新事件要打 @mode 标签，生成的目录会校验声明与调用点一致。见下表。
件 5 · 注册 = 可逆副作用
一切注册自带 disposer
工具 schema、prompt 片段、事件监听全部经 ctx.effect()/ctx.on() 注册（ctx.on 内部就是 fiber.effect——我在源码 index.js:344 验证过）。插件卸载时按注册的逆序退回。官方 cookbook 的说法是："every registration is a ctx.effect → vendored HMR just works"（每次注册都是 effect，热重载白拿）。

五种派发模式：事件不是"广播"，是五种不同的合同

这是理解 dsh 插件协作的钥匙——同一个事件系统，五种语义。监听者怎么写、能不能短路、有没有返回值，全由模式决定：

模式等待？顺序返回值dsh 里的真实用途（实例）
emit否按注册序观察无session/event 会话日志广播——所有观察者只看不动
waterfall否中间件链有tools/pre-execute 权限门、agent/pre-step 输入裁决、system-prompt/assemble——"要么加工后 next() 委托，要么短路"
parallel是（全并行）同时观察无互不依赖的旁路观察者
serial是（依次）按注册序有agent/turn-stopping 轮次收口（无 next，不能短路）
bail否到第一个 bail 为止有快速裁决类事件——有人给出答案就停
waterfall 的协作礼仪（primer 原则 + 实测补充）

监听者收到 (...args, next)。官方推荐"加工共享对象后 return next()"——合作型监听者改写同一个请求/决策对象再委托；决策型监听者可以不调 next() 直接短路返回。一个实测细节：npm 上的 cordis 4.0.0-rc.10 里 next() 不接收值参数，值传播靠 mutate 共享对象 + 调用侧终止闭包，比 dsh 文档里 vendored 版的"值经 next() 返回值传播"更朴素——写跨版本兼容代码时按 mutate 风格最稳。

03 / TURN FLOW

流程怎么转：一轮对话里插件协作的完整时序

dsh 的 turn（轮）= 一次用户输入驱动的完整循环；step（步）= 一次模型请求 + 它点名的工具执行。一轮可以有很多步。下面是官方架构文档的 turn flow，按"哪些环节哪些插件能插手"重排：

turn/start开轮用户输入进入队列，循环认领一条消息
↓
waterfallagent/pre-step —— 输入裁决门任何插件可改写或拒绝本条输入；被拒绝/改空 → 本轮无步直接收口（记忆注入类插件在这里排队上下文）
↓
assemblesystem-prompt/assemble —— 拼系统提示词所有插件注册的 section（静态/动态 provider）、工具 schema、变量参与组装；组装结果过一道协作 waterfall——此刻记忆插件渲染的记忆段、进化插件渲染的规则段全部生效
↓
logsystem/message + user/message 落日志运行时不变式："模型看得见的，日志里一定有"——提示词进历史而不是请求字段，改 prompt 只替换 0 号节点，前缀缓存照常命中
↓
llm/streamagent/request → 模型流式响应模型历史由日志推导（deriveMessages），请求是不可变快照；流式 chunk 经 agent/assistant-stream 转发给 UI 插件
↓
toolstools/pre-execute → execute → post-execute每个工具调用先过权限/校验 waterfall；未知工具返回结构化错误（UNKNOWN_TOOL）且不终止本轮——模型下一轮还能修正自己
↓
loopstep/end → 还有工具调用？→ 下一步 or 收口工具结果作为消息进日志，驱动下一个 step；没有工具调用则 serial 的 agent/turn-stopping 收口 → turn/end 落日志

注意两个设计后果：① 一切可观察——每个环节都有事件出口，UI 插件、遥测插件、记忆插件都是纯观察者，不需要改循环一行代码；② 一切可拦截——输入门、权限门、组装、收口全是 waterfall/serial 监听位。官方 cookbook 用一张"feature → mechanism map"把每个产品功能映射到具体扩展点（例如权限系统 = tools/pre-execute 返回 ask；压缩 = ctx.compaction seam；MCP = 每服务器一插件转注册进 ctx.tools），并称之为"让微内核主张可检验"——声称自己是微内核的框架很多，把每个功能列成可对账清单的是第一个。

插件从哪里长出来：profile → bundle → patch 三层叠装

插件在运行时怎么组织成"一个产品"？dsh 的答案是分层组合，启动时从空配置逐层叠加：

bundle
能力包
Cordis 配置行 + 它挂载的代码的发布单元。dsh-base 是共享底层（模型适配、工具、持久化、沙箱、审批、设置）；dsh-web-app 加浏览器应用；dsh-headless 加一次性运行器；dsh-sdk-app 加 JSON-RPC 服务。
profile
产品形态
命名组合（web / headless / sdk / sdk-minimal / acp 五个出厂模板），列自己叠哪些 bundle，持有用户的外挂插件和 cordis.patch.yml。dsh web 就是 --profile web 的别名。
patch
可对账的覆盖层
按行 id 定位，可整行替换、可插新行。应用顺序：bundle（按 profile 列出的顺序）→ profile 的 patch → home 级 patch → 命令行 --patch 叠加。dsh --profile web --dump-config 能打印整机插件树，任意一行你都能用 patch 换掉。

这个设计的锋利之处：定制一个产品 = 写一段 YAML，而不是 fork 一份代码。web profile 支持 patch 热重载（live reload）；一次性 profile 在启动时叠完即冻结。外部插件的安装入口是 dsh plugin --profile <name> <pnpm args>——本质上是把 pnpm 装进 profile 目录，让你的插件在下一层生效。

Demo：给 mini-harness 装上"长期记忆 + 自我进化"插件

目标：零 API key、单目录、npm i cordis 就能跑。做法是把 dsh 的内核插件逐个缩小复刻（接口形态与真实包一一对应），再把两个真正要研究的插件挂上去。所有代码在 cordis 4.0.0-rc.10 + Node 24 实测通过。

M
官方 cookbook 对 Memory 的标准答案是两个注册：一个 prompt section provider + 一个工具（"Memory: section provider + tool"）。本 Demo 忠实这个范式：记忆插件注册 section（让模型"想起"）+ 注册 memory_save/search 工具（让模型主动存取）；自我进化插件则复用同一套挂点——观察工具错误 → 反思生成规则 → 规则作为另一个 section 注入 → 下一轮模型行为改变。这是"CLAUDE.md 自我更新"模式的最小可运行版。

核心层里最值得看的是"注册即副作用"的落法——工具注册表的两行：

// ToolRegistry（对应 dsh-tools）：注册挂到"调用方插件"的 fiber 上，插件卸载时自动回滚
register(def) {
  return this.ctx.fiber.effect(() => {
    this.defsByName.set(def.name, def)
    return () => this.defsByName.delete(def.name)   // disposer：与插件同生共死
  })
}

以及组装系统提示词时，为什么插件们"自动出现在正确位置"：

// SystemPromptService（对应 dsh-system-prompt）
assemble(assembleCtx = {}) {
  const assembly = { sections: [] }
  for (const def of [...this.sectionMap.values()].sort((a, b) => a.order - b.order)) {
    const text = typeof def.text === 'function' ? def.text(assembleCtx) : def.text  // 动态 provider：每次组装实时求值
    if (text) assembly.sections.push(`## ${def.name}\n${text}`)      // 空贡献不占 prompt
  }
  return this.ctx.waterfall('system-prompt/assemble', assembly, () => assembly)
}                // ↑ 与真实 dsh 同名同模式：协作 waterfall，监听者可加工整份组装结果

第 1 步：长期记忆插件（三件事：听、注、给工具）

三个注册，一个回读，全部走官方 Memory 范式：

export const memoryPlugin = {
  name: 'long-term-memory',
  inject: ['sessions', 'systemPrompt', 'tools'],  // 声明依赖：三项就绪才挂载
  apply(ctx) {
    // ---- 0. 启动回读：保存 → 重启 → 回读 的闭环在这 ----
    let memories = existsSync(MEMORY_FILE) ? JSON.parse(readFileSync(MEMORY_FILE, 'utf8')) : []
    const persist = () => writeFileSync(MEMORY_FILE, JSON.stringify(memories, null, 2))

    // ---- 1. 听：观察会话事件流，出现"记住：X"自动提取（产品版换成 LLM 提取）
    ctx.on('session/event', (session, ev) => {
      if (ev.type === 'user/message' && /记住[:：]/.test(ev.data.content)) store.add(ev.data.content)
    })

    // ---- 2. 注：prompt section（动态 provider）—— 模型由此"想起" ----
    ctx.systemPrompt.section({
      name: 'long-term-memory', order: 50,
      text: () => store.all().length
        ? ['与用户长期协作中确认的事实：', ...store.all().map((m) => `- ${m.content}`)].join('\n')
        : '',                       // 空记忆不占 prompt
    })

    // ---- 3. 给工具：memory_save / memory_search，模型可主动存取 ----
    ctx.tools.register({ name: 'memory_save', description: '把一条用户偏好/事实存入长期记忆库。',
      parameters: { content: { type: 'string', required: true } },
      async execute({ content }) { store.add(content); return `已存入长期记忆：${content}` } })
    ctx.tools.register({ name: 'memory_search', /* 按关键词检索，略 */ })
  },
}

三个注册里有两个技术要点值得点破：① "听"的是日志事件流而不是对话对象——append-only 日志是唯一事实源，任何插件都从同一个 firehose 取数据，不需要互相认识；② "注"是动态 provider——不是启动时拼一次字符串，而是每次组装 prompt 时实时求值，记忆库更新下一轮立刻生效。两条路径汇聚同一个去重记忆库（自动提取与模型主动存都过同一个 store.add 的去重），这是产品版记忆系统必须处理的双写问题。

第 2 步：自我进化插件（观察错误 → 反思 → 规则注入）

export const evolvePlugin = {
  name: 'self-evolve',
  inject: ['sessions', 'systemPrompt'],
  apply(ctx) {
    let rules = readRulesFromDisk()                 // 进化跨重启持续
    const MAX_RULES = 12                            // 防膨胀上限：规则宁少勿多

    // 反思函数：Demo 用"错误类别 → 规则"启发式映射；产品版换成一次 LLM 反思调用
    const reflect = (errorText) => {
      if (errorText.includes('UNKNOWN_TOOL'))
        return '工具名必须与清单精确匹配：调用前逐字核对可用工具列表，绝不凭记忆拼写工具名。'
      return null                                    // 未知错误不硬造规则
    }

    // 观察：工具结果落日志 → 广播 → 这里反思 → 去重后追加规则并落盘
    ctx.on('session/event', (session, ev) => {
      if (ev.type !== 'tool/result' || !ev.data.result.isError) return
      const rule = reflect(ev.data.result.text)
      if (!rule || rules.includes(rule) || rules.length >= MAX_RULES) return
      rules.push(rule); persistRules(rules)        // 写 rules.md —— 与 CLAUDE.md 自我更新同构
    })

    // 注入：规则作为另一个 prompt section —— 进化的落点
    ctx.systemPrompt.section({
      name: 'evolved-rules', order: 60,
      text: () => rules.length
        ? ['AGENTS RULES（从历史错误中自我进化而来，必须遵守）：',
           ...rules.map((r) => `- RULE-EVOLVED: ${r}`)].join('\n') : '',
    })
  },
}
为什么这个闭环是"真的"而不是演的

Mock 模型不是打印预定的剧本——它的决策函数真的读组装后的 system prompt：prompt 里没有规则时它就凭记忆幻觉工具名（模拟真实模型的高频错误）；有 RULE-EVOLVED 规则时逐字核对。所以"规则注入 → 行为改变"这条因果链是由框架机制真实传导的，与接真模型时的传导路径完全相同——把 MockLlm 换成 DeepSeek adapter（同样一个插件位），闭环不变。

第 3 步：装配与运行

装配代码就是 dsh 精神的浓缩——内核与扩展一律 plugin()，没有特权代码路径：

async function boot() {
  const root = new Context()
  const fibers = {
    session: root.plugin(SessionLog),          // 日志
    prompt:  root.plugin(SystemPromptService), // prompt 组装
    tools:   root.plugin(ToolRegistry),         // 工具
    llm:     root.plugin(MockLlm),             // 模型适配器（换真模型 = 换这一个插件）
    loop:    root.plugin(agentLoop),          // agent 循环 —— 也只是插件
    memory:  root.plugin(memoryPlugin),        // 扩展 1：长期记忆
    evolve:  root.plugin(evolvePlugin),        // 扩展 2：自我进化
  }
  await Promise.all(Object.values(fibers))    // fiber 异步加载；inject 依赖自动排队
  return { root, fibers }
}

三个验证场景的实际运行输出（有删节）。细心的读者会注意到场景 A 里 [evolve] 的规则行打印在它所响应的错误之前——这不是剪辑错了：所有插件（包括负责打印的驱动脚本）都是 session/event 的监听者，事件落日志时按注册顺序同步触发，进化插件注册得比打印机早，于是它的日志行先于打印机的错误行出现。整个系统里没有任何组件"调用"任何其他组件，大家只是围在同一条事件流边上：

═══ 场景 A：模型幻觉工具名 → 工具门拒绝 → 进化插件生成规则 → 下轮修正 ═══
┌ 用户: 记住：我的部署环境是 k8s 生产集群，别用 docker-compose
  [memory] 存入记忆 #1: 我的部署环境是 k8s 生产集群…
  [evolve] ⚡ 从错误学到新规则 #1：工具名必须与清单精确匹配…
  │   tool/call    memory_sav                              ← 幻觉拼写
  │   tool/result  ❌ UNKNOWN_TOOL: memory_sav（可用工具: memory_save, memory_search）
  │   assistant: （我调用的工具不存在，这轮先记下来了……）

┌ 用户: 请保存这条偏好：构建一律用 pnpm
  [memory] 存入记忆 #2: 构建一律用 pnpm…
  │   tool/call    memory_save                             ← 规则生效：逐字核对
  │   tool/result  ✅ 已存入长期记忆：构建一律用 pnpm
  │   assistant: 好的，已存入长期记忆：构建一律用 pnpm。

═══ 场景 B：进程"重启"——记忆与规则从磁盘回读，行为在线 ═══
  [evolve] 回读 1 条历史规则
  [memory] 回读 2 条持久记忆

┌ 用户: 我的部署环境是什么？
  │   assistant: 根据长期记忆：我的部署环境是 k8s 生产集群，别用 docker-compose。
                                                ↑ 答案只能来自回读的 section，不是查上下文
═══ 场景 C：热卸载 memory 插件 —— 注册的 section 与工具全部自动消失 ═══
  卸载前：工具清单 = memory_save, memory_search
  卸载前：prompt sections = long-term-memory | evolved-rules
  卸载后：工具清单 = (空)
  卸载后：prompt sections = evolved-rules          ← evolve 未卸载，它的注册仍在（正确！）
┌ 用户: 我的部署环境是什么？
  │   assistant: 我没有任何关于你环境的记忆。       ← 卸载即回滚，没有残留状态

运行方式（全部代码五个文件约 400 行，package.json 只需一个依赖）：

npm init -y && npm pkg set type=module && npm i cordis
node run.js          # 三个场景一气跑完，无需任何 API key

顺带交一份实测踩坑账单（cordis 4.0.0-rc.10）

这些是文档没写、源码里翻出来的行为。写跨版本插件的人应该知道：

函数插件不要 return 值。apply 返回对象时，本插件 apply 期间注册的全部 effect 会被丢弃——症状是"注册没报错但什么都没生效"。实测把 return { store } 删掉立刻恢复。
ctx 是 Proxy，服务属性别用 "_" 前缀。下划线前缀撞了框架内部命名空间（fiber._store 等），经 ctx 访问服务方法时属性会被路由到别处——用普通名（this.defsByName）。
WeakMap 存服务状态会失效。经 ctx 调用方法时 this 是 traceable Proxy，与构造时的原实例不是同一个对象，WeakMap 的 key 对不上——状态放普通属性。
waterfall 的值传播靠 mutate。rc 版 next() 不接收值参数；监听者加工共享对象、调用侧用终止闭包取回。与 dsh 文档描述的 vendored 版语义有差异。
05 / TO REAL DSH

从 Demo 到真 dsh：同一套心智模型，换真实的挂点

Demo 里每个机制在真实 dsh 里都有名字。写真正插件时，按这张表对号入座：

你想要什么Demo 的做法真实 dsh 的挂点（官方文档）
注册模型可见工具ctx.tools.register(def)ctx.tools.register(defineTool({...}))——defineTool 给参数类型推断和输出 schema；schema 自动进 prompt 组装
注入系统提示词片段ctx.systemPrompt.section({name, order, text})同款 API，另有 context()（落为持久 user 快照）、tools() provider、variable()；order 有集中分配的命名槽位

权限/校验门tools/pre-execute waterfall同款事件，返回类型化决策（allow/deny/ask）；官方 cookbook 的权限门示例十几行

官方插件的最小形态（develop/basic 教程原文骨架），与 Demo 的 object form 完全同构：

import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'greet-tool'
export const inject = ['tools']          // 框架等 tool registry 就绪后才挂载

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'greet',
    description: 'Greet someone by name.',
    parameters: { name: { type: 'string', required: true } },
    output: { schema: { type: 'string' }, render: (_args, value) => [{ type: 'text', text: value }] },
    async execute(args) { return `Hello, ${args.name}!` },
  }))
}

也就是说：读完 Demo 的人去写真插件，需要补的只有 defineTool 的类型细节和打包配置，心智模型零迁移成本——这是"一切皆插件"最实际的好处：学一次挂载协议，扩展整个产品。

06 / VERDICT

冷静评价：这套架构强在哪、弱在哪，该学什么

先声明证据边界：dsh 处于 developer preview，官方 BENCHMARK.md 目前只给了运行说明、没有公开对照数据；下文的横向对比基于四家公开文档、此前两篇源码解剖（见文末关联），不引用无法核实的性能数字。

优点：四条真正的护城河

① 可逆副作用是热重载、崩溃清理、A/B 插件的共同地基
"每次注册都是 effect"意味着：插件可以运行中卸载再装回（demo 场景 C 验证过零残留）、崩溃恢复时能精确回滚半完成的注册、"试运行一个插件"不需要重启进程。其他三家的扩展点（hook/脚本/子进程）都没有这种结构性保证——它们靠约定和文档，dsh 靠类型系统。
② 事件语义是 API 契约，不是实现细节
五种 dispatch mode 是事件的公开合同，@mode 标签 + 生成目录自动校验"声明与调用点一致"。对比之下，多数框架的事件只是"调了就调了"——监听者该不该有返回值、能不能短路，全靠读源码。把派发语义提升到契约层，插件生态的协作才可预测。
③ "模型可见 = 已落日志"式的不变式设计
上下文工程最容易烂在"prompt 是哪次拼的、内容哪来的"上。dsh 把软约定升级为运行时硬规则（模型收到的一切必须可从日志重建，并有断言检查），这让审计、回放、压缩、fork 全部建立在同一地基上。Demo 里记忆/规则插件能"零协调"协作，正是因为大家都只跟日志流打交道。
④ 组合是声明式的，而且可对账
产品 = bundle 层 + profile 层 + patch 层的有序叠加，--dump-config 能打印整棵插件树。定制一个产品 = 一段 YAML 而不是一次 fork；官方和第三方插件走完全相同的挂载路径（无特权内核），微内核主张用 feature→mechanism map 变成可审计的清单而非营销话术。

缺点：四条真实代价

① API 在流沙上
官方预告破坏性变更；底层 cordis 是 4.0.0-rc（npm 自述"API 尚不稳定"）。本文实测就撞到 vendored 版与 npm 版的行为差异（waterfall 值传播）。在 preview 阶段为它写生产插件，等于接受随时重写。
② Proxy 魔法有税
ctx 是运行时代理："_" 前缀撞内部命名空间、this 身份漂移让 WeakMap 失效、函数插件返回值吞掉注册——三个坑 TypeScript 编译期全拦不住。框架的灵活性是拿"遇到诡异 bug 时要读框架源码"换的。
③ 一切皆插件的抽象税
加一个小功能也要懂插件契约、事件模式、fiber 生命周期。Claude Code 的 hook 是"抄一段 JSON 就能用"的插槽，dsh 的插件是"先学一个范式"。对偶尔写个 hook 的用户，门槛差一个数量级——这是微内核与有限插槽的经典取舍。
④ 生态在零点附近
225k stars 的关注度 ≠ 可用插件的规模；dsh-plugin topic 刚起步，官方配置目录里现成的只有 review webhook、schedule、memory MCP 等寥寥几类。对比 Claude Code 已成事实标准的 skills/hooks 格式——生态位差距比代码质量差距大得多。

一句话读法

四家在"扩展面所有权"上给出四个答案：Claude Code 把扩展收窄成产品插槽（最稳、生态最强、但换不了循环）；Codex 把扩展压成配置与策略（编译期纪律最强）；OpenCode 把扩展留给插件与协议但不管编排（最轻）；DSH 把扩展做成唯一的存在方式（最彻底、最可组合、也最年轻）。这不是排名，是四组不同的取舍——你的场景里"要不要换循环"出现得越频繁，DSH 的架构越值钱；你越需要"明天就能用、别坏"，它今天越不合适。

我们该学什么（可照抄的七条）

注册必须自带 disposer。任何框架/平台的扩展点设计，注册函数的返回值都应该是"如何撤销我"。这一条同时买到热重载、崩溃清理和沙箱化试运行——demo 场景 C 的零残留就是它的直接收益。
把派发语义写进 API 合同。观察、拦截、并行、串行裁决、快速短路是五种不同的需求——用类型化事件 + 模式标签让监听者"知道自己被承诺了什么"，并让 CI 校验声明与调用点一致。
把软约定升级为运行时不变式。"模型可见 = 已落日志"值得每个 agent 框架抄：凡是给模型的输入，都必须可从持久事实重建。审计、回放、压缩、fork 从此共享一个地基，上下文工程不再是玄学。
依赖声明替代启动顺序。inject 数组让"谁先谁后"从 boot 脚本退化成声明式约束——小型系统无所谓，插件一多这是维护性的分水岭。
组合产物可打印、可对账。--dump-config / feature→mechanism map 两招本质相同：让"我的系统现在由什么组成"永远可回答。微内核不是宣称出来的，是对账清单撑起来的。
互操作靠采纳，不靠发明协议。DSH 把竞品后端、竞品 hooks、竞品指令文件全部直接认下来——历史上赢的从来不是新协议，是兼容面最宽的那个实现。
诚实是架构的一部分。developer preview 加粗警告、SAFETY.md 自曝未审计、BENCHMARK.md 不放没跑过的数字——在一个大家习惯宣传"遥遥领先"的品类里，可验证的克制本身就是竞争力。
关于"自我进化"的最后一盆冷水

Demo 的反思函数是十五行启发式——真实产品的自我进化要面对三道额外的门：① 反思质量（错误 → 规则的映射换成 LLM 后，错误规则比没有规则更糟）；② 规则治理（去重、上限、过期、冲突检测——规则库膨胀的 agent 会比没有记忆的 agent 更快失控）；③ 安全边界（让模型写"自己下次要遵守的规则"等于间接 prompt 注入的入口，生产系统必须有审批层，就像 Codex 用沙箱 subagent 审阅记忆写入）。闭环跑通是第一天，治理才是余生。
