Jev：放弃生成文本、专做结构化决策的模型，把 AI 判断做成 70 毫秒级的"智能 if 语句"

前 OpenAI 研究员 Diogo Almeida 创办的 TypeSafe AI 在两年隐身研发后，于 2026 年 9 月 16 日发布了新模型类别 System One Models 与首个公开模型 Jev。它不生成任何文字：输入一段非结构化状态（比如一张工单、一段对话、一份策略），输出一组类型安全的决策值——每个答案自带概率分布与置信度分数，端到端延迟 70–500 毫秒，每百万 token（模型处理文本的最小单位，约合四分之三个英文单词）输入 0.042 美元、输出免费。

官方 workflow 评测（把任务拆成多个小问题、由代码组合答案）显示：Jev 四项任务平均 67.8% 准确率、每案例 0.0004 美元、0.4 秒——与 Claude Sonnet 5 同模式持平的准确率。发布 24 小时内在技术社区 Hacker News 攒到 1699 分、459 条评论，争论焦点集中在"不能幻觉"的表述边界与评测公信力；同日开源社区用约 40 亿参数的开源模型加 logits（模型对每个候选输出给出的原始分数）复刻出同类原型。

先给结论Jev 押注的判断是：LLM（Large Language Model，大语言模型）在聊天上早已超人，但自动化没有兑现——因为把"生成一段文字"塞进代码要交三笔税：自回归（一个词一个词往下写的逐字生成）慢、输出要解析验证、置信度不可靠。System One Models 用"放弃生成字符串"一次性免掉三笔税，把 AI 判断做成代码可以直接消费的智能 if 语句。对 AI 工程师，真正值得带走的不只是这个模型，而是三件事：把概率输出做成接口一等公民、用问题分解替代长提示词、用"会说不知道"的置信度设计分级放行。同时要清醒：类型安全不等于事实正确，官方评测是厂商自建，生态接入工具几乎为零。

01 / Decision brief

TL;DR（太长不看）：一个为"if 语句"重新发明的模型

01 / WHAT

发生了什么

TypeSafe AI 于 2026-09-16 发布 System One Models（取自心理学家卡尼曼"快与慢"里的 System 1 直觉思维）及首个模型 Jev（取自经济学家杰文斯，借"成本每降一个数量级、用例数量级增长"之意）。Jev 不输出文字，只输出类型安全的决策：Choice（从固定选项中选）、Score（沿定义等级打分）、Noul（"是否为真"的概率），全部附带校准（报 90% 把握就应在约 90% 的情况下命中）概率与置信度。早期访问已开放。

02 / WHY

解决谁的问题

要把 AI 判断嵌进业务代码的工程师。LLM 做分类、路由、评分要 3–329 秒、输出还要解析校验、置信度自报不可信；Jev 用 70–500 毫秒、免解析、训练目标就是校准概率，换掉这三笔"集成税"，让 AI 判断可以放进对延迟敏感的同步路径（实时风控、客服分派、Agent（能自主调用工具、多步完成任务的 AI 程序）步间审查）。

03 / HOW

核心机制

一次请求 = 一段状态 + 一批问题。三种原语并行输出全部概率（非逐 token 生成）；新训练方法 RLCD（校准决策强化学习）把"概率对得上真实结果"作为优化目标，区别于奖励人类偏好的 RLHF 与奖励答案正确的 RLVR；置信度由概率分布形状派生，代码按阈值分级放行。单请求预算约 3.2 万 token，多问问题几乎不增加延迟与成本。

04 / SHIP

生产判断

官方评测里 Jev 平均 67.8% / $0.0004 / 0.4s，追平 Sonnet 5 但远逊 opus 5（73.1%）与 sol（74.1%）的准确率上限；发票处理一项仅 61.8%（opus 5 为 78.4%）。评测为厂商自建、参考答案是 GPT-6 Astra 与 Claude Fable 5.1 的平均（官方自认偏向 OpenAI/Anthropic）；OpenRouter（第三方模型 API 聚合网关）、vLLM、Ollama 生态均无接入（来源 06）。替换现有流程前，必须用自己的数据复测校准性。

来源事实发布信息、三种原语、RLCD 描述、定价与延迟、workflow 评测数据均来自 TypeSafe 官方博客、文档与评测站（数据截至 2026-09-17）；争议与社区反应来自 Hacker News 讨论帖（1699 分/459 评论，数据截至 2026-09-17）与 Reddit r/LocalLLaMA 讨论帖。本文推断"专用决策模型会成为一个独立类别"与"护城河在校准质量而非架构"为本文判断；判断依据在各章节内标注。
02 / Background

背景与问题：聊天超人四年，自动化迟迟不来

System One Models 的出发点是一句反问："模型在聊天上超人已经很多年了，那么自动化在哪里？"提问者 Diogo Almeida 曾在 OpenAI 参与让语言模型学会听从指令、与人对话的方法研究——这些研究后来成了 ChatGPT 的底子。他当年的判断是聊天模型通向通用智能，而两年隐身研发后交出的答案相反：要自动化，先得有一种软件能直接依赖的模型。

ALLM 进代码的三笔税

把 LLM 的判断接进业务代码，工程师一直在替"生成式"付代价。速度税：LLM 是自回归（autoregressive）生成——一个 token（模型处理文本的最小单位，约四分之三个英文单词）接一个 token 往下写，前沿模型端到端 3–329 秒（来源 01 引用的公开基准）。人可以等，嵌在代码里的判断等不起。可靠税：输出是自由字符串，用之前要解析、要校验；再聪明的模型也会输出 schema（预先定义的数据结构）之外的值——工具调用幻觉是 Agent（能自主调用工具、多步完成任务的 AI 程序）的常见故障，而在有延迟承诺、多层依赖链的系统里是致命的。置信税：让 LLM 自报"我有几成把握"，它倾向于过度自信且前后不一致；一个 95% 时间正确的模型，若说不清自己什么时候在错的那 5%，这 5% 就足以让整个任务无法自动化。

B市场的空白地带

现有解法各占一角：约束解码（constrained decoding，限制模型只能输出符合语法规则的内容）解决格式、不解决速度与校准；小模型分类器便宜快、但覆盖面窄；给 LLM 接上 logits 读数（模型最后一层输出的原始概率分数）需要供应商开放且概率本身未经校准训练。厂商结构化输出接口（OpenAI、Anthropic 的工具调用）仍是"生成后修剪"。市场缺的是：把"决策"当作原生输出形态从头训练的模型——这正是 TypeSafe 选的命名，System One：不与 System 2（慢速推理）抢活，专做卡尼曼意义上的"一秒钟直觉判断"。

命名即战略：Jev 取自威廉·斯坦利·杰文斯（William Stanley Jevons）——蒸汽机效率提升后，煤的消耗不降反增（杰文斯悖论）。TypeSafe 把它读成 AI 版：智能的成本每下降一个数量级，解锁的是数量级增长的用例。70–500 毫秒、$0.0004 一单的判断，会出现在 3 秒、$0.1 一单的判断永远进不去的地方。（来源事实：命名出处与定价来自官方博客；将杰文斯悖论读成 AI 成本曲线为官方声明。）

03 / Mechanism

核心原理：一次请求，状态进、类型化决策出

Jev 的接口只有一个动作：把一段"状态"（state，通常是 JSON 文档：工单、对话记录、策略文本）和一组"问题"（questions）发过去，拿回每个问题对应的类型化答案。没有对话历史、没有思维链、没有生成——所有概率在单次查询里并行给出。

01 / STATE组装状态把要判断的原文料装进 JSON：工单正文、订单记录、退款策略，字段名即语义边界；代码用点路径引用具体字段。
02 / QUESTIONS定义问题每个问题一个判断：Noul（是否为真）、Choice（选哪个选项）、Score（落在哪一级）。单维度、可在代码里加权组合。
03 / PARALLEL并行出概率所有问题的答案概率一次算完，不是逐 token 生成——加问问题几乎不增时延，成本只按问题 token 计。
04 / CONFIDENCE派生置信度probabilities（各选项概率分布）由模型给出，confidence（0–1 的置信分）由分布形状算出：越集中于一个选项越自信，摊平即不确定。
05 / COMPOSE代码做决策阈值放行、if 分支、加权合成、转人工——组合逻辑全在代码里，改权重不改提示词。
70–500 毫秒端到端延迟（来源 01）。对比前沿 LLM 的 3–329 秒，官方博客称 System One 形态的查询在同等智能水平下快 40–200 倍（原帖标题曾用"快 20–200 倍"的宣传口径，见争议 02）。
$0.042 / 百万输入 token输入定价；输出免费（"便宜到不计量"）。对比 LLM 输入 $0.2–10/百万 token、输出约为输入 5 倍（来源 01）。
约 32,000 token / 请求状态与问题共享的单请求预算，约合 15 万英文字符（来源 02）。问题数量只受预算限制。

三种原语：把"判断"定型成三种可执行形状

文档把问题类型收敛为三种，每种返回结构固定的答案（来源 02）：Noul 回答"是否为真"，返回 0 到 1 的概率（Noul 值 0.5 表示模型对正反各给一半概率，而非"中等程度"——要测程度用 Score）；Choice 回答"是哪一个"，返回选定项、全选项概率分布与置信度；Score 回答"在哪个级别"，沿你自己定义的有序等级（如"冷静/着急/愤怒"）返回位置、分布与置信度。博客称 Choice 支持最高 255 个选项的高基数选择，高基数时用"先评分再显式选择"的两段式。

RLCD：把校准从技巧变成训练目标

现有 LLM 的训练范式：RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）奖励"人类更喜欢的说法"；RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）奖励"答案正确"。两者的概率输出都不为校准负责——RLVR 的奖励作用于整条推理路径，并不训练模型输出"这题我八成把握"。TypeSafe 的 RLCD（Reinforcement Learning for Calibrated Decisions，校准决策强化学习）官方描述是："为校准的决策而训练：概率对照真实结果优化，以反映不确定性。"通俗说：模型报 0.9 置信时，应当在约 90% 的情况下真的对——校准（calibration，报出的概率与实际命中率的吻合程度）本身进了损失函数。官方未公开架构与训练细节，社区对"并行采样如何实现"存在 diffusion（扩散式生成，一次并行出全部输出而非逐个生成）类猜测（来源 05），截至发稿未见官方证实。

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient state = {"ticket_message": "My flight was cancelled. Can I get a refund?", "refund_policy": "Cancelled flights are eligible for a full refund."} with TypeSafeClient() as client: response = client.system_one( state=state, questions={ "refund_requested": Noul(instructions="Does `ticket_message` request a refund?"), "request_type": Choice(instructions="What is the main request?", criteria={"refund": "money returned", "rebooking": "replacement flight", "information": "asking only"}), "frustration": Score(instructions="How frustrated does the customer appear?", criteria=["Calm and neutral.", "Concerned but civil.", "Very angry or using strong language."]), }) # 一次请求，三个问题并行，每个答案自带概率分布；问题ID不进模型，仅用于代码取值 # （示例节选自官方文档，来源 02）

投机式扇出（speculative fan-out）：官方鼓励把"可能需要"的问题一次全问——反正每个问题只按 token 计价、并行评估、几乎不增加延迟，答案用不用由代码决定。官方 cookbook（示例代码集）数据：13 个问题合并为一次调用，比 13 次单独调用便宜 11.5 倍、快 9.6 倍，答案不变（来源 02）。这与传统"少问省 token"的 prompt（提示词）直觉完全相反。

竞品对比：五条已有路线都能逼近，但没有一条全部占住

LLM + 约束解码

（GLiNER 一类零样本分类器）		编码器对"文本-标签"对直接打分输出概率快且便宜，类 Jev面向实体/标签任务设计，非通用决策Reddit 讨论将其列为"现成等价物"，但任务形态（自由问题定义、等级评分、255 选项）覆盖窄，工程接口不成体系（来源 05）
小 LLM 做分类路由
（deepseek v4 flash、haiku 4.5 等）		提示词要求输出类别，或配合约束解码中等：秒级；官方评测中 DS v4 flash 客服任务 76.8% 准确率反而高于 Jev 的 76.0%（来源 03）无原生置信度；分类任务"非前沿模型加一点手艺也已极好"（HN 讨论观点）已很强的存量方案：Jev 的增量在延迟（0.4s vs 34.6s）与成本（约 30 倍差距），不在准确率
开源复刻
（openjev 等）		Qwen 4B（约 40 亿参数）级开源模型 + logits 输出层，发布 24 小时内出现，含浏览器可玩 demo宣称复刻 Jev 交互形态无 RLCD 训练，校准性未经验证证明接口形态容易被复制；本文据此推断 Jev 的护城河更可能在校准质量与产品化，而非架构本身（来源 05）

差异点的精确表述：把五条路线摆在一起可以看出，"结构化输出"不新（约束解码）、"读概率"不新（logits）、"快分类"不新（编码器/小模型）。Jev 的差异点是把三者同时做成默认形态：格式由构造保证、概率由训练校准、延迟由并行采样压进亚秒——并配齐了 SDK（软件开发工具包）、confidence 语义、请求预算这些生产接口。单点皆可替代，组合体目前没有第二个供应商。（前半句为来源事实归纳，最后一句为本文推断：以 OpenRouter 无上架、vLLM/Ollama 无支持为证。）

06 / Engineering

工程化视角：从 Demo 到生产，隔着六件事

Jev 的接口设计已经明显带着生产味（阈值、置信度语义、请求预算），但把它接进真实系统，以下环节一个都绕不开。

接入生产系统要考虑的环节

问题设计是新的提示词工程，而且责任更重

官方文档要求每个问题保持单维度："描述里说'准时、聪明、有经验'就是三个维度混进一个 Score，输入高一个低一个就放不下，置信度会掉、分数失去意义"（来源 02）。判定边界从模型侧移到了问题侧——问题写歪，校准概率会诚实地给你一个低置信，而不是替你猜对。这比提示词工程的试错成本更高：每个问题都是一份要长期维护的 schema。

置信度分级放行：官方给了可直接照抄的三段式

高置信自动执行；中置信走确认（问用户、标记审核、补信息）；低置信不动作，转人工或换系统。地板值官方示例取 0.5，高风险动作（如"批准转账"）再叠加 >0.9 才免确认的二级阈值——读操作低门槛、写操作高门槛，风险容忍度写进代码而非写进提示词（来源 02）。

校准漂移监控必须自建

校准是 Jev 的核心承诺，但官方文档只说"先用保守阈值、用自己的数据测"（来源 02）。ECE（Expected Calibration Error，期望校准误差，衡量报出概率与实际命中率偏差的指标）监控、分布漂移告警、问题版本化——这些 MLOps（机器学习运维）基本功一样都不能少。供应商给了类型错误的数学保证，没给校准的运维保证。

供应商与定价锁定风险

早期访问、闭源、单一供应商、输出免费的反常定价——官方 FAQ 直言"无法证明定价没有补贴，需要长期来证明可持续性，我们预期它会降而不是涨"（来源 01）。接入即押注这家公司活得比你的业务久；问题 schema 又全在它家格式上，迁移成本随问题库增长。

对现有 LLM 应用架构的影响

最直接的影响是分层：LLM 继续干"生成"（写作、代码、总结、对话），决策模型接走"判断"（分类、路由、评分、守门）。HN 讨论中最被看好的落位是给 coding agent 当"监督层"：agent 每步执行后跑一批问题——"任务完成了吗？""改动是否碰了不该碰的文件？""是否遵循代码规范？"——用亚秒级判断给长跑 agent 加护栏（来源 04，属讨论中的使用构想）。官方文档同样点名"coding agent 容易一次只问一个问题"，并发布了配套 agent skill（教 agent 一次批量提问的能力包）纠正这个习惯（来源 02）。

第二个影响藏在官方评测里、却容易被忽略：workflow 模式对 LLM 也成立。评测里每个模型都跑两种模式——把任务拆成多问题+代码组合（workflow），或一整段 prompt 直答（prompt）。四项任务全部模型、无一例外，workflow 模式更准、更便宜、更快：opus 5 从 64.8% 提到 73.1%，haiku 4.5 从 18.1% 提到 53.6%（来源 03）。这意味着"问题分解+代码组合"本身是一条独立于 Jev 的可迁移方法论——今天就可以用在你现有 LLM 的路由/分类逻辑上。

从 Demo 到生产可用，主要差距在哪里

差距一：评测公信力。四项 workflow 的参考答案是 GPT-6 Astra 与 Claude Fable 5.1 两个最强模型的平均，官方自认"偏向 OpenAI 与 Anthropic 的模型、可能低估自家与 DeepSeek"（来源 01、03）；且方法假设"工作流代码本身正确"——真实系统里工作流是要维护、要测试的活代码。差距二：能力边界未标定。四项任务里 Jev 在发票处理仅 61.8%（opus 5 为 78.4%），在 Agent 轨迹审查 71.6%（低于 luna 的 76.1% 与 sol 的 76.6%，luna 与 sol 为评测站列出的对比模型）——"接近前沿智能"在部分任务上并不成立，选型必须逐任务实测。差距三：生态为零。OpenRouter 未上架（来源 06）、vLLM 与 Ollama 无对应接口、无第三方基准，社区在 Reddit 明确呼吁 vLLM 支持这类推理接口（来源 05）。可观测、灰度、回滚、本地化部署，全部自己搭。

来源事实三段式阈值与示例、agent skill、32K 预算、评测数字与自评偏向声明均来自官方文档与评测站（来源 02、03）。本文推断"分层架构"与"监督层"落位综合自 HN/Reddit 讨论倾向；ECE 监控自建的必要性为本文工程判断。
07 / Critique

局限与风险：发布 24 小时内被争透了的六件事

HN 帖子 459 条评论几乎把这项发布拆解了一遍，官方联合创始人也在场逐条回应（来源 04）。以下六点是争论的实质内容，判断留给读者。

争议 01 · 强度：高

"不能幻觉"是个被压缩的定义

官方语境：不会输出 schema 之外的值——类型错误数学上不可能。批评语境：自信地给出类型正确但事实错误的值，同样是幻觉；把图片上的橙子标成"苹果：置信 99%"，照样是错。官方在 HN 承认"类型安全不等于事实正确"，也主张"随机森林不像 LLM 那样幻觉"——但博客宣传图用 0% 幻觉对比 LLM 的实测数字，这个视觉修辞已经越过了它自己承认的边界。

争议 02 · 强度：高

标题在发布一小时内被修改过

原帖标题"Jev: New frontier model 40-400x cheaper and 20-200x faster"（倍数为发布方宣传口径，与官方博客"快 40–200 倍"的表述不完全一致）被指出误导后改为现标题。"frontier model"（前沿模型）的称谓被质疑：它放弃了字符串生成，就不能再按通用模型的尺子量；20–200 倍的速度对比，也让位于"结构化决策这一子任务上的帕累托前沿（多目标权衡下不存在'更快更好还更便宜'替代方案的最优边界）"这个准确得多的表述。

争议 03 · 强度：高

对比基准不对等

HN 讨论：LLM 参与对比时用自回归把类型名、schema 文本一个个字生成出来，Jev 则直接输出数字——更公平的对比是让 LLM 也只输出原始数值。官方回应称这是让 LLM 以"最准确的决策模式"参赛，但也承认该模式比 LLM 平常用法更慢更贵。

争议 04 · 强度：中

模型规模与能力上限成谜

官方未公布参数量与架构。HN 有评论按"无长上下文、Choice 选项有限"推测其规模不大；官方博客强调 Jev "不是小 LLM"，但未给出可验证的证据。官方口径之外，重新审视的空间完全存在：Jev 在发票任务上 16.6 个百分点的准确率差距（61.8% vs opus 78.4%，来源 03）说明复杂状态理解仍有硬上限。

争议 05

单题校准 ≠ 组合校准

每个答案的概率是校准的，但把十几个答案的置信度组合成一次业务决策时，组合体是否仍然校准，官方没有给方法。HN 评论指出：一个未授权操作完全可能在其他维度上得分很高——"单个答案校准，不等于组合它的那个决策校准"。组合层的校准验证工作，最终仍落在使用者头上。

争议 06

Demo 的输入不是你以为的输入

Doom 实时游玩 demo 喂给模型的不是游戏画面，而是游戏状态的结构化文本描述（官方在博客中自注）；Wikiracing 对比的是各模型的非推理模式。两个 demo 都合法，但都应按"结构化状态输入下的判断速度"来理解，而非"模型看画面打游戏"。

诚实边界声明：本文对 Jev 的全部能力描述均来自官方博客、文档、评测站与公开社区讨论（来源 01–05），未包含作者实测数据。官方声称中可独立证伪的（速度、定价、类型安全）与不可独立证伪的（智能水平、校准质量）已在上文区分标注；引用的评测均为厂商自建，采信前应以自有数据复测。

08 / Outlook

未来方向：决策模型会不会成为下一个品类

以下为本文推断，依据来源事实在各条内标注。

A品类分化已成趋势

模型市场正在从"一个 LLM 干所有事"走向按任务形态分化：对话模型、推理模型、决策模型各占一档。Jev 发布 24 小时内 HN 1699 分/459 评论、Reddit 当日复刻讨论帖（来源 04、05）——一个新品类的关注度门槛已经跨过。按杰文斯逻辑（官方声明），亚秒级、微美元级判断解锁的用例规模，可能反过来推动"决策模型"成为独立采购项。

B生态与标准的三个观察点

一，推理栈支持：vLLM/Ollama 尚无此类接口，Reddit 已出现明确呼声（来源 05）——若 vLLM 落地"概率输出"接口，开源复刻潮会真正开始；二，聚合渠道：OpenRouter 未上架 TypeSafe（来源 06 数据），说明其仍处于早期访问阶段，规模化信号未到；三，大厂跟进：现有结构化输出接口（约束解码路线）离"校准概率"只差一步训练目标——RLCD 思路被证明后，主流 API 把概率做成一等公民的门槛不高。

更远一层的想象（本文推断，无来源佐证，置信度自评：中低）：Agent 架构可能长出"双系统"形态——System 2 的 LLM 负责慢速规划与生成，System 1 的决策模型负责每步之间的快判断（审查、守门、路由）。这类零件的需求正在两个方向同时增长：Agent 要长跑数小时，每一步都需要有人守着；Agent 越自主，对其行为的审查要求就越高。两个方向最终指向同一种能力——亚秒级、可校准、可组合的判断。

09 / Takeaways

工程师可以借鉴：不换模型也能带走的五件事

以下五条为本文从这则发布中归纳的可迁移经验，与是否选用 Jev 无关；引文与数据来源随条标注。

把概率输出当接口一等公民来设计

logits 被主流 API 藏起来是产品决策——社区归因于防蒸馏（防止他人用你的模型输出去训练小模型，来源 05）——而非技术必然。内部模型服务完全可以把"每个输出带概率分布"做成默认：下游拿到的不是一次赌注，而是一个可设阈值、可分级的信号面。

问题分解优于长提示词，且对所有模型成立

官方评测里所有模型 workflow 模式都比单 prompt 更准更便宜更快（opus 5：64.8%→73.1%）。把"一段策略长文"拆成带类型的问题+代码规则，是今天就能在现有 LLM 上复用的方法论（来源 03）。

三段式置信放行可以直接抄

低置信不动作、中置信走确认、高置信自动执行；地板 0.5，写操作再叠 >0.9。这套阈值结构（来源 02）适用于任何能输出概率的模型，风险容忍度显式进代码。

给系统装一个"会说不知道"的部件

官方文档的立场值得裱起来："一个智能系统——无论人还是机器——若不能表达诚实的不确定，就不值得信任"（来源 02）。自建判断类功能时，先问一句：它敢在什么时候说"我不知道"？说不知道的路径不存在，校准就无从谈起。

把厂商的"can't"还原成精确定义再做决策

"不能幻觉"实为"不能输出 schema 外的值"；"前沿智能"实为"结构化决策子任务上的性价比前沿"。采购任何 AI 能力时，把宣传语逐条还原成可证伪命题——这一条审查习惯，比任何单一选型结论都值钱。
