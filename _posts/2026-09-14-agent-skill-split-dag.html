AGENT 架构 · 拆分决策

Agent/Skill 到底应该怎么拆：一套可量化的 DAG 判断流程

不谈"agent 负责判断、skill 负责执行"这种无法证伪的分工话术。本文把拆分问题还原成一个可测量的资源分配问题：上下文（token）是唯一的一等公民——拆分边界 = 上下文容器的边界，一切"感觉"都必须翻译成六个可测量的数字，数字不支持的拆分就是错的拆分。

六指标：S · C · R · U · L · F 六站 DAG 判断流程 边界裁决表 两个带数字的完整算例 局限性全声明
没有标准
行业现状：各家按直觉拆——Cognition 反对多 agent，Anthropic 自己却在生产中跑多 agent，两边都对，但都没给出什么时候用哪边的可操作判据。
Cognition《Don't Build Multi-Agents》/ Anthropic 工程博客
15×
多 agent 系统的 token 消耗约是普通对话的 15 倍（单 agent 是 4 倍）——注意：这是 Anthropic 拆得正确的多 agent 系统的固有运行成本。它的含义不是"拆散的账单"，而是：每新增一个容器边界，都必须有足够任务价值为其买单。

§0 · TL;DR

先给结论：三个问题，三个唯一判据

整个框架回答的就是开头那三个问题。每问只有一个判据，其他一切理由（职责清晰、模块整洁、复用好看）如果不能翻译成这三个判据之一，就不足以构成拆分或合并的依据。

复杂需求
需要几个 agent？
数上下文容器，不数职责。每个 agent = 一条独立、隔离、有生命期的对话轨迹（history）。有几个容器由三个量决定：隐式状态耦合 S（两个单元之间无法序列化传递的工作状态越多，越必须同容器）、容量压力 C（单元群需要的 token 超过有效工作窗口，必须切容器）、失败重放半径 F（切分后单元失败会不会拖累全容器重跑，决定这条边切了值不值）。三者构成三输入与门：S ≤ 30% 打开边界，C > 70% 才强制通过，F 超标一票否决。
哪些东西是 skill、
该拆几个？
skill 是载荷，不是流程。判断某段知识/流程要不要做成独立 skill，只看两个量：复用度 U（被几个不同父流程引用，U=1 一律内联不建 skill）和加载共现率 L（两个候选载荷是否几乎总被同时触发：共现 > 80% 合并成一个，< 20% 且各自高频触发才值得拆开）。skill 的本体是"分层的、按需加载的上下文"，所以拆分准则只有一句话：按触发场景拆，不按主题拆。
为什么不能合并？
为什么不能再拆？
因为合并和拆分的收益都能被定价。合并的唯一收益 = 省掉容器间的往返开销 R（一次委派的任务描述 + 上下文重建 + 结果回传，占被委派单元自身 token 的比例）；拆分的唯一收益 = 缓解容量压力 C、获得复用收益 U、缩小失败重放半径 F。任何"为什么不能合并/为什么不能再拆"的争论，最后都收敛为这四个数的比较——这就是准则的全部。
§1 · 调研

行业现有主张：四家四种拆法，但没有一家给出可操作的准则

把四份一手材料（Anthropic 三篇工程文章 + Cognition 的反多 agent 文章）的拆分相关主张全部摊开对比，可以看到行业共识确实存在，但全部停在定性层。

来源核心主张给出的拆分信号对拆分判断而言的缺陷
Anthropic《Building Effective Agents》 从最简单方案开始，只有"可证明的收益"才加复杂度 步骤可预先枚举 → 用 workflow（prompt chaining）；步骤不可预定义、需模型自主决定 → 才用 agent 回答了"要不要 agentic"，没回答"一个系统里几个 agent、skill 怎么切"
Anthropic《How we built our multi-agent research system》 多 agent 在内部研究评测上比单 agent 提升 90.2%；但 token 15× 三个适用信号：任务价值高到付得起 15×；子任务可真并行；信息量超出单上下文窗口 有实测数字，但只覆盖研究检索类任务，且没给阈值——"超出单窗口"超多少、怎么算，没说
Cognition《Don't Build Multi-Agents》 上下文是核心资源；默认单线程单 agent 两条原则：共享完整 trace 而非单条消息；行动携带隐式决策，冲突的隐式决策必然互相破坏 原则正确且深刻，但是"原则化"的——"隐式决策"如何识别、多少算多、何时值得为并行性违反原则，均无可测量的回答
Anthropic《Equipping agents for the real world with Agent Skills》 skill = 文件夹（SKILL.md + 脚本 + 资源），三级渐进披露 skill 拆分信号：单文档过大 → 拆附属文件；内容互斥/很少一起用 → 分开存放 最接近可操作（渐进披露 = 按需加载），但只讲文档层切分，不涉及 agent 边界，也没量化"多大算大"
调研结论：共识存在，判据缺失
四家材料拼起来其实已经逼近真相：上下文是唯一稀缺资源（Cognition 的"隐式决策"、Anthropic 的"上下文窗口溢出"、Skills 的"渐进披露"，全都是上下文经济学的不同侧面）。缺的只是把它们统一成一套任何人拿到都能执行的测量流程——这正是本文接下来要做的事：把四家的定性主张翻译成六个可测量的指标和一张 DAG。
§2 · 痛点定量化

为什么拆分会疼：两种失败形态的成本结构

你说的两个痛点——拆太散、拆太大——不是玄学，各有明确的成本构成。把成本列出来之后，"拆到什么程度"就从口味问题变成了定价问题。

拆太散：每次切开都在支付三种固定税

  • 往返税（R）：每新增一个 agent 边界，每次委派都要付出"任务描述 + 上下文重建 + 结果回传"三段 token。Anthropic 实测其多 agent 系统总 token 约为普通对话的 15 倍——需要诚实拆账：这 15 倍的大头是并行子 agent 各自探索的必要消耗（买性能的钱），但每层委派叠加的三段结构成本不买任何性能，是纯开销。
  • 损耗税：跨边界传递必然有损——无法序列化的隐式状态（风格约定、探索中的中间发现）根本传不过去，只能靠父 agent 反复纠正，这就是 Cognition 说的"传话游戏"（game of telephone）。
  • 工具重发现税：每个新容器都要重新读一遍工具/skill 的 description、重新理解工具集，tool 调用链路整体变长。Anthropic 早期 agent 对简单查询 spawn 过 50 个 subagent——这是拆散失控的极端形态。

拆太大：单容器被三种衰减拖垮

  • 压缩衰减：轨迹太长必然触发上下文压缩/截断。Anthropic 明说：200K token 窗口在长任务中依然要靠外置 Memory 保计划、靠开新 subagent 续命——标称窗口 ≠ 有效工作窗口。
  • 注意力衰减：单容器塞进越多无关轨迹，关键状态的注意力权重越被稀释。Anthropic 用子 agent 的核心理由就是"独立上下文窗口"带来的关注点分离。
  • 重放衰减：容器越大，中途失败后从头重跑越贵。生产系统必须做到断点续跑（resume），而一个大容器里根本没有可用的断点。
Σ
拆分决策的经济学：把 N 个单元切成 k 个容器的总成本由三项可测量构成——① 容器固定成本：系统提示 + 工具/技能描述的常驻 token，每容器一份（trace 可测）；② 边往返成本：R × 边调用次数（trace 可测）；③ 不切部分的容量损耗：压缩次数 × 每次压缩丢弃的轨迹比例（trace 可测）。设计期解析求"边际往返税 = 边际容量收益"的最优 k 不可行（数据不足，见局限 1），本框架的替代方案是用阈值开关近似定位这个交点：S、C、R 的 30%/70%/50% 阈值就是交点的经验坐标——牺牲精度，换取可执行。
§3 · 定义

先把话说死：什么是 agent、什么是 skill、什么是 tool

"agent 负责判断、skill 负责执行"是描述，不是定义——描述没法证伪。判定式定义给出的是可测量的架构属性：任何一个候选模块，跑一遍下面三个问题，它是什么就是什么，不看它的名字怎么起。

Q1
它执行时要维持自己的中间状态轨迹吗？（对话历史、探索发现、未定稿的决策）
是 → 它持有上下文 → 它是（或属于）一个 AGENT / 上下文容器。往下走 §4-§5 的容器判定，决定它是独立容器还是并入现有容器。
Q2
它是静态的知识/流程/脚本——加载进某个容器就生效，自身不产生轨迹？
是 → 它是 SKILL / 载荷。它没有"执行"，只有"被某容器在合适的时机读入"。往下走 §4 的 U、L 判定，决定它独立成 skill 还是内联。
Q3
它是无状态的环境接口——调用即返回，既不持有轨迹也不教方法？
是 → 它是 TOOL。注意：tool 的每次返回值仍会写进所在容器的轨迹，所以 tool 的输出体积直接消耗容器的 C 预算（大结果必须落盘只回引用）。
这组定义的可操作性体现在哪里
  • 反例自检：按"职责分工"定义，一个"负责写代码的 agent"和一个"代码生成 skill"都能成立——这就是含糊的根源。按本文定义：写代码过程需要试错轨迹 → 必然是 agent；而"团队代码规范文档"加载即生效、无轨迹 → 必然是 skill。同名异构的问题直接消失。
  • 边界可检验："两个 agent 共享同一条对话 history" 按定义就不是一个系统的两个 agent，而是一个 agent 的两段 prompt；反过来，一个 skill 如果内部自己跑多步对话并维持轨迹，它就已经是 agent，无论文件名叫什么——按本判定它应被当作容器参与聚类。
  • skill 的三级加载成本是物理事实（Anthropic Skills 机制）：L1 = name+description 常驻每个容器的系统提示（每会话都付）；L2 = SKILL.md 正文按需读入；L3 = 附属文件再按需读入。后文的 L 指标就建立在这三级成本上。
§4 · 指标

六个可测量指标：每个都给出测量步骤、阈值与无数据默认值

前三个（S、C、F）决定 agent 容器边界；中间两个（U、L）决定 skill 载荷边界；R 检验 容器间每条通信边是否成立。每个阈值都标注了推导依据或明确声明为待校准的经验值（如 C 的 d），并给出"没有历史数据时"的保守默认值。

S隐式状态耦合率容器维度
单元 j 在拿不到 i 的过程轨迹、只拿 i 的输出 schema 时，产出被复核的重写率。它捕捉的正是隐式状态——探索中的中间发现、风格约定、"哪些路走不通"的负知识（Cognition 说的"行动携带的隐式决策"）。全文所有"隐式占比"都指这同一个量，别无第二定义。
取数三档（按可得性降级，不许跳档）：致命陷阱：隐式冲突在暴露前无法枚举——Cognition 的 Flappy Bird 案例里，美术风格冲突在发生前不在任何人的传递清单上，所以清点法必漏掉最致命的项。
① 历史返工记录（零成本，最优先）：旧系统或人类团队处理同类任务时，下游对上游产出的返工记录，直接换算。
② 桌面推演（零 token，设计期主路径）：把 i 的输出 schema 摆上桌，i 侧作者与 j 侧执行者各自独立推演"拿这份 schema 开工会卡在哪"，然后先做显式化排除：每个卡点先问"能否在动手前通过补 schema / 写说明文档消除？"——能消除的是 schema 缺陷（回 A0 补字段），把它记进 S 等于把"文档写作认真程度"当成耦合强度；消除不了的（卡点内容只存在于过程轨迹中：试错记录、被否决的方案、未定稿的倾向——写不进任何预先文档）才是隐式状态。两人档位不一致 → 取高档（保守仲裁）。推演输出三档：低（≤30%）/ 中（30%~60%）/ 高（>60%），中、高档一律按 > 30% 处理——设计期不假装百分比精度（2~3 条样本的重写率噪声带 ±26 个百分点），三档足够驱动 30% 阈值的二分裁决。
③ 对照实测（有原型后，A5 执行）：同一模型同一 prompt 版本跑对照组——j 拿全轨迹 vs 只拿 schema，两组重写率之差才是 S（直接用绝对重写率会把模型能力、prompt 质量的噪声混进来，误诊"模型弱"为"耦合高"）；≥ 10 条样本才可当连续值。
阈值：S > 30% → i、j 必须同容器。
依据：Cognition 原则的量化版本——30% 的产出被重写意味着每三次协作损失一次完整产出，失败已可预期。S 是模型相关测量（换代后须重测，见局限 2）。
无数据默认值：桌面推演做不了（没人熟悉 j 侧）→ 按高档（>60%）保守合并，宁大勿碎。
C上下文占用率容器维度
容器完成任务所需的峰值 token / 有效工作窗口。有效工作窗口 = 标称窗口 × d（折扣系数，默认 0.50，是全文第一个必须校准的参数）：Anthropic 的 200K 窗口在长任务里仍要外置 Memory + 压缩 + 开新 subagent 续命，证明标称窗口打不了满额——但 0.50 是保守经验值，不是测量结果。锚点校准法：找 2~3 个历史上靠压缩续命的任务（溢出锚点）和 1~2 个从未触发压缩的长任务（安全锚点），d 取两锚点间的居中值；无锚点才允许用 0.50。
测量：取 10~20 条历史同类任务的 trace，统计每条在单容器假设下的完整轨迹 token（系统提示 + skill 加载 + 工具返回 + 思考输出），取 P90。
阈值：C > 70% → 容器必须切分，切分点选在 S 最低的边上。
依据：留 30% 余量给失败重试与计划变更——Anthropic 明确把"计划外溢出"列为生产事故源。
敏感性警告：C 的裁决对 d 高度敏感（算例 2 的"不拆"结论在 d ≥ 0.43 时才成立；同一需求部署在 128K 档位会得出"双超限"）——d 必须锚点校准，不许默认信任。三个保守量（d=0.5、70% 上限、P90）有意相乘，设计预算 ≈ 标称窗口的 35%：这是刻意保守的初始偏置，依据不是"漏拆无害"（§2 的压缩/注意力/重放三种衰减都是真实损失），而是可观测性——保守侧的错误（多付容量）会被 A5 压缩计数立刻报出来，激进侧的错误（跨边损耗）是隐性、难归因的。A5 实测成本数据到位后应把偏置校回中性——漏拆与错拆的真实相对成本取决于业务失败模式（长链路不可重试任务漏拆更贵，轻量可重试任务错拆更贵），这个排序该由你自己的 A5 数据说话，不由默认值预判。
无数据默认值：d=0.50 + 拿人工估算（输入×3 + 工具返回×N），宁可高估。
R往返开销率通信维度
跨容器委派一次的总 token（任务描述 + 为重建上下文而灌入的背景 + 结果回传）/ 被委派单元自身执行 token。这是"拆太散"的直接度量——15× 总成本的大头是并行探索的必要消耗（买性能的钱），R 度量的是叠加其上的纯结构开销；当 R 占比高时，开销就吞噬了拆分换来的并行收益。
测量：trace 中取出委派 prompt 的输入 token 与子容器输出 token，除以子容器内部执行 token。
阈值：R > 50% → 该委派不成立：要么合并两端，要么把大输出改为外置工件只传引用。
依据：R>50% 意味着一半以上算力花在"搬信息"而非"做事情"上。
无数据默认值：任务描述 + 背景重建的 token 超过被委派单元预期执行 token 的 50% → 默认超标（与 R 的比值定义保持同一量纲，不用绝对值判比值）。
U复用度载荷维度
一段候选载荷被引用的不同父流程数。这是 skill 存在的唯一理由：skill 的 L1（name+description）在每个会话都要付常驻成本，只有被多处复用才能摊薄。
测量：盘点现有/规划中的父流程清单，数引用点。注意：同一流程内的多次调用算 U=1（只算不同流程）。
阈值：U ≥ 2 → 候选独立 skill；U = 1 → 永远内联进父流程，不建 skill。
依据：传统代码的 Rule of Three 降到 Rule of Two，因为 skill 抽取成本低（写文档）而持有成本高（每次会话付 L1 常驻）。
无数据默认值：新业务先按 U=1 处理；判定"第二个引用点"时，只有已存在或已立项排期（有需求单/排期表背书）的父流程算数，纯设想中的未来用法不算——否则任何候选载荷都能靠畅想未来凑出 U=2，指标即失效。第二个真实引用点出现后，抽取是机械操作。
L加载共现率载荷维度
两个候选 skill 在任务中被同时需要的程度。决定载荷之间"合并还是拆开"——这是对"为什么不能合并/额外拆分"的直接回答。
测量（两阶段，缺一不可）：① 设计期场景重叠盘点：颗粒度规则——每个场景 = 一条可立项的父需求条目（以需求单/工单为单位，不允许盘点人自由切分——清单划粗划细可盘出任意值，自由颗粒度会让 L 沦为构造量）；分别列出两个候选载荷的适用条目，输出三档：几乎全重叠（高共现）/ 部分重叠（中间）/ 几乎不重叠（低共现），设计期不给裸百分比（与 S 卡同一伪精度纪律）。② 运行期附属文件加载审计：正交候选内容按 A3 体量分层放进附属文件（L3）后，附属文件的按需读取是工具调用日志里天然可观测的真实信号，用 read 事件统计共现。警告：不能用 skill 级触发标记统计 L——合并之后日志里只剩一个触发位，"两个载荷"的共现在原理上不可计算；纯文档型 skill 若未做 L3 分层，先分层再审计，无分层则维持合并并接受"无拆分证据"的代价。
阈值：高共现（≈> 80%）→ 合并为一个 skill；低共现（≈< 20%）且各自高频触发 → 拆开。中间地带 → 合并，等附属文件 read 事件显示正交后再拆。
依据：几乎总一起触发却拆成两个 = 双份 L1 常驻 + 两次 L2 加载，纯亏损；但低共现 + 低频 → 也维持合并（按需加载比独立建 skill 便宜）。
无数据默认值：合并（拆分需要共现证据支持，合并不需要）——但正交候选内容应放进附属文件（L3），让 read 事件成为可观测信号，否则拆分支永远不可达。
F失败重放半径容器维度
单元失败后需要重放的范围占已完成轨迹的比例。切分一条容器边前必须检查：边对面的单元失败，是否会把本容器已完成的工作拖进重跑。
测量：对每个切分边做失败注入演练：使边对面单元失败一次，记录必须重新执行的 token / 全轨迹 token。
阈值：切分后 F > 40%（一次失败重跑近半轨迹）→ 该边不合格：先把可持久化状态外置成工件（checkpoint），再切。
依据：Anthropic 生产经验——"重启昂贵且令用户沮丧"，必须能从断点 resume。
无数据默认值：所有切分边默认先配工件外置，再谈切分。
运行期还有第七个指标（V），不参与初始拆分，负责事后纠错
变更联动率 V：过去 N 次修订中，改载荷 A 必须连带改载荷 B 的比例。上线后 V > 50% 说明两条载荷其实是同一份知识被劈成了两半——边界划错，回 DAG 站 A3 重划。V 是唯一只能在上线后测量的指标，所以放在验证回路（A5）而不是设计期指标里。
§5 · 判断流程

DAG 总览：从新需求到拆分方案，六站走完

先声明框架的两阶段属性，不装全能：设计期（上线前）真正可用的只有 S 的取数三档（历史返工记录 → 桌面推演 → 保守高档，见 §4 S 卡）和 C 的人工估算，第一次走图的产出是保守架构 + 一张带阈值的观察点清单；R、L、F、V 的精确值都要等运行期（上线后）trace，由 A5 回站校准。所以"新需求从顶端进、底端出"得到的是"最保守的可运行方案 + 何时必须回来重拆的触发器"，而不是终局架构——这正是框架与"凭感觉拆"的本质区别：感觉派没有触发器，不知道何时该回来。虚线是回路——拆错了不是失败，是回到对应站点修正。

图 1 · Agent/Skill 拆分判断流程图。实线 = 主流程推进；红虚线 = 设计期回边；橙虚线 = 运行期纠偏回边；每个阈值均对应 §4 指标。图论说明：回边使它成为带反馈环的有向图而非纯 DAG——去掉回边后的主干是 DAG；回边不是缺陷，正是"拆分是可迭代决策"的体现（A2 规则 4 为回边提供终止条件，防无限震荡）。

六站详卡：每一站做什么、过什么判断、不满足去哪

A0操作单元分解输出：OM 清单
把需求拆成操作单元（OM, Operation Unit）：每个 OM 是一次"读懂输入 → 产出输出"的最小完整动作。此时不预设任何 agent/skill 身份——身份是后面算出来的，不是这一步定的。
  • 每个 OM 必须能写成"一个动词短语 + 输入 schema + 输出 schema"。写不出输出 schema 的 OM 要继续拆（它混了两件事）。
  • 数量参考：复杂需求通常落在 3~12 个 OM——这是经验观察，不是硬约束。OM 数量由"每个 OM 能否写出 I/O schema"决定，不设上限：若 > 15 个，先检查是否把"功能模块"当成了"动作"（最常见的误拆）；检查后仍多于 15 个，按 schema 纪律执行即可，不为凑数把两个动作捏合成一个假动作——那会破坏 A1 的边标注和后续所有判定。
A1信息流标注输出：带类型的数据流图
把 OM 按数据依赖连成 DAG，然后给每条边估计隐式占比——即该边的 S 值（定义与取数方法见 §4 S 卡：桌面推演三档制），后续所有容器边界判断共用这一个数：
  • S 低档（≤30%）→ 显式边：schema 可完整描述（如"提取的 20 个字段"）。
  • 大体量但 S 低档 → 工件边：产物（报告全文、代码文件、表格）落外置存储只传引用。
  • S 中/高档（>30%）→ 隐式边：跨容器非法（判据与 A2 规则 1 是同一把 S 尺子，见 A4）。
  • 档位直接对比 30% 阈值裁决：低 → 可切，中/高 → 同容器。边的"名字"（显式/工件/隐式）只是通讯标签，裁决只看档位——避免归类争议。
A2容器聚类 —— 回答"有几个 agent"输出：容器边界
依次过三条规则，不可跳序：
规则 1 · S 合并对每对相邻 OM 算 S（§4 三档取数法）。S > 30% → 同容器。先合再切，防止把高耦合单元强行分离。
规则 2 · C 强制切分估每个簇的峰值 token（系统提示 + skill 加载 + 工具返回 + 轨迹）与有效工作窗口之比。C > 70% → 该簇必须吐出单元，吐谁？沿S 最低的边切——把 S 档位最低的 OM 移出容器。注意与规则 1 的顺序：S 合并在前，C 切分在后，切分点只允许落在低耦合边上。
规则 3 · F 边检查对每条新切出的边做失败注入预演：边对面单元挂掉，本容器要不要大范围重跑？重放半径 > 40% → 先把可持久化状态外置成工件（checkpoint），再切；外置后仍超标 → 该边不合格，两端合并。合并后若簇 C 仍 > 70% → 进入规则 4。
规则 4 · 双超限裁决（终止条件）当簇 C > 70% 且所有候选切分边 S 均 > 30%：输出结论"容量-耦合双超限"——这已不是拆分问题，是当前模型能力边界问题。出路按序判定：① 仅当仍存在规则 3 未穷尽的可外置状态时，工件化后重估 C——对"不可压缩共享状态"型业务（全局文风约束、架构口径本身吃掉窗口）本条无米之炊，直接跳②；② 接受压缩损耗 + 登记"已裁决技术债清单" + 把"压缩时保什么丢什么"显式决策化——登记断的是 A2↔A5 的自动震荡，不是监测：清单内簇改为双周复核压缩质量与产出走样率（压缩丢状态是周级损害，季度节奏追不上），重入 A2 有两把钥匙：（a）模型/长上下文能力升级；（b）A5 对照实测推翻了当初的 S 判档——当初高档是推演者不熟悉 j 侧的误判时，实测重写率差 < 30% 即为证据（双超限未必是容量问题，也可能一开始就是判档错误，钥匙不能只配容量成因的锁）；③ 无钥匙到位则维持登记并双周复核。三条出路走完必居其一，禁止在 A2（合并）与 A5（报警）之间反复震荡。
冷启动无数据没有 trace、也没有人能做桌面推演时：默认 1 个容器起步（C 按人工估算 + d=0.50、S 全部按保守高档），上线后由 A5 的压缩计数触发第一次真实切分。这是框架内置的无数据路径，不靠直觉。
A3载荷判定 —— 回答"哪些是 skill、拆几个"输出：skill 清单 + 各自触发描述
对容器内的每块"专业知识/流程资产"（领域规范、操作流程、脚本包）依次判定：
U 判定U ≥ 2 → 候选 skill；U = 1 → 内联进父容器系统提示。注意：新需求本身只有一个引用点很正常——先内联，等第二个引用点真实出现再抽出（届时是机械操作，不是重构）。
L 判定两个候选载荷共现档位为高共现 → 合并为一个（拆开 = 双份 L1 常驻 + 两次 L2 加载，纯亏）；低共现且各自高频触发 → 拆开；中间档 → 合并。设计期用场景重叠盘点（§4 L 卡测量①，以可立项需求条目为颗粒度），运行期用附属文件 read 事件校准（测量②）——凡执行合并，正交候选内容必须放进附属文件（L3），让 read 事件成为可观测信号，否则拆分证据在原理上无法积累。这一条就是"为什么不能合并/为什么不能再拆"的正式回答：合并与否只由触发场景的统计关系决定，与主题是否相似无关。
体量分层单个 skill 正文 > 500 行（约 8K token）→ 把按场景分支的内容拆成附属文件（L3 渐进披露），主文件只留"何时读哪个附属文件"的索引。注意：附属文件按触发场景拆，不按文档主题拆——和 skill 之间的切分遵循同一条准则。
A4通信契约输出：边契约表
容器之间的每条边都要有契约，且契约类型由 A1 的隐式占比档位唯一决定（与 A2 用同一把 S 尺子）：
显式边直接传 JSON 消息（schema 在 A0 已产出）。
工件边大产物落外置存储，边上传引用（路径/ID）——Anthropic 生产模式：子 agent 产出写文件系统，只把轻量引用回传父容器，同时避开"传话游戏"和 token 膨胀。
隐式边隐式占比 > 30% 的边不允许跨容器——与 A2 规则 1 是同一把 S 尺子：A2 允许切的边（S ≤ 30%）在这里天然合法，规则自洽，不存在"A2 说能切、A4 说非法"的顶牛。占比 ≤ 30% 的残留隐式部分不能装看不见：契约中必须把它提炼成外置工件或说明文档（提炼 = 隐式显式化），并把该边列入 A5 的"回传重写率"重点观察名单——重写率 > 30% 即提炼失败的判据，触发回 A2 合并。提炼不是自由裁量，它有可测的失败标准。
R 复核对每条边实测 R。R > 50% → 合并两端，或把边上的传递物全部改写为工件引用再复测。
A5验证回路 —— 上线后持续纠偏输出：纠偏动作
拆分不是一次定终身，A5 是框架的免疫机制。六项体检，超标即回站修正——特别注意稀疏加载审计：它是六项中唯一的"拆分方向"触发器，其余五项的裁决都指向合并/重划/补外置。这不是设计偏好，是观测不对称：合并方向的证据（返工、压缩、联动变更）免费来自日常运行，拆分方向的证据（正交加载）必须专门分层才能观测——代价是冷启动期框架天然偏保守（见 §4 C 卡的偏置说明）：
压缩计数跑最长链路任务，统计单容器上下文压缩次数。≥ 2 次/任务 → 回 A2 重估（阈值 2 而不是 1：留一次余量给异常路径）：存在合格切分边（S ≤ 30%）→ 吐单元；所有候选边 S 均 > 30% → 走 A2 规则 4（双超限裁决），禁止震荡。"已裁决技术债清单"内的簇不触发本条——它们由规则 4 出口②接管：双周复核压缩质量与产出走样率，重入钥匙见规则 4（模型升级或 S 实测推翻判档）。
token 审计以本系统自身历史周为基线做环比审计：各容器 token 曲线异常抬升 → 查当周新增的边与 skill。不要拿 Anthropic 研究系统的 4×/15× 当通用诊断线——那组数字测量自研究检索类任务，对编码/客服类系统没有可比性（见 §9 诚实声明）；它只用于建立"多 agent 天然就是重成本架构"的量级预期。抬升时优先排查：R 超标的边、U=1 的僵尸 skill（白付 L1 常驻）。
失败注入定期让每个容器的关键 OM 失败一次，实测重放半径。F > 40% → checkpoint 缺失，回 A2 补外置。
变更联动率统计 skill 修订记录。改 A 必须连带改 B 的比例 V > 50% → 载荷边界划错，回 A3 重划（多半是两个"看似不同主题"的 skill 其实共享同一触发场景，按 L 准则合并）。
稀疏加载审计对每个 skill 统计附属文件（L3）的 read 事件：某附属文件在 ≥ 20 次加载中被 read < 20% 且其对应场景自身高频出现 → 回 A3 拆分；低引用 + 低频场景 → 维持合并——按需加载比独立建 skill 便宜，把低频内容拆成独立 skill 只会白付 L1 常驻，正是 U 卡警告的僵尸形态（低共现证明不了各自高频，这是与 L 卡阈值一致的双条件）。这是六项中唯一的拆分方向触发器——没有它，一个错误合并的胖 skill 将永远失明（它 U=2 不算僵尸、不联动变更、也不占容器轨迹）。
回传重写率对 A4 里"提炼过隐式残留"的每条边：子容器产出被父容器重写的比例。> 30% → 提炼失败，隐式残留实际上跨不过边界 → 回 A2 合并该边两端（对应裁决表第 7 行）。
§6 · 速查

边界裁决表：七种常见争论，七个可计算裁决

争论摆到桌面上，先量指标，再看裁决。每一行都给出成本解释——这就是"为什么不能合并/为什么不能再拆"的完整答案集。

你观察到的现象量化信号裁决为什么（成本解释）
两个单元几乎总在同一次任务里先后出现 共现率 > 80% 合并 常拆的两个 skill 是双份 L1 常驻 + 两次 L2 加载；两个常一起干的 agent 是每任务都付一次往返税 R。合并一次省两类税。
两个载荷几乎从不在同一任务中出现 共现率 < 20%，各自触发 ≥ 2 种场景 拆开 互斥内容挤在同一容器里，每次执行互相挤占 C 预算；分开放各自按需加载，L1 常驻成本由复用摊薄。
某容器跑长任务时总在压缩历史 压缩次数 ≥ 2 / 任务 容器过大 → 回 A2 重估 每次压缩都是一次有损状态丢弃，等效于把有效窗口再打折。有合格边（S≤30%）就吐单元；所有边 S>30% 说明踩到模型能力边界，走双超限裁决而不是硬拆。
两个 agent 之间总在传一大坨 JSON R > 50% 合并或改契约 一半以上算力用于搬信息而非做事情；先试"大产物落盘只传引用"，降不下来就合并——这条边在物理上不成立。
某段知识只有一个流程在用 U = 1 内联，不建 skill skill 的 L1 常驻成本每个会话都在付，U=1 意味着纯支出零摊薄。等第二个引用点出现再抽，抽的动作是机械的。
每次改 skill A 都得同步改 skill B 联动变更率 V > 50% 重划载荷边界 联动修订 = 同一份知识被劈成两半。按触发场景（L 准则）重新合并或重新切，而不是按主题"归档整齐"。
子 agent 干完活，父 agent 总要大幅返工 回传结果被父容器重写率 > 30% 回 A2 合并容器 返工是隐式状态跨边损耗的直接症状——任务描述里没写进去的约定（风格、口径、排除项）子 agent 全猜错了。这条边是隐式边，物理上不可传递。
§7 · 算例

两个完整算例：一个拆成多 agent，一个坚决不拆

同一套流程，跑两个方向相反的典型需求。所有数字都是按 §4 测量方法得出的估算值，展示的是怎么算，而不是唯一答案。

算例 1 ·「对 50 家竞品公司做尽职调查报告」→ 拆：1 个 lead agent + N 个调研 subagent + 1 个 skill
典型的研究检索型需求，走 DAG 各站：
A0 分解
OM1 采集单公司公开信息（×50 并行）· OM2 从原始信息提取财务/风险字段 · OM3 汇总横向对比 · OM4 撰写报告章节。每个 OM 的输出都能写出 schema（公司清单 → 字段表 → 对比矩阵 → 章节草稿）。
A1 标注
OM1→OM2：工件边（原始信息量大，落盘）；OM2→OM3：显式边（字段表 JSON）；OM3→OM4：显式边（对比矩阵）；调研过程内部的"哪些信源不可靠"是隐式状态，但只存在于单个公司调研内部，不跨公司边界。
A2 聚类
50 家公司之间 S ≈ 0（互不依赖，无共享隐式状态）——可完全切开。单容器估算：50 × ~8K = 400K token >> 100K 有效窗（200K×50%），C ≈ 400% → 强制切分，切分点在 S≈0 的公司边界上。F 检查：单公司失败只重放该公司（其余 49 家的产物已落盘）→ F ≈ 2%，边合格。结论：1 个 lead agent（做 A2 聚类、A3 汇总）+ 50 个或分批的调研 subagent。
A3 载荷
"信源可靠性评估流程"被本次尽调和已立项排期（下季度需求单已过评审）的"供应商尽调"两个流程引用——第二个引用点有排期背书、不是畅想，U=2 → 抽 skill；"财务字段提取规则"与之做场景重叠盘点（设计期 L 测量①，以需求条目为颗粒度）：两者的适用条目清单几乎完全重叠（凡需要评估信源的报告几乎都要提字段口径）→ 判高共现 → 合并进同一个 skill，字段口径细则作为正交候选内容放进附属文件（L3），让 read 事件成为将来的拆分观测信号（高共现是场景盘点的纸面档位，上线后由 A5 稀疏加载审计校准——若该附属文件 read 正交且高频，说明盘估错了，拆开）。正文超 500 行的部分（分行业的提取细则）拆成附属文件 L3 按行业加载。
A4 契约
subagent 产出全部落盘（每公司一个 JSON 工件），只回传"公司名 + 完成标记"。设计期无实测数据，走默认判据：单次委派的描述 + 背景重建 ≈ 1.5K token，被委派单元预期执行 ≈ 8K token，1.5K < 8K × 50% = 4K → 默认不超标（量纲与 R 一致）；上线后实测 R ≈ 15%，合格。lead agent 汇总时读工件。
裁决：这是教科书式的多 agent 需求——S≈0 可切、C 超限必切、工件化后 R 合格、任务价值付得起 15× 的固有成本（对应 Anthropic 研究系统在内部评测上 +90.2% 性能提升的适用画像：高价值、真并行、信息超窗）。
算例 2 ·「给现有系统加 OAuth 登录」→ 不拆：1 个 agent + 1 个 skill + 若干 tool
典型的编码型需求——正是 Anthropic 明说"大多数编码任务不适合多 agent"的那类：
A0 分解
OM1 设计接入方案（选 provider、回调约定）· OM2 改数据库 schema · OM3 写认证代码 · OM4 写测试。OM3/OM4 高度依赖 OM1 的每一个决策。
A1 标注
OM1→OM3、OM1→OM4 之间是隐式边：设计决策（redirect 约定、异常处理口径、会话策略）没有完整 schema，编码与测试的每一步都在引用这些约定的"氛围"。这正是 Cognition 说的"行动携带隐式决策"。
A2 聚类
对 OM1→OM3 做桌面推演（设计期 S 三档取数，零 token 成本）：把 OM1 的输出 schema（provider、redirect URL、token 结构）摆上桌，编码执行者推演"只拿这份 schema 开工会卡在哪"。第一轮卡点三处——redirect 权威入口未指明、异常码映射缺失、并发约定缺失——按显式化排除规则，这三处都能在动手前补进 schema（回 A0 补字段，它们是文档缺陷不是耦合）。补全后第二轮推演仍卡三处，且卡点写不进任何 schema：三个 provider 方案各试过什么、为何弃用（错误处理代码的风格必须跟随弃用原因）；哪些异常场景被明确排除在处理范围外（负知识，不写进文档）；会话失效的处置倾向（未定稿的权衡，影响测试用例取舍）——这些只存在于设计过程轨迹里。档位 = 高（>60%）> 30% → 全部并入同一容器。显式化排除正是推演的关键纪律：不排除第一轮的 schema 缺陷，"文档认真程度"就会被误记成耦合；排除之后，"补全后仍卡壳"暴露的才是真隐式（Cognition 的 Flappy Bird 式负知识逃不过第二轮）。容量检查：整个任务轨迹估 60K token < 100K 有效窗（d=0.50 校准值），C ≈ 60% < 70% → 无需切分。反向验证：若强行拆 4 个 agent，每个子 agent 都要重建"设计决策"上下文，每次委派 R 估 > 60% → 全部不合格。结论：单容器单 agent；上线后由 A5 对照实测（全轨迹 vs 仅 schema 的重写率差）把 S 从三档校准为精确值。
A3 载荷
"本团队 OAuth 接入规范"（provider 白名单、redirect 安全要求）会被已立项排期的"SSO 接入""第三方授权"复用，U=2 → 抽 skill；"本次需求的临时设计决策"U=1 → 内联进任务上下文，不建 skill（登记进复用观察名单，等下一个真实引用点出现时机械抽取）。
A4 契约
容器内无跨边通信；代码文件作为工件落盘。唯一对外接口是人（需求方）。
裁决：不拆。需求虽"复杂"，但复杂度全在决策一致性而非容量与并行度上——前者惩罚拆分（S 高、R 高），后者奖励拆分（C 高、S 低）。两个算例对照即可看出：框架对拆不拆不持立场，只对六个数负责。
两个算例揭示的关键洞察
"需求复杂"≠"该拆"。惩罚拆分的复杂度（决策互相缠绕、隐式状态多、失败要整体回滚）与奖励拆分的复杂度（信息体量大、子任务天然独立、可并行）是两种正交的复杂度。行业里凭感觉拆的人大多是把前者当成了后者——这个框架的全部价值，就是让你在下刀之前先分清眼前的复杂度是哪一种。
§8 · 局限

这套流程的局限：依赖什么、适用什么、在哪儿失效

不诚实声明局限的框架都是营销物料。以下五条局限按严重程度排列，其中前两条决定了你在什么条件下才能放心使用本框架。

局限 1 · 指标依赖历史数据，新业务存在冷启动窗口

需要先知道：C 和 R 需要 trace（10~20 条同类任务的 token 轨迹）；L 需要 skill 触发历史；U 需要父流程清单；F、V 需要上线后的运行记录。

后果：上线前的第一次拆分，六个指标里通常只有 S 和 C（粗估）可用，此时框架退化为"保守默认值引导"：单容器起步、全部内联、按 A5 的压缩计数触发第一次真实切分。换句话说：框架对存量系统是"决策工具"，对新系统是"观察协议"——它告诉你拆分信号出现时该测什么，而不是替你预知。你可能会问：新业务的答案 = "1 容器 + 0 skill + 上线再看"，这和"凭感觉拆、跑起来再改"有什么区别？区别在触发器：感觉派没有"何时必须回来重拆"的清单；本框架的第一次走图都会产出一组带阈值的观察点（压缩 ≥ 2、第二个真实引用点出现、回传重写率 > 30%、R 实测 > 50%、附属文件 read 正交、变更联动率 > 50%），每个观察点都有明确回站路径。保守架构不是放弃决策，是把决策挂在可观测的扳机上。

局限 2 · 阈值随模型能力漂移，需要周期性校准

依赖关系：C 的折扣系数 d（默认 0.50，无推导的保守经验值）、70% 切分线、S 的 30% 线都建立在当前代模型上——d 是全框架最承重也最缺出处的常数，是校准时的第一复核对象（锚点校准法见 §4 C 卡）。窗口翻倍或长上下文注意力改善后，单容器可承载的单元变多，最优容器数下降——同样的任务换一代模型可能从"该拆"变成"不该拆"；同一任务部署在不同窗口档位结论也会不同（这是框架如实反映成本结构而非不稳定，前提是 d 经过锚点校准）。

后果：模型换代（大约每 6~12 个月）必须重跑 A5 体检并重新校准阈值，S 是模型相关测量（§4）须用对照实测重测；30%/70%/50% 这些数字是可调参数而不是物理常数，每个数字的推导依据写在 §4，校准时优先复核推导链而不是死守数值。

局限 3 · DAG 是静态先验，运行时动态编排不在覆盖范围

本框架产出的是初始架构：容器边界、skill 清单、边契约。但 agent 的本性是运行时自主决定路径（orchestrator-workers 里的子任务划分就是运行时产生的）。运行时该 spawn 几个临时 subagent、何时提前终止，是另一层决策——本框架不替代它，只通过 A5 的持续体检间接约束它。

局限 4 · 明确的适用域与不适用域

适用：信息密集型（研究、尽调、报告生成）、多工具长轨迹、子任务天然可并行的业务；有生产数据可回溯的存量系统。

不适用：① 单轮可完成的任务（无容器边界问题可谈）；② 强实时人机对话（容器边界由对话节奏而非任务结构决定）；③ 极低延迟要求（多容器串行会放大延迟）；④ 多 agent 并发写同一状态库（隐式冲突无法用指标修复，属于 Cognition 原则的禁区）；⑤ 需求本身还在剧烈探索期（OM 清单不稳定，测了也白测）；⑥ 全局一致性长轨迹业务：整个任务依赖一条不可压缩的共享状态（30 万字系列小说的伏笔与文风、超大代码库的全局架构约束）——每条候选切分边 S 都 > 30%、总需求 C 又远超窗口，正是 A2 规则 4 的"容量-耦合双超限"场景。当前代模型没有好的多 agent 解；本框架对它的输出不是"不可解"三个字，而是规则 4 的成套裁决（登记技术债清单 + 压缩策略显式化，或换更大窗口模型后重评）——"不可通过拆分解决"也是一个有出路清单的结论，比硬拆出 15× 成本的一致性事故诚实得多。

局限 5 · 只优化技术维度，组织约束按外生变量处理

现实拆分还受团队边界、权限合规、成本中心、供应商锁定影响。本框架把这些当作外生约束：当组织强加的边界与技术最优解冲突时，如实标注"此边界为组织约束、按 S/C/R 计算为次优"——框架不假装组织因素不存在，但也拒绝用"组织需要"给错误拆分做技术背书。

关于本文数字的诚实声明
