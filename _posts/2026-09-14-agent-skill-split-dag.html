AGENT 架构 · 拆分决策

Agent/Skill 到底应该怎么拆：一套可量化的 DAG 判断流程

不讲"agent 负责思考、skill 负责干活"这种没法说对错的话。这篇文章把拆分变成一道算术题：上下文（token）是最贵、最不够用的资源，拆分边界就是在分 token。所有"感觉"都要翻译成六个数字；数字不支持的拆分，就是错的拆分。

§0 · TL;DR

先说结论：三个问题，各自只有一条标准

整个框架回答的就是这三个问题。每个问题只有一条标准。其他理由——职责清晰、模块整洁、看着好复用——如果换算不成这三条标准之一，就不构成拆或合的依据。

复杂需求
需要几个 agent？
数 agent，不数职责。每个 agent = 一条独立的对话记录（history）。个数由三个数字决定：耦合程度 S（两个步骤之间说不清、传不过去的东西越多，越必须放同一个 agent）、上下文占用 C（活太多、token 超过了实际能用的窗口，必须切开）、失败重跑范围 F（切开之后，一个步骤挂了会不会拖累整个 agent 从头重跑）。三个条件：S ≤ 30% 才允许切开，C > 70% 必须切开，F 超标一票否决。
哪些东西做成 skill、
拆几个？
skill 是资料，不是流程。判断一段知识/流程要不要做成独立 skill，只看两个数：复用度 U（被几个不同流程用到；U=1 一律写进父流程，不建 skill）和一起用的频率 L（两个候选是否几乎总被同时用到：一起用 > 80% 就合并，< 20% 且各自都常被用才值得拆开）。skill 的本质是"分层的、用到才加载的上下文"，所以拆分只有一句话：按触发场景拆，不按主题拆。
为什么不能合并？
为什么不能再拆？
因为合和拆的收益都能算成钱。合并的唯一收益 = 省掉 agent 之间的来回开销 R（派活的任务描述 + 重建背景 + 结果回传，这些 token 花在"搬运"上）；拆分的唯一收益 = 缓解C、拿到U 的复用、缩小F。所有"为什么不能合/为什么不能再拆"的争论，最后都变成这四个数的比较——这就是标准的全部。
§1 · 调研

行业现状：四家四种拆法，没有一家给出能照着做的标准

四份一手材料（Anthropic 三篇工程文章 + Cognition 的反多 agent 文章）里关于拆分的主张，全部摆出来对比：共识确实有，但全停在嘴上，没有数字。

来源核心主张给出的拆分信号对拆分判断而言的缺陷
Anthropic《Building Effective Agents》 从最简单的方案开始，只有"能证明的收益"才加复杂度 步骤能提前列全 → 用 workflow（prompt 串起来）；步骤列不全、要模型临场自己决定 → 才用 agent 回答了"要不要做成 agent"，没回答"一个系统里放几个 agent、skill 怎么切"
Anthropic《How we built our multi-agent research system》 多 agent 在内部研究评测上比单 agent 提升 90.2%；但 token 15× 三个适用条件：任务价值高到付得起 15×；子任务真的能并行；信息量超过单个上下文窗口 有实测数字，但只覆盖研究检索类任务，而且没给判断线——"超出单窗口"超多少才算超、怎么算，没说
Cognition《Don't Build Multi-Agents》 上下文是核心资源；默认单线程单 agent 两条原则：共享完整日志，不要只传单条消息；行动带着说不出口的隐含决定，两边隐含决定不同，必然互相打架 原则是对的，但没法照着做——隐含决定怎么认出来、多少算多、什么时候值得为并行破例，全都没有能测量的答案
Anthropic《Equipping agents for the real world with Agent Skills》 skill = 文件夹（SKILL.md + 脚本 + 资源），三级渐进加载 skill 拆分信号：单文档太大 → 拆附属文件；内容互相用不到/很少一起用 → 分开存 最接近能照着做（渐进加载 = 用到才读），但只讲文档怎么切，不涉及 agent 边界，也没说"多大算大"
调研结论：共识有了，标准没有
四家材料拼起来其实已经接近真相：上下文是唯一稀缺资源——Cognition 说的"隐含决定"、Anthropic 说的"窗口装不下"、Skills 说的"用到才读"，说的都是同一件事：token 不够用。缺的只是把它们拼成一套谁拿到都能照着做的测量流程——这就是本文接下来要做的：把四家的定性主张翻译成六个能量出来的数字和一张流程图。
§2 · 痛点定量化

为什么拆分会疼：拆太散、拆太大，各有各的账单

拆太散、拆太大这两个毛病不是玄学，各有明确的账单。把账单列出来，"拆到什么程度"就从口味问题变成算钱问题。

拆太散：每切一刀都要交三种固定税

  • 来回税（R）：每多一个 agent 边界，每派一次活都要付三段 token：任务描述、重建背景、结果回传。Anthropic 实测它的多 agent 系统总 token 约是普通对话的 15 倍——要诚实算账：这 15 倍的大头是并行子 agent 各自探索的必要开销（花钱买性能），但每层委派叠加的三段是纯白花的，不买任何性能。
  • 损耗税：隔着边界传话必然丢东西——说不清、写不下的隐含状态（风格约定、探索到一半的发现）根本传不过去，只能靠父 agent 反复纠正。Cognition 把这叫"传话游戏"（game of telephone）。
  • 工具重发现税：每个新 agent 都要重新读一遍工具/skill 的说明、重新理解工具集，调用链路整体变长。Anthropic 早期 agent 对一个简单查询开过 50 个 subagent——拆散失控的极端样子。

拆太大：一个 agent 被三种衰减拖垮

  • 压缩衰减：对话记录太长必然触发压缩或截断。Anthropic 明说：200K token 的窗口在长任务里还是要靠外部 Memory 存计划、靠开新 subagent 续命——标称窗口不等于实际能用的窗口。
  • 注意力衰减：一个 agent 塞进越多无关记录，关键信息的注意力越被稀释。Anthropic 用子 agent 的核心理由就是"独立的上下文窗口"能让它专注。
  • 重跑衰减：agent 越大，中途挂了从头重跑越贵。生产系统必须能从断点续跑，而一个大 agent 里根本没有可用的断点。
Σ
拆分决策的经济学：把 N 个步骤切成 k 个 agent 的总成本由三项能测量的部分构成——① 每个 agent 的固定成本：系统提示 + 工具/skill 说明的常驻 token，每个 agent 一份（日志可测）；② 每条边的来回成本：R × 边的调用次数（日志可测）；③ 没切开的部分的容量损耗：压缩次数 × 每次压缩丢掉的记录比例（日志可测）。想在设计期直接算出最优的 k，做不到（数据不够，见局限 1）。本框架的替代方案是用几个带判断线的开关去近似定位这个交点：S、C、R 的 30%/70%/50% 就是交点的经验坐标——牺牲精度，换来能执行。
§3 · 定义

先把话说死：什么是 agent、什么是 skill、什么是 tool

"agent 负责判断、skill 负责执行"是描述，不是定义——描述没法说对错。判定式定义给的是可测量的属性：任何候选模块，跑一遍下面三个问题，它是什么就是什么，不管它名字叫什么。

Q1
它干活时要维护自己的中间过程吗？（对话记录、探索发现、没定稿的决定）
是 → 它装着上下文 → 它是（或属于）一个 AGENT。接着走 §4-§5 的判断，决定它自己单独一个 agent，还是并进现有的 agent。
Q2
它是静态的知识/流程/脚本——读进某个 agent 就生效，自己不产生过程？
是 → 它是 SKILL / 资料。它没有"执行"，只有"被某个 agent 在合适的时机读入"。接着走 §4 的 U、L 判断，决定它独立成 skill 还是直接写进父流程。
Q3
它是无状态的环境接口——一调就返回，既不装过程也不教方法？
是 → 它是 TOOL。注意：tool 每次的返回值会写进所在 agent 的记录，所以 tool 的输出大小直接吃掉该 agent 的 C 预算（大结果必须存成文件、只回传引用）。
这组定义的可操作性体现在哪里
  • 反例自检：按"职责分工"定义，"一个负责写代码的 agent"和"一份代码生成 skill"都能成立——这就是含糊的根源。按本文定义：写代码需要试错过程 → 必然是 agent；"团队代码规范文档"读进去就生效、没有过程 → 必然是 skill。同一个名字两种东西的问题直接消失。
  • 边界可检验："两个 agent 共享同一条对话记录"按定义就不是一个系统的两个 agent，是一个 agent 的两段 prompt；反过来，一个 skill 如果内部自己跑多步对话、维持过程，它就已经是 agent，不管文件名叫什么——按本判定它应当作 agent 参与分组。
  • skill 的三级加载成本是物理事实（Anthropic Skills 机制）：L1 = name+description，常驻每个 agent 的系统提示（每个会话都要付）；L2 = SKILL.md 正文，用到才读；L3 = 附属文件，再要用到才读。后文的 L 指标就建立在这三级成本上。
§4 · 指标

六个能量出来的指标：怎么量、判断线是多少、没数据时怎么办

前三个（S、C、F）决定 agent 的边界；中间两个（U、L）决定 skill 的边界；R 检查 agent 之间每条传话划不划算。每条判断线都标了依据，或者老实承认是待校准的经验值（比如 C 的 d），并给出"没有历史数据时"的保守默认值。

S耦合程度agent 边界
下游步骤 j 在拿不到上游步骤 i 的过程记录、只拿到 i 的输出格式时，干完的活被返工重写的比例。它量的正是那些说不清、传不过去的东西——探索到一半的发现、风格约定、"哪些路走不通"（Cognition 说的"行动带着隐含决定"）。全文所有"隐含占比"都指这同一个量，没有第二个定义。
怎么量（三档，按可得性降级，不许跳档）：先说一个致命陷阱：隐含的冲突在暴露之前没法列清单——最致命的约定在出问题之前，不在任何人的交接清单上，所以靠清点必漏。
① 历史返工记录（零成本，最优先）：旧系统或人类团队处理同类任务时，下游对上游产出的返工记录，直接换算。
② 纸面推演（零 token，设计期主路径）：把 i 的输出格式摆上桌，i 侧作者和 j 侧执行者各自独立推演"只拿这份格式开工会卡在哪"，然后先做排除：每个卡点先问"能不能在动手前补格式、写说明消除？"——能消除的是文档缺陷（回 A0 补字段），把它记进 S 等于把"文档写得认不认真"当成耦合强度；消除不了的（卡点内容只存在于过程记录里：试错记录、被否决的方案、没定稿的倾向——写不进任何提前准备的文档）才是真耦合。两人档位不一致 → 取高档（保守）。推演输出三档：低（≤30%）/ 中（30%~60%）/ 高（>60%），中、高档一律按 > 30% 处理——设计期不假装有百分比精度（2~3 条样本的重写率噪声带 ±26 个百分点），三档足够支撑 30% 判断线的二分裁决。
③ 对照实测（有原型后，A5 执行）：同一模型同一 prompt 版本跑两组——j 拿全记录 vs 只拿格式，两组重写率的差才是 S（直接用绝对重写率会把模型能力、prompt 质量的噪声混进来，把"模型弱"误诊成"耦合高"）；≥ 10 条样本才能当连续值用。
判断线：S > 30% → i、j 必须放同一个 agent。
依据：Cognition 原则的量化版——30% 的产出被重写，等于每干三次就废一次，失败已经可以预期。S 是跟模型相关的测量（换模型要重测，见局限 2）。
没有数据时：纸面推演做不了（没人熟悉 j 侧）→ 按高档（>60%）保守合并，宁可先合在一起。
C上下文占用agent 边界
一个 agent 干完任务需要的峰值 token ÷ 实际能用的窗口。实际能用的窗口 = 标称窗口 × d（折扣系数，默认 0.50，是全文第一个必须校准的参数）：Anthropic 的 200K 窗口在长任务里还要外部 Memory + 压缩 + 开新 subagent 续命，说明标称窗口打不了满额——但 0.50 是保守经验值，不是测量结果。锚点校准法：找 2~3 个历史上靠压缩续命的任务（溢出锚点）和 1~2 个从没触发过压缩的长任务（安全锚点），d 取两个锚点中间的值；没有锚点才允许用 0.50。
怎么量：取 10~20 条历史同类任务的日志，统计每条在"一个 agent 装下"的假设下的完整记录 token（系统提示 + skill 加载 + 工具返回 + 思考输出），取 P90。
判断线：C > 70% → 必须切，切的位置选在 S 最低的边上。
依据：留 30% 余量给失败重试和计划变更——Anthropic 明确把"计划外溢出"列为生产事故来源。
敏感性警告：C 的裁决对 d 非常敏感——d 定 0.50 还是 0.43，可能直接翻转一次"拆不拆"的结论；同一个需求放到 128K 窗口的档位上，会直接得出"容量、耦合双超线"。d 必须锚点校准，不许默认信任。三个保守量（d=0.5、70% 上限、P90）是有意叠乘的，设计预算 ≈ 标称窗口的 35%：这是刻意保守的初始偏向，依据不是"漏拆无害"（§2 的压缩/注意力/重跑三种衰减都是真实损失），而是可观测性——保守侧的错误（多付容量）会被 A5 的压缩计数立刻报出来，激进侧的错误（跨边损耗）是隐性的、难归因的。A5 实测数据到位后应把偏向校回中性——漏拆与错拆哪个更贵，取决于业务失败模式（长链路不可重试的任务漏拆更贵，轻量可重试的任务错拆更贵），这个排序该由你自己的 A5 数据说话，不由默认值预判。
没有数据时：d=0.50 + 人工估算（输入×3 + 工具返回×N），宁可往高了估。
R来回开销agent 之间
跨 agent 派一次活的总 token（任务描述 + 重建背景 + 结果回传）÷ 被派单元自己干活的 token。这是"拆太散"的直接度量——15× 总成本的大头是并行探索的必要开销（花钱买性能），R 量的是叠加在上面的纯结构开销；R 占比高时，来回搬运就吃掉了拆分换来的并行收益。
怎么量：从日志里取出派活的输入 token 和子 agent 的输出 token，除以子 agent 内部干活的 token。
判断线：R > 50% → 这次委派不成立：要么合并两端，要么把大输出改成存文件、只传引用。
依据：R>50% 意味着一半以上算力花在"搬信息"而不是"做事情"上。
没有数据时：任务描述 + 重建背景的 token 超过被派单元预期干活 token 的 50% → 默认超标（和 R 的比值定义保持同一量纲，不用绝对值判比值）。
U复用度skill 边界
一段候选资料被几个不同的父流程引用。这是 skill 存在的唯一理由：skill 的 L1（name+description）每个会话都要付常驻成本，只有被多处复用才摊得薄。
怎么量：盘点现有/规划中的父流程清单，数引用点。注意：同一流程内调用多次算 U=1（只数不同流程）。
判断线：U ≥ 2 → 候选独立 skill；U = 1 → 永远写进父流程，不建 skill。
依据：传统代码的 Rule of Three 降到 Rule of Two，因为 skill 抽出来便宜（写文档），养起来贵（每会话付 L1 常驻）。
没有数据时：新业务先按 U=1 处理；判定"第二个引用点"时，只有已存在或已立项排期（有需求单/排期表背书）的父流程算数，纯畅想的未来用法不算——否则任何候选都能靠畅想凑出 U=2，指标就失效了。第二个真实引用点出现后，抽出来是机械动作。
L一起用的频率skill 边界
两个候选 skill 在任务里被同时需要的程度。决定资料之间"合并还是拆开"——这是对"为什么不能合并/为什么还要拆"的直接回答。
怎么量（两步，缺一不可）：① 设计期场景重叠盘点：颗粒度规则——每个场景 = 一条可立项的父需求条目（以需求单/工单为单位，不许盘点人自由切分——清单划粗划细能盘出任意值，自由颗粒度会让 L 沦为想造多少造多少的量）；分别列出两个候选资料的适用条目，输出三档：几乎全重叠（高共现）/ 部分重叠（中间）/ 几乎不重叠（低共现），设计期不给裸百分比（和 S 卡同一纪律：不假装有精度）。② 运行期附属文件加载审计：正交的候选内容按 A3 的体量规则分层放进附属文件（L3）后，附属文件被读是工具调用日志里天然可观测的真实信号，用 read 事件统计共现。警告：不能用 skill 级触发标记统计 L——合并之后日志里只剩一个触发位，"两个资料"的共现从原理上就不可计算；纯文档型 skill 若没做 L3 分层，先分层再审计，没有分层就维持合并，接受"没有拆分证据"的代价。
判断线：高共现（≈> 80%）→ 合并成一个 skill；低共现（≈< 20%）且各自高频触发 → 拆开。中间地带 → 合并，等附属文件 read 事件显示真的正交再拆。
依据：几乎总一起用却拆成两个 = 双份 L1 常驻 + 两次 L2 加载，纯亏；但低共现 + 低频 → 也维持合并（按需加载比独立建 skill 便宜）。
没有数据时：合并（拆分需要共现证据支持，合并不需要）——但正交的候选内容应放进附属文件（L3），让 read 事件成为可观测信号，否则"该拆"的证据永远积累不起来。
F失败重跑范围agent 边界
一个步骤挂了以后，要重跑的范围占已完成记录的比例。切一条 agent 边之前必须检查：边对面的步骤挂了，会不会把这边已完成的工作拖进重跑。
怎么量：对每条要切的边做失败注入演练：让边对面的步骤故意失败一次，记录必须重做的 token ÷ 全部记录 token。
判断线：切开后 F > 40%（一次失败重跑接近一半记录）→ 这条边不合格：先把能存下来的状态放到文件里（checkpoint），再切。
依据：Anthropic 生产经验——"重启又贵又让用户崩溃"，必须能从断点继续。
没有数据时：所有要切的边默认先配好 checkpoint，再谈切。
上线后还有第七个指标（V），不参与初始拆分，负责事后纠错
改动联动率 V：过去 N 次修订里，改 skill A 必须连带改 skill B 的比例。上线后 V > 50%，说明两份 skill 其实是同一份知识被劈成了两半——边界划错了，回流程图 A3 重划。V 是唯一只能上线后测量的指标，所以放在验证回路（A5），不放在设计期。
§5 · 判断流程

总流程：从新需求到拆分方案，六步走完

标题里的 DAG = 有向无环图，说白了就是一张"每步只往前走、不绕圈"的依赖图。先说清楚这个框架分两段，不装全能：设计期（上线前）真正能用的只有 S 的三档取数（历史返工记录 → 纸面推演 → 保守高档，见 §4 S 卡）和 C 的人工估算，第一次走图的产出是保守架构 + 一张带判断线的观察点清单；R、L、F、V 的精确值都要等运行期（上线后）的日志，由 A5 回头校准。所以"新需求从顶端进、底端出"得到的是"最保守的能跑方案 + 什么时候必须回来重拆的明确信号"，不是终局架构——这正是框架和"凭感觉拆"的本质区别：凭感觉的人没有回头信号，不知道什么时候该回来。虚线是回头路——拆错了不算失败，是回到对应的步骤修正。

图 1 · Agent/Skill 拆分判断流程。实线 = 主流程；红虚线 = 设计期的回头路；橙虚线 = 上线后的回头路；每个数字都对应 §4 的指标。图论说明：带回头路的图严格说不是纯 DAG——去掉回头路，剩下的主干才是 DAG（有向无环图，一张"只往前走、不绕圈"的依赖图）；回头路不是缺陷，它说明拆分可以迭代（A2 规则 4 给回头路设了终止条件，防止无限循环）。

六步详卡：每步做什么、过什么检查、不达标去哪

A0拆步骤输出：步骤清单
把需求拆成一个个步骤：每个步骤是一次"读懂输入 → 产出输出"的最小完整动作。这一步不预设任何 agent/skill 身份——身份是后面算出来的，不是这步定的。
  • 每个步骤必须能写成"一个动词短语 + 输入格式 + 输出格式"。写不出输出格式的步骤要继续拆（它混了两件事）。
  • 数量参考：复杂需求通常落在 3~12 个步骤——这是经验观察，不是硬约束。数量由"每个步骤能不能写出输入输出格式"决定，不设上限：超过 15 个，先检查是不是把"功能模块"当成了"动作"（最常见的误拆）；检查完还是多于 15 个，就按格式纪律执行，不为凑数把两个动作捏成一个假动作——那会破坏 A1 的标注和后面所有判断。
A1标依赖输出：带类型的依赖图
把步骤按数据依赖连成图，然后给每个交接估计耦合档位——就是该边的 S 值（定义和取法见 §4 S 卡：纸面推演三档制），后面所有 agent 边界判断共用这一个数：
  • S 低档（≤30%）→ 格式边：内容能写进输出格式，照着格式就能干。
  • 大体量但 S 低档 → 文件边：产物存到外部存储，边上传引用（路径/ID）。
  • S 中/高档（>30%）→ 隐含边：不允许跨 agent（判断和 A2 规则 1 是同一把 S 尺子，见 A4）。
  • 档位直接跟 30% 判断线比：低 → 可以切，中/高 → 同一个 agent。边叫什么名字（格式边/文件边/隐含边）只是通讯标签，裁决只看档位——免得在归类上吵架。
A2分组 —— 回答"有几个 agent"输出：agent 边界
依次过三条规则，不许跳序：
规则 1 · S 合并对每对相邻步骤算 S（§4 三档取法）。S > 30% → 同一个 agent。先合再切，防止把高耦合的步骤强行拆开。
规则 2 · C 强制切分估每组的峰值 token（系统提示 + skill 加载 + 工具返回 + 记录）÷ 实际能用的窗口。C > 70% → 这组必须吐出步骤。吐谁？沿S 最低的边切——把 S 档位最低的步骤移出去。注意顺序：S 合并在前、C 切分在后，切分点只允许落在低耦合的边上。
规则 3 · F 边检查对每条新切出来的边做失败预演：边对面的步骤挂了，这边要不要大范围重跑？重跑范围 > 40% → 先把能存下来的状态放到文件里（checkpoint），再切；放到文件里之后还超标 → 这条边不合格，两端合并。合并后如果这组 C 还是 > 70% → 进规则 4。
规则 4 · 双超线裁决（终止条件）当一组 C > 70% 且所有候选切分边的 S 都 > 30%：输出结论"容量和耦合双超线"——这已经不是拆分问题了，是当前模型能力不够的问题。出路按顺序判定：① 只有还存在规则 3 没试完的、能放到文件里的状态时，存成文件后重算 C——对"没法压缩的共享状态"型业务（全局风格约束、架构口径本身吃掉窗口），这一条没有能放到文件里的东西，直接跳②；② 接受压缩损失 + 登记"已裁决技术债清单" + 把"压缩时保什么丢什么"写成明确决定——登记是为了断掉 A2 和 A5 之间的自动来回，不是不监测：清单内的组改为双周复核压缩质量和产出走样率（压缩丢状态是周级损害，季度节奏追不上）。重新进 A2 要两把钥匙：（a）模型/长上下文能力升级；（b）A5 对照实测推翻了当初的 S 判档——如果当初判高档是因为推演的人不熟悉下游那头，实测重写率差 < 30% 就是证据（双超线未必是容量问题，也可能一开始就是判错了档，钥匙不能只配容量这一把锁）；③ 没有钥匙就维持登记、双周复核。三条出路必居其一，禁止在 A2（合并）和 A5（报警）之间反复折腾。
冷启动无数据没有日志、也没人能做纸面推演时：默认 1 个 agent 起步（C 按人工估算 + d=0.50，S 全按保守高档），上线后由 A5 的压缩计数触发第一次真实切分。这是框架内置的无数据路径，不靠直觉。
A3挑 skill —— 回答"哪些做成 skill、拆几个"输出：skill 清单 + 触发说明
对 agent 内的每块"专业知识/流程资产"（领域规范、操作流程、脚本包）依次判定：
U 判定U ≥ 2 → 候选 skill；U = 1 → 直接写进父 agent 的系统提示。注意：新需求本身只有一个引用点很正常——先写进去，等第二个引用点真实出现再抽出来（那时是机械操作，不是重构）。
L 判定两个候选资料的共现档位为高共现 → 合并成一个（拆开 = 双份 L1 常驻 + 两次 L2 加载，纯亏）；低共现且各自高频触发 → 拆开；中间档 → 合并。设计期用场景重叠盘点（§4 L 卡测量①，以可立项的需求条目为颗粒度），运行期用附属文件 read 事件校准（测量②）——只要执行了合并，正交的候选内容必须放进附属文件（L3），让 read 事件成为可观测的信号，否则"该拆"的证据从原理上积累不起来。这一条就是"为什么不能合并/为什么不能再拆"的正式回答：合不合并只由触发场景的统计关系决定，跟主题像不像无关。
体量分层单个 skill 正文 > 500 行（约 8K token）→ 把按场景分支的内容拆成附属文件（L3，用到才读），主文件只留"什么时候读哪个附属文件"的索引。注意：附属文件按触发场景拆，不按文档主题拆——跟 skill 之间的切分是同一条准则。
A4定传话规矩输出：交接规矩表
agent 之间的每条边都要有规矩，规矩的类型由 A1 的耦合档位唯一决定（和 A2 用同一把 S 尺子）：
格式边直接传 JSON 消息（格式在 A0 已经写好）。
文件边大产物存到外部存储，边上传引用（路径/ID）——Anthropic 的生产做法：子 agent 的产出写文件系统，只把轻量引用回传父 agent，同时避开"传话游戏"和 token 膨胀。
隐含边隐含占比 > 30% 的边不允许跨 agent——和 A2 规则 1 是同一把 S 尺子：A2 允许切的边（S ≤ 30%）在这里天然合法，规则自洽，不存在"A2 说能切、A4 说不行"的矛盾。占比 ≤ 30% 的残留隐含部分不能装看不见：规矩里必须把它写进文件或说明文档（提炼 = 把隐含的写明白），并把这条边列入 A5 的"回传重写率"重点观察名单——重写率 > 30% 就是提炼失败的标准，触发回 A2 合并。提炼不是随口一说，它有可测的失败线。
R 复核对每条边实测 R。R > 50% → 合并两端，或把边上传递的东西全部改成文件引用再复测。
A5上线后体检 —— 持续纠错输出：纠错动作
拆分不是一次定终身，A5 是框架的自动纠错机制。六项体检，超标就回对应的步修——特别注意闲置文件审计：它是六项里唯一的"拆分方向"触发器，其余五项的裁决都指向合并、重新划边、把状态存到文件。这不是设计偏好，是观测不对称：合并方向的证据（返工、压缩、联动变更）免费来自日常运行；拆分方向的证据（正交加载）必须专门分层才观测得到——代价是冷启动期框架天然偏保守（见 §4 C 卡的偏向说明）：
压缩计数跑最长链路的任务，统计单个 agent 的上下文压缩次数。≥ 2 次/任务 → 回 A2 重估（线取 2 不是 1：留一次余量给异常路径）：有合格的切分边（S ≤ 30%）→ 吐步骤；所有候选边 S 都 > 30% → 走 A2 规则 4（双超线裁决），不许反复折腾。"已裁决技术债清单"内的组不触发本条——它们由规则 4 出路②接管：双周复核压缩质量和产出走样率，重进的钥匙见规则 4（模型升级，或 S 实测推翻判档）。
token 审计拿本系统自己的历史周当基线做环比：各 agent 的 token 曲线异常抬升 → 查当周新增的边和 skill。别拿 Anthropic 研究系统的 4×/15× 当通用诊断线——那组数量的是研究检索类任务，对编码/客服类系统没有可比性（见 §8 诚实声明）；它只用于建立"多 agent 天生就是重成本架构"的量级预期。抬升时优先排查：R 超标的边、U=1 还挂着名的 skill（白付 L1 常驻）。
失败注入定期让每个 agent 的关键步骤故意失败一次，实测重跑范围。F > 40% → 说明缺 checkpoint，回 A2 先把状态存成文件。
改动联动率统计 skill 修订记录。改 A 必须连带改 B 的比例 V > 50% → skill 边界划错，回 A3 重划（多半是两个"看着主题不同"的 skill 其实共享同一个触发场景，按 L 准则合并）。
闲置文件审计对每个 skill 统计附属文件（L3）的 read 事件：某个附属文件在 ≥ 20 次加载里被读 < 20%，而它对应的场景自己又常出现 → 回 A3 拆分；低引用 + 低频场景 → 维持合并——按需加载比单独建 skill 便宜，把低频内容建成独立 skill 只会白付 L1 常驻，正是 U 卡警告的浪费形态（低共现证明不了各自高频，这是和 L 卡判断线一致的双条件）。这是六项里唯一的拆分方向触发器——没有它，一个错误合并的胖 skill 永远看不见（它 U=2 不算浪费、不联动变更、也不占 agent 记录）。
回传重写率对 A4 里"提炼过隐含残留"的每条边：子 agent 的产出被父 agent 重写的比例。> 30% → 提炼失败，说不清的部分实际上跨不过边界 → 回 A2 合并这条边的两端（对应裁决表第 7 行）。
§6 · 速查

边界裁决表：七种常见争论，七个能算出来的裁决

争论摆上桌：先量指标，再看裁决。每一行都给出成本解释——这就是"为什么不能合并/为什么不能再拆"的完整答案。

你观察到的现象量化信号裁决为什么（成本解释）
两个步骤几乎总在同一次任务里先后出现 共现率 > 80% 合并 常一起用的两个 skill 拆开是双份 L1 常驻 + 两次 L2 加载；常一起干的两个 agent 是每任务都白付一次来回开销 R。合并一次省两类钱。
两个 skill 几乎从不在同一任务里出现 共现率 < 20%，各自触发 ≥ 2 种场景 拆开 互斥内容挤在同一个 agent 里，每次执行互相挤占 C 预算；分开放各自按需加载，L1 常驻成本由复用摊薄。
某个 agent 跑长任务时总在压缩历史 压缩次数 ≥ 2 / 任务 agent 过大 → 回 A2 重估 每次压缩都是一次有损丢弃，等于把能用的窗口再打折。有合格边（S≤30%）就吐步骤；所有边 S>30% 说明踩到模型能力边界，走双超线裁决，不是硬拆。
两个 agent 之间总在传一大坨 JSON R > 50% 合并或改规矩 一半以上算力用来搬信息而不是干活；先试"大产物存文件只传引用"，降不下来就合并——这条边物理上不成立。
某段知识只有一个流程在用 U = 1 写进父流程，不建 skill skill 的 L1 常驻成本每个会话都在付，U=1 意味着纯支出零摊薄。等第二个引用点出现再抽，抽的动作是机械的。
每次改 skill A 都得同步改 skill B 改动联动率 V > 50% 重划 skill 边界 联动修订 = 同一份知识被劈成两半。按触发场景（L 准则）重新合并或重新切，不是按主题"归档整齐"。
子 agent 干完活，父 agent 总要大幅返工 回传结果被父 agent 重写率 > 30% 回 A2 合并 agent 返工是说不清部分跨边丢失的直接症状——任务描述里没写的约定（风格、口径、排除项），子 agent 全靠猜。这条边是隐含边，物理上传不过去。
拆不拆，先分清你面对的是哪种复杂
"需求复杂"不等于"该拆"。惩罚拆分的复杂——决策互相缠绕、说不清的部分多、失败要整体回滚——和奖励拆分的复杂——信息量大、子任务天然独立、可以并行——是两种不一样的复杂。凭感觉拆的人，大多把前者当成了后者。这个框架的全部价值，就是让你在动手拆之前，先用六个数字分清眼前是哪种。
§7 · 局限

这套流程的局限：依赖什么、适用什么、在哪失效

不老实说清局限的框架都是营销材料。五条局限按严重程度排，前两条决定你在什么条件下才能放心用。

局限 1 · 指标依赖历史数据，新业务有冷启动窗口

需要先知道：C 和 R 需要日志（10~20 条同类任务的 token 记录）；L 需要 skill 触发历史；U 需要父流程清单；F、V 需要上线后的运行记录。

后果：上线前的第一次拆分，六个指标里通常只有 S 和 C（粗估）能用，这时框架退化为"保守默认值引导"：单个 agent 起步、全部写进父流程、按 A5 的压缩计数触发第一次真实切分。换句话说：框架对存量系统是"决策工具"，对新系统是"观察清单"——它告诉你拆分信号出现时该测什么，不是替你预知。你可能会问：新业务的答案 = "1 个 agent + 0 个 skill + 上线再看"，这和"凭感觉拆、跑起来再改"有什么区别？区别在回头信号：凭感觉的人没有"什么时候必须回来重拆"的清单；本框架每走一遍图都会产出一组带判断线的观察点（压缩 ≥ 2、第二个真实引用点出现、回传重写率 > 30%、R 实测 > 50%、附属文件 read 正交、改动联动率 > 50%），每个观察点都有明确的回步路径。保守架构不是放弃决策，是把决策挂在能观测的信号上。

局限 2 · 判断线随模型能力漂移，需要定期校准

依赖关系：C 的折扣系数 d（默认 0.50，没有推导的保守经验值）、70% 切分线、S 的 30% 线都建立在当前这代模型上——d 是全框架最承重也最没出处的常数，校准时第一个复核它（锚点校准法见 §4 C 卡）。窗口翻倍或长上下文注意力改善后，单个 agent 能装的步骤变多，最优 agent 数下降——同一个任务换一代模型可能从"该拆"变成"不该拆"；同一任务部署在不同窗口档位，结论也会不同（这是框架如实反映成本结构，不是不稳定，前提是 d 经过锚点校准）。

后果：模型换代（大约每 6~12 个月）必须重跑 A5 体检、重新校准判断线；S 是跟模型相关的测量（§4）要用对照实测重测；30%/70%/50% 这些数字是可调参数不是物理常数，每个数字的依据写在 §4，校准时优先复核推导链，不要死守数值。

局限 3 · 流程图是静态设计，运行时的临场编排不在覆盖范围

本框架产出的是初始架构：agent 边界、skill 清单、边上的规矩。但 agent 的本性是运行时自己决定路径（orchestrator-workers 里的子任务划分就是运行时产生的）。运行时该临时开几个 subagent、什么时候提前终止，是另一层决策——本框架不替代它，只通过 A5 的持续体检间接约束它。

局限 4 · 明确的适用范围与不适用范围

适用：信息密集型（研究、尽调、报告生成）、多工具长记录、子任务天然可并行的业务；有生产数据可回溯的存量系统。

不适用：① 单轮能完成的任务（没有 agent 边界问题可谈）；② 强实时人机对话（agent 边界由对话节奏决定，不由任务结构决定）；③ 极低延迟要求（多个 agent 串行会放大延迟）；④ 多 agent 并发写同一个状态库（隐含冲突没法用指标修复，属于 Cognition 原则的禁区）；⑤ 需求本身还在剧烈探索期（步骤清单不稳定，测了也白测）；⑥ 全局一致性长链路业务：整个任务依赖一条没法压缩的共享状态——每条候选切分边 S 都 > 30%、总需求 C 又远超窗口，正是 A2 规则 4 的"双超线"场景。当前这代模型没有好的多 agent 解；本框架对它的输出不是"没救"三个字，而是规则 4 的成套出路（登记技术债清单 + 压缩策略写明确，或换更大窗口的模型后重评）——"拆分解决不了"也是一个带出路清单的结论，比硬拆出 15× 成本的一致性事故诚实得多。

局限 5 · 只优化技术维度，组织约束当外部变量处理

现实拆分还受团队边界、权限合规、成本中心、供应商锁定影响。本框架把这些当外部约束：当组织强加的边界和技术最优解冲突时，如实标注"此边界是组织约束、按 S/C/R 算是次优"——框架不假装组织因素不存在，但也拒绝用"组织需要"给错误的拆分做技术背书。

关于本文数字的诚实声明
15×、4×、80%、90.2%、50 个 subagent 这些数字都出自 Anthropic/Cognition 的公开材料，而且量的是研究检索类任务；本文把它们用作成本结构的量级参考（不是普适常数）。特别澄清：15× 在原文语境里是拆对了的多 agent 系统本来就有的运行成本（Anthropic 认为该由任务价值买单），本文用它论证"每个 agent 边界都有固定成本"，不是"拆分过散的账单"。S/C/R/U/L/F 六个指标和 30%/70%/50% 这些判断线是本文提出的工程约定，依据随文标注；正确姿势是按 §7 局限 2 定期校准，不是照抄。
本文是方法论文章，不绑定任何具体框架（Claude Agent SDK / LangGraph / swarm / AutoCode 都适用这套流程）。指标判断线欢迎拿生产数据反驳——按 §7 的校准协议，被数据推翻的判断线会变成本框架的一部分。
