Ollama 0.34.0：上下文压缩开始成为模型服务的接口能力

这次更新的价值不在于让模型“记得更多”，而在于把长任务续跑所需的压缩、保留和恢复，放进一个可被 Agent 客户端调用的 Responses 应用程序编程接口（API，Application Programming Interface）兼容层。

先给结论值得在本地模型或自托管 Agent 的灰度环境验证；不应把 encrypted_content 当作加密边界，也不应在没有连续性回归集的情况下直接替换现有上下文管理器。

01 / WHAT

做了什么

Ollama 0.34.0 新增 OpenAI 兼容的客户端工具搜索与响应压缩，并注册 /v1/responses/compact。

02 / WHY

解决谁的问题

解决长时间 Agent 对话不断累积工具结果、推理和状态，最终超出上下文窗口或重复发送大工具目录的问题。

03 / HOW

核心机制

服务端把有序轨迹交给普通 Responses 推理链，要求模型严格调用 create_summary，再校验保留项并返回版本化续接状态。

04 / SHIP

生产判断

可作为本地/云模型切换时的兼容层候选。生产接入的关键不是“压缩率”，而是状态完整性、失败可恢复和可审计。

来源事实Ollama GitHub Release 页面显示 v0.34.0 发布于 2026-09-09 21:51:51 协调世界时（UTC）。本文推断它更像 Agent 基础设施接口的成熟化，而不是模型能力跃迁。
02 / Background

背景与问题：长上下文不是无限工作记忆

上下文窗口（context window）是模型一次请求可以引用的输入与输出总量。随着多轮对话推进，用户消息、模型响应、工具定义、工具结果、推理块和图像都会进入这个预算。窗口变大并不等于信息管理问题消失：Anthropic 的官方文档明确提醒，长上下文会出现“上下文腐化”（context rot），即输入变长后准确性和召回能力下降。

A普通 Agent loop 的成本

如果每一轮都把完整历史重新发送，成本和延迟随轨迹增长。更危险的是，工具结果常常比用户目标大得多：日志、网页、文件内容和中间 JSON 既占空间，又可能把真正的约束挤出模型注意力。

  • 超过模型上限时，请求直接失败。
  • 接近上限时，摘要必须在仍能容纳摘要请求的窗口内完成。
  • 删错一条工具调用或结果，会破坏下一轮的协议配对。

B为什么压缩要成为接口

把摘要逻辑散落在每个客户端，会造成不同 Agent 的状态格式、保留策略和重试行为不一致。对使用 OpenAI Responses API 形状的编码 Agent 来说，压缩触发器和压缩结果也需要能在多轮请求之间传递。

Ollama 的选择是接住这些控制项：普通 Responses 请求继续走原路径，只有出现压缩触发器或压缩项时，兼容层才介入。

判断边界：来源材料没有给出 v0.34.0 的官方压缩率、质量提升或延迟基准。因此本文只讨论已实现的协议、状态处理和工程影响，不把“能压缩”写成“压缩后一定更好”。

03 / Mechanism

核心原理：让模型写摘要，让服务端守住状态边界

Ollama 的实现把一次压缩拆成四个可检查的阶段。它并没有训练一个专用压缩模型，而是复用普通 Responses 推理栈，让当前请求中的模型生成摘要，再由 Go 代码校验摘要结构、保留项引用和工具状态。摘要与续接状态使用 JavaScript 对象表示法（JSON，JavaScript Object Notation）编码。

01 / TRIGGER检测控制项/v1/responses 的最后一项为 compaction_trigger，或客户端调用 /v1/responses/compact。
02 / PLAN整理轨迹把消息转成有序 transcript，并收集工具名称、描述和命名空间信息。
03 / SUMMARIZE生成摘要普通 Responses 请求被要求只调用一次严格的 create_summary。
04 / VALIDATE验证选择检查摘要非空、引用存在、无重复，并验证工具调用与结果成对。
05 / CONTINUE返回续接项返回 type=compaction，下一轮由 Ollama 展开其私有载荷。
POST /v1/responses/compact
{
  "model": "your-model",
  "input": [/* ordered conversation and tool items */]
}

response.output[0]
{
  "type": "compaction",
  "encrypted_content": "{ type, version, summary, retained }"
}

触发模式：主动请求与边界触发

独立端点用于客户端主动压缩；/v1/responses 末尾的 compaction_trigger 用于兼容会在轨迹中发出控制项的 Codex 客户端。源码要求该触发器只能是最后一项，且流式请求必须把 stream 设为 true。

如果普通请求没有触发器，responsesCompactionMiddleware 不改写请求。这个“只在控制项出现时介入”的边界降低了兼容层对已有调用的回归风险。

摘要模式：可选择保留原文

摘要请求要求模型保留目标、决策、约束、仓库状态、改动文件、测试结果、失败、当前工作和下一步动作；模型还必须给出不能安全改写的原始输入项引用。

这比“把所有历史压成一段文字”更稳健：摘要承担语义连续性，retained 承担不可丢失的原始证据。

一个容易被忽略的事实：线上的字段名仍然是 encrypted_content，但 Ollama 源码明确说明其中保存的是未加密、带版本号的 JSON。它是“对外表现为不透明续接项”，不是机密数据保护机制。

04 / What changed

真正的创新在哪里：把“上下文控制”放进可互操作的服务边界

01不是摘要提示词，而是状态协议

真正有工程价值的部分是 compaction_trigger、compaction 和 /v1/responses/compact 形成了可传输的生命周期。客户端不必知道 Ollama 内部如何组织摘要，只要在下一轮原样携带续接项，服务端就能恢复摘要与保留消息。

这使压缩从“某个 Agent 的私有技巧”变成可被客户端、代理网关和模型服务共同理解的接口能力。

02不是盲删，而是带工具配对的裁剪

源码为工具调用、工具结果和独立命名函数保留了结构检查。发生压缩请求本身超出模型上下文时，服务端最多执行一次上下文溢出重试，优先移除较旧轨迹，并把完整工具调用及结果作为整体处理。

摘要模型选中的保留项还要经过服务端校验：引用必须存在、不能重复，工具状态不允许凭空改写。

03同一条 Responses 兼容链路

压缩推理通过普通 Responses 处理链执行，而不是另起一套模型路由。这样本地模型与 Ollama 能访问到的其他模型路径可以共享请求形状、模型选择和错误处理。

代价是压缩会消耗一次正常模型调用，压缩质量和成本受当前模型、提示和输出预算影响。

04工具搜索与压缩互相补位

客户端工具搜索把工具目录检索留给调用方：声明 tool_search 后，客户端返回 tool_search_output，Ollama 将命名空间成员展平为模型可见的函数名。服务端明确拒绝 execution=server 的托管工具搜索。

因此它能减少“每轮都把全部工具 schema 塞进上下文”的浪费，但工具检索召回率仍由客户端目录和搜索实现负责。

来源事实以上四点对应 v0.34.0 Release diff 中的 openai/responses.go、openai/responses_compact.go、server/responses_compact.go 及测试。本文推断压缩和工具搜索的共同方向，是把上下文预算从 Agent 提示词问题提升为服务协议问题。

06 / Production

工程化视角：从 Demo 到生产要补上六个环节

“能返回一个 summary”只是 Demo。生产系统需要证明压缩后仍然能完成任务、遵守约束、正确调用工具，并且失败时不会把原始状态破坏掉。

定义触发和预算策略

不要等到模型返回“prompt too long”才第一次压缩。按模型上下文上限、工具定义 token、预计输出和安全余量设置水位；记录触发时的输入 token，而不是只记录请求总 token。压缩模型调用本身也要占预算。

把续接项当作状态数据保存

保存 type、版本号、摘要、保留消息、来源请求 ID、模型版本和时间戳。原样保存 encrypted_content 便于回放，但必须在存储和日志层做密钥、个人信息和工具结果脱敏，因为它并未加密。

对摘要和保留项做机器校验

沿用服务端的严格思路：摘要非空、引用存在且不重复，工具调用与结果成对，保留项顺序可恢复。下游只消费校验通过的压缩结果；失败时保留原始会话不变。

把工具搜索做成独立注册表

为工具建立稳定的命名空间、版本、权限标签和描述。评估搜索召回率、误召回率、schema 完整性和单次返回大小。tool_search 只能发现工具，不应绕过权限判断；真正执行前仍需服务端鉴权。

设计有限且可解释的失败路径

Ollama 对摘要格式错误允许一次修复重试，对上下文溢出允许一次裁剪后重试。接入方要把这些边界纳入状态机，超过上限后返回可恢复错误或转人工，不要无界重试。

建立压缩前后成对评测

同一任务跑“完整历史”和“触发压缩”两条轨迹，比较任务完成、约束保留、工具调用、事实引用、续跑成功率和人工复核结果。每次更换模型、摘要指令、工具注册表或 Ollama 版本都跑回归。

它会怎样影响现有大语言模型（LLM，Large Language Model）应用架构

CLIENTAgent loop决定何时触发、携带哪一份续接状态。
GATEWAYContext manager估算 token、脱敏、限流、路由和失败处理。

推荐接入顺序：先在离线黄金集上把“压缩前/后结果差异”跑通，再启用建议模式记录真实轨迹；之后只对低风险、可重试任务开启自动压缩，最后再扩到写入数据库、发起外部操作或带敏感数据的任务。

07 / Limits

局限与风险：压缩让上下文变小，也让错误更难察觉

高

没有官方质量和压缩率基准

Release 只说明功能和实现，没有给出任务集上的召回、延迟、成本或成功率。任何“节省了多少 token”的数字都必须由接入方自测。

高

摘要不可逆，保留策略依赖模型

摘要模型可能漏掉隐含约束。retained 能保留部分原文，但不能自动证明所有事实都被保留。关键约束应结构化存储，不要只放在自然语言历史里。

高

40% 目标尚未成为硬约束

源码的摘要请求实现明确标注，保留上下文目标比例还没有在模型渲染和 token 预算可用后强制执行。这意味着实际压缩比例由摘要结果和上下文边界共同决定。

中

私有载荷不是跨供应商格式

Ollama 的 ollama_compaction 载荷带版本号，只有 Ollama 兼容层能展开。迁移到 Anthropic 或其他 Responses 实现时，不能把它当作通用可移植会话格式。

高

工具搜索减少不了错误授权

客户端搜索只解决“把哪些工具放进上下文”。工具的权限、参数校验、审批和实际执行仍需独立的服务端安全边界。

中

压缩失败可能增加一次调用

摘要格式修复和上下文溢出裁剪都有重试路径。应把它们计入延迟和成本，并设置任务级预算，避免长任务在错误恢复中继续放大。

安全结论：压缩状态应按“包含工作历史和工具结果的敏感业务数据”处理；日志系统需要脱敏、访问控制和保留期限，不能因为字段名称里有 encrypted 就跳过这些措施。

08 / Outlook

未来方向：上下文管理会继续向三层分化

模型层：更可控的摘要与选择

可能出现面向状态摘要的专用模型、结构化记忆字段、可验证的保留理由和基于任务类型的摘要模板。本文推断，单一长摘要会逐步与“目标、约束、证据、工具状态、产物”分栏的结构化状态并存。

协议层：版本协商与可移植状态

当压缩成为 API 能力，客户端需要知道载荷由谁生成、版本是什么、能否跨模型或跨服务展开。未来协议可能加入能力发现、状态签名、加密封装和明确的过期策略。以上属于工程方向推断，不是 Ollama 已公布的路线图。

平台层：从 token 计费到状态计费

生产系统会同时优化输入 token、工具 schema、摘要调用、缓存命中、恢复调用和状态存储。工具搜索与压缩结合后，Agent 网关可能像数据库查询优化器一样，动态决定“检索哪些工具、保留哪些历史、何时压缩”。

评测层：从单轮正确到连续性正确

未来基准需要固定任务、工具、预算和中断点，专门测压缩前后的一致性、恢复质量与安全边界。单次回答正确不能代表长任务续跑正确。

09 / Takeaways

工程师可以借鉴什么

先把上下文看成有类型的状态

用户目标、不可违反的约束、工具调用、工具结果、文件快照和模型解释不应在系统里等价处理。压缩前先定义哪些字段必须保留。

把“模型记住了”改写为可验证契约

下一轮能否继续，应该由结构化检查、工具配对、产物存在性和任务回归集证明，而不是由摘要读起来是否流畅证明。

把上下文预算纳入架构评审

工具目录、检索结果、历史消息、推理块和压缩摘要共享同一预算。选择模型服务时，除了吞吐和价格，还要问它如何暴露上下文控制、失败和观测接口。

把兼容层当作边界，不当作安全系统

Ollama 可以帮 Agent 客户端接住协议，但权限、审批、脱敏、审计和外部副作用仍需要应用自己的控制面。

本文判断如果你的系统已经有长时间运行的工具型 Agent，Ollama 0.34.0 值得做灰度验证；如果只是短对话问答，压缩接口暂时不会改变主要架构。
