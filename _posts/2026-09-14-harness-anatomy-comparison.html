实现对比 · Harness 解剖

四个 Agent 运行时的解剖：同题，四种答案

Claude Code、Codex、DeepSeek Harness、OpenCode 都在干同一件事：让一个模型能在你的代码仓库里真正干活。这件事的核心是一个循环——调模型、执行工具、再调模型。四家从这个循环的第一步起就走了不同的路：派子 agent 时，有的复制上下文（fork），有的用线程，有的用子会话，有的用一张可替换的清单；拼系统提示词（prompt）时，有的在本地拼，有的从服务器下发，有的按模型发不同版本，有的干脆当成聊天记录里的一条消息。这篇用四家官方文档加一份 83 页的源码研究论文，把四种做法逐项对比清楚。

对比对象：四家 Harness Claude Code · Codex · DeepSeek Harness · OpenCode 主依据：arXiv 2609.00006（源码级研究） 差异最大的一章：多 agent 委派 抓取时间：2026-09
TL;DR

先说结论

如果你只记四件事：

15×
多 agent 的 token 放大倍数
源码研究的设计建议直说：用多个 agent 干活，token 消耗约是单 agent 的 15 倍；而大多数编码任务里，真正能同时进行的工作很少，这个钱花得不划算（arXiv 2609.00006，建议 12）。四家都做了委派机制，但克制程度完全不同。
4 层
Claude Code 的四层多 agent 机制
它同时有四种多 agent 机制：在单个会话里派活的 subagent；让你并行开多个会话、在一块面板里统一看进度的 agent view；多个会话组队协作的 agent teams；让模型自己写脚本来批量派活的 workflows。官方对其中三种给出了"谁持有计划"的对比表，是四家里最全的。
6 个
DeepSeek Harness 的子代理后端数
它派子 agent 走的是一张按名字注册的清单，清单里的后端可以整体替换：进程内派活（spawn）、进程内复制（fork）、外部协议（ACP）、独立 SDK——清单里还包括两个竞品：Codex 和 Claude Code 都能被它当子 agent 来调用（DSH 官方文档）。
0 个
400 万行代码里的两个零
研究者读了 11 个生产级 harness、约 400 万行 Python/TypeScript/Rust 源码，两个结论都是零：没有任何一个使用通用 agent 框架（LangChain、AutoGen、CrewAI……一个都没有），也没有任何一个用向量检索来读代码。
背景

Harness 是什么，这对比怎么读

H
Agent = 模型 + Harness。模型负责思考和做决定；harness 是模型之外的全部程序，负责把模型的每个决定真的执行下去。2026 年 7 月的源码研究《Harness Engineering》（arXiv 2609.00006，Wavestone AI Lab，83 页）给的定义是：harness 就是连接模型与真实世界的运行时，具体管六件事——调用模型的循环、工具、上下文管理、安全控制、多 agent 编排、扩展接口。本站前两篇解读了"怎么测 harness"（Harness-Bench、FrontierHarness 榜单），这一篇回答另一个问题：被测的这些东西，里面到底是什么。

D1 · Agent Loop

同一个循环，四种跑法

每个 harness 的核心都是同一个 while 循环：调模型、执行工具调用、再调模型。分歧从这么基础的地方就开始了。

Claude Code
流式输出 + 按风险决定能不能并行
模型的输出用 SSE 流式传输（一种边生成边发送的技术，不用等全部生成完）。它对"工具调用能不能同时执行"分得很细：每个工具默认标为 isConcurrencySafe = false——默认不许并发（宁可慢一点，安全优先）；只有显式声明安全的只读工具（grep/glob/read）才同时执行，写文件的操作一律一件一件来（论文 §6.2.2）。
Codex
用 Rust 写的异步状态机
Codex 是四家里唯一用 Rust 语言写的。轮次由 session 统一调度；多个工具调用可以同时执行，但结果严格按发起的顺序依次交付（用 Rust 的 FuturesOrdered 机制）；工具执行部分的代码被单独抽成了一个独立模块（crate，Rust 的包单位）（论文 §6.2.3）。Rust 语言在编译阶段就会强制检查错误处理，所以它的错误恢复策略在程序构建时就被锁死，运行时绕不过去。
OpenCode
日志就是任务清单
循环就是一个写死的 while(true)（无限循环）。特别之处：消息日志同时当任务清单用——要做的子 agent 生成、上下文压缩，不写死在代码流程里，而是作为一条条消息存进日志；循环每一轮从日志里取一件活来干。好处是待办事项本身就存在日志里，程序重启后照样接着干。没有默认的步数上限；同一个工具调用连续三次一模一样时，会停下来问用户"是不是卡死了"（doom-loop 询问）；上下文快满时从不重试，直接转压缩（论文 §6.2.9）。
DeepSeek Harness
循环本身是个插件
官方架构文档明说：连 agent loop 本身都只是一个插件（实现 Agent 接口的默认驱动器），可以改配置把它换掉。每一轮的流程是：先过一串前置检查（pre-step waterfall，每个检查点都能拒绝或改写输入），然后拼 prompt、从日志整理出一份固定不变的模型历史再发请求；任何阶段的取消操作都不写日志（DSH 文档 reference/index）。

一个有用的读法：OpenCode 和 DSH 把"可恢复"当作头等目标（一切以日志为中心，DSH 甚至把它定成运行时硬规则，见 D4 节），Claude Code 和 Codex 把"流式性能"当作头等目标。这不是谁对谁错，是两种使用场景下的取舍。

第一层：单个子 agent 怎么建

Claude Code：复制出去干活，缓存照常能用
subagent（子代理）用 markdown 文件加 YAML 开头定义（项目 .claude/agents/ 或用户 ~/.claude/agents/），每个定义写明五样东西：自己的上下文窗口、自己的 system prompt、能用哪些工具、自己的权限模式、用哪个模型。官方明说可以把杂活派给 Haiku 这类便宜模型。三个硬细节：① 所有 subagent 的描述加起来超过 15,000 token，启动时会告警；② 派生（spawn）子代理的本质，是复制一份上下文（context fork）。论文数出 6 个维度的复制内容：中断控制、文件状态缓存、权限提示、拒绝追踪等。最关键的优化在 system prompt：fork 时把父代理已渲染好的 system prompt 逐字冻结、原样传给子代理——这样子代理发请求时，开头部分和父代理完全一样，能命中父代理已建立的缓存前缀（相同开头不用重新计算，省钱省时间；论文 Table 4 给它的标签是"prompt-cache-sharing forks"，意思是"共享 prompt 缓存的复制"，并说其他系统只是在照抄它这个参考做法）；③ 定义里可以加 isolation: worktree，让子代理在一个临时复制的 git 工作树里干活（改坏了也不污染主目录）。官方文档还支持前台/后台两种派生方式，以及按名字恢复（resume）一个子代理。
Codex：每个子代理就是一条线程
Codex 派子代理的基本构件是 agent thread（代理线程）：每个 subagent 有自己的线程，用户可用 /agent 命令随时切进某个线程查看（官方文档 subagents 页）。源码研究拆出三件套：中央的 AgentControl（统一管理派生）、AgentRegistry（登记全部存活 agent 的信息）、带 fork 模式的派生流程。SpawnAgentForkMode 决定子代理继承多少历史——全部，或只拿最近 N 轮；继承时会过滤消息：只保留 system/developer/user 和最终答案，中间的工具调用和推理过程全部剔除，防止上下文膨胀。代理之间通信用类型化的 InterAgentCommunication 记录（Spawn/Message/Followup/Result 四种）。工具本身有两代（multi_agents 与 multi_agents_v2），按模型元数据选该用哪一代。子代理的角色可以用 TOML 文件声明（explorer/worker）——论文称之为"Codex 对 Claude Code agent definitions 的回答"（官方文档 + 论文 §11.3）。
OpenCode：子代理就是一个子会话
OpenCode 的 subagent 不是独立引擎，就是一个带 parentID 的子会话（child session），和主代理跑同一个循环（论文 §11.9）。结果用 <task_result> XML 包一层返回，后台完成的结果作为一条合成的 user 消息注入对话。两个反差极大的细节：① 权限继承不对称——子代理只继承父代理的拒绝（deny）规则，允许（allow）规则不继承；② 递归派生默认关闭（子代理再调 task 工具会被自动拒绝），在 agent 定义里显式开启后没有层数上限。还有四家独一份的功能：让 LLM 现场生成 agent 定义（用结构化输出生成 identifier / whenToUse / systemPrompt），不写配置文件就能"变出"一个子代理。官方文档侧：内置 subagent 有 General、Explore、Scout 等，可用 @ 提及显式点名，也会按描述自动匹配。
DeepSeek Harness：委派是一张清单，后端随便换
DSH 的 subagent 是一个可选能力 seam。seam 是 DSH 的架构术语，意思是"可替换的能力槽位"：一个能力只声明接口，实现单独提供，运行时可以整体换掉，所以它不属于 agent loop 的主干。实现方式是一张按名字注册的提供方清单，同一个上下文里可以同时存在多个后端（DSH 文档 subsystems/subagent）。官方列出六个提供方：进程内 spawn（新起一个、不继承上下文）、进程内 fork（拿父日志里已完成轮次的一段稳定前缀当起点）、ACP（进程外）、codex 后端、claude-code 后端（把两个竞品当子代理，通过 subprocess 启动）、独立 dsh SDK 运行时。子代理分两类：one-shot（一次性前台调用，返回一个结果）与 continuable（持久子 Session + 至多一个进程内激活，可跑多轮、可冷恢复）。消息只允许直接父子之间传递，兄弟、隔代、自己调自己一律拒绝。请求可以带 outputSchema（强制输出符合指定的 JSON 结构）、maxDepth（派生深度上限）、toolFilter（过滤子代理能看见哪些工具——文档强调这是"控制可见性"而不是"控制权限"：被过滤的工具从 prompt 里消失，调了也会被拒绝执行）。能力不匹配的请求返回 UNSUPPORTED_CAPABILITY，原则是宁可大声报错、绝不静默降级。

第二层：编排——"谁持有计划"的四种回答

单次委派之上，谁去编排几十个 agent？四家给出了四个方向不同的回答：

Claude Code：模型写 JavaScript
Workflows 机制：Claude 写一段 JS 脚本（agent()、parallel()、pipeline()、phase()、log()），运行时在后台执行这段脚本，主会话保持响应。硬上限：16 个并发、单次运行 1000 个 agent、单条 pipeline 4096 项。最精妙的是批量并行时的缓存处理：第一个 agent 先启动，把 prompt 缓存前缀建立起来，其余 agent 间隔 5 秒错峰启动，直接复用这份缓存——等于把"prompt 缓存"写进了编排规则本身。脚本可以保存成斜杠命令反复使用、中途可恢复（官方文档 workflows 页）。
DeepSeek Harness：同款结构，官方文档承认保持一致
DSH 的 workflow 工具让模型运行"会启动 subagent 的编排脚本"：script（一段纯 JS 函数体）、meta、args。脚本引擎跑在独立的 worker 线程和隔离沙箱里（node:worker_threads 的 vm 上下文），提供 parallel()/pipeline() 两个组合函数和 maxTotalAgents 总量上限。两个特色：meta 块的字段命名，官方文档注明与 Claude Code 动态工作流的 meta 块保持一致；失败纪律是"拼错的选项必须直接报错（fatal），绝不静默降级成普通失败"（DSH 文档 subsystems/workflow）。另有内置的 ralph 工具（固定在前台跑的工作流，每轮启动一个全新的结构化子级，即 Ralph 循环模式）。
Codex：不写脚本，写数据
Codex 的答案不是让模型自由写编排脚本，而是按数据批量派活：spawn_agents_on_csv 工具对 CSV 的每一行生成一个子代理，全部共享同一个 JSON Schema 结果契约（结果必须符合规定格式），带并发上限，跑完的结果自动收回来（论文 §11.3）。派子代理这件事本身也受模型管控：新的 ultra 推理档在模型目录里的描述是"maximum reasoning with automatic sub-agent task delegation"（最高强度推理、自动把任务派给子 agent）——论文指出，这是研究的全部系统里唯一会改变编排行为的推理档；本地 Codex 文档则说明触发条件是用户直接要求，或 AGENTS.md / skill 指令请求。
OpenCode：不给编排层
OpenCode 的多 agent 全部 = task 工具 + child session 树 + 快捷键导航（child_first/child_cycle/parent 在会话树里移动）。没有 workflow 引擎、没有常驻团队、没有批量并行派活的机制。这是设计选择而不是缺东西没做——它的定位是轻量中立的客户端，把重编排留给上层。

第三层：团队——lead、teammates 与任务板

"Agent team"是用户最容易感知的一层。四家的现状：

Claude Code Agent Teams：机制最完整，但官方自己先泼冷水
  1. 结构：一个 lead 会话（就是你正在对话的这个）派出多个 teammates，每个 teammate 是一个完全独立的 Claude Code 会话——各自加载自己的 CLAUDE.md、MCP 和 skills，但不继承 lead 的对话历史。四件套：lead、teammates、共享任务列表、mailbox（信箱，其实是磁盘上的 JSON 文件：~/.claude/teams/{team-name}/inboxes/{agent-name}.json）。
  2. 任务板：每个任务有三种状态（pending 待办 / in progress 进行中 / completed 完成）+ 依赖关系；lead 做完被依赖的任务后，下游任务自动解锁；多个 agent 抢同一个任务时，用文件锁防止冲突。
  3. 权限纪律：teammate 继承 lead 的权限模式（dontAsk 模式除外）；teammate 的权限提示会上抛给 lead，由你来批；teammate 不能替另一个 teammate 批权限，被拒的动作也不能借别的 teammate 中转绕过检查。
  4. 质量门：TeammateIdle / TaskCreated / TaskCompleted 三个 hook（事件钩子）可以拦截动作并给反馈（返回 exit code 2 即拦截）。
  5. 硬限制（官方 Limitations 节）：实验性、默认关闭（要设 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 才能开）；团队里不能再嵌套团队；一个会话只能有一个团队；lead 固定、不可转移；进程内的 teammate 不能再开后台 subagent；用 /resume 恢复会话时不恢复 teammates。
  6. 官方定位：启用前先问"更轻的选项够不够"——subagent 在单个会话内就能干，cross-session messaging 能在你自己开的多个会话之间互传消息。
code.claude.com/docs/en/agent-teams（v2.1.178 起免 setup 步骤；细节大量随小版本变动，读原文为准）。
DeepSeek Harness 的团队层
同样标实验、默认禁用（dsh-base 里关着，官方提供 profile patch 启用）。工具面 9 个：spawn_teammate、send_message、wait_agent、interrupt_agent、list_agents，加 team_task_* 一组 4 个。两个更精细的设计：任务板更新用 compare-and-swap（每次修改版本号递增，防止并发互相覆盖）；blockedBy 字段维护任务依赖（谁被谁挡着）。另外每个任务的 writeScopes 只是"建议写到这些路径"，官方文档直接注明"不是锁"（DSH 文档 subsystems/agent-team）。
Codex 与 OpenCode：用别的机制替代团队
Codex 没有常驻团队，它的"多个实例并行干活"答案是做成了产品功能的 git worktrees（每个 chat 可以跑在一个独立复制的仓库目录里，存放在 $CODEX_HOME/worktrees，各自停在自己的提交点上，默认保留 15 个），Handoff 命令把 chat 在本地目录与 worktree 之间来回搬（官方文档 git-worktrees 页）。OpenCode 的答案是用户自己多开几个会话。两家都把"协调"这件事留给人来做。

第三层半：不开实验开关的轻量并行

顺带补齐 Claude Code 这套机制里不需要任何实验开关的两个机制：agent view 让你自己并行开多个 Claude Code 会话，在一块面板里查看全部会话的状态、收割结果；cross-session messaging 让你自己开的多个会话之间互传消息。官方把这两个机制列在 agent teams 之前，作为启用团队前"先看看更轻的选项够不够"的推荐路径——它们的定位是由人来驱动并行，而不是 agent 自动协调。

第四层：成本与模型路由

多 agent 的花费问题，四家的态度差异极大：

Claude Code
把"缓存省钱"贯穿到派子代理这件事上：fork 时冻结 system prompt 保缓存命中；官方文档明确 subagent 可以派给 Haiku 省钱；进程内 teammate 的请求有独立的缓存过期计时（TTL 默认 5 分钟，可用 subagentPromptCacheTtl 调到 1 小时，代价是缓存写入价更贵）。官方 agent teams 页多处明确警告"token 显著更多"。
Codex
模型选择是产品功能的一部分：内置 subagent 按活选模型（worker 干执行、explorer 干只读探索）；多代理工具按模型选代；派多少子代理由推理档管着（ultra 档 = 自动委派）。
OpenCode
官方文档：subagent 默认沿用调用它的主代理的模型。没有"派给便宜模型"的选项——省 token 的方式就是少派。
DeepSeek Harness
每次派子代理都可以临时改配置：提供方、模型、推理强度、token 上限都能按单个请求覆盖（agentOptions），还提供 list_subagent_models 工具列出有哪些模型可用。灵活性四家最高。
多 agent 的冷静提醒

源码研究的设计建议 12 值得抄录：保持单 agent，除非你能指出一段具体的、适合同时铺开干的工作，并且确认并行的收益真的大过它的代价——因为多 agent 约多耗 15 倍 token（论文特意注明：这个 15 倍是跟单次对话比的，不是跟优化过的单 agent 比的），而且大多数编码任务里真正能同时干的部分，比调研类任务少得多。研究同时发现，"一个主控带一群工人"（coordinator-worker）的结构在多家独立出现（观察 7）——说明这个结构有用，但四家优化的方向各不相同：Claude Code 优化成本，Codex 优化隔离与规模。先判断你的场景里有没有真正能同时干的部分，比选哪家 harness 更重要。

第五层：跨 harness 委派——最出人意料的一步

回到上面全景表最后一行。DSH 的六个后端里有两个是竞品（dsh-subagent-codex 与 dsh-subagent-claude-code），这个设计决策有专门的设计记录（仓库 .agents/notes/ 内 2026-08-04 的 Agent Note）。这件事的意义是：派活这一层一旦设计对了，能调动的就不只是模型，还有别家 harness 的整套能力——DSH 用户可以在一个会话里把一个任务派给 Codex、把另一个任务派给 Claude Code，它们各自带着自己家的工具和 prompt 来干活。

协议层的背景同样重要。论文观察到 ACP（Agent Client Protocol，一个标准通信协议）已进入 6/11 个系统，还出现了设计者没预料到的第二种用途：用它来托管其他 harness（harness hosting）——OpenHands 通过 ACP 把 Claude Code、Codex、Gemini CLI 当作可互换的"大脑"接进自己的对话（论文的原话：为编辑器设计的协议，最后成了托管用的接口）。但同时，9 个有多 agent 能力的系统里，8 个的自家 subagent 仍是进程内实现（在同一个程序里直接调用）；跨进程的也绕开标准协议（Pi 用私有的 JSONL 格式，Hermes 用 SQLite 做共享存储）；唯一把子代理协调走标准协议的是 OpenClaw。论文给出的工程指导是：对外发布 ACP server（一次就能服务 IDE、宿主程序、上层编排器三类调用方），对内 subagent 保持进程内——派子代理这件事的竞争力，在 fork 隔离、缓存共享、权限上抛这些进程内细节，不在协议（§13.3）。

D2 · Prompt 动态组装

四种做法，一个问题：请求里哪些部分保持不变

prompt 组装表面上是拼字符串，实际是在回答一个工程问题：每次发请求，哪些部分保持不变（不变的部分能命中缓存、省 token），哪些部分必须每轮都变。四家的答案完全是四条路。

Claude Code：静态/动态边界
system prompt 由 12–15 个命名 section 组成，用 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 标记一分为二：边界之前（身份、系统规则、任务指引、工具模式、语气）是静态区——这部分内容不变，做 Blake2b 哈希（算个指纹，指纹没变就直接复用），缓存跨会话生效；边界之后（会话指引、memory、环境、MCP 指令、语言、scratchpad）是动态区——按轮重新计算，但算过的结果会记住（memoize），不用重复算（论文 §7.2.3）。配合 fork 冻结继承，这套缓存边界设计贯穿它的所有功能。
Codex：prompt 是服务端数据
Codex 走得最远：prompt 不写在代码里。真正生效的 prompt 存在模型清单文件里（models.json：本地有兜底、主要从服务器的 /models 接口拉取、用 ETag 做缓存版本标记），就是其中的 base_instructions 字段，按模型代际下发，还带 {{ personality }} 模板变量。论文发现这些 prompt 在随模型换代悄悄变化：GPT-5.2 的开头是"You are GPT-5.2 running in the Codex CLI…"，GPT-5.5 缩为"You are Codex, a coding agent based on GPT-5…"，5.6 再缩为"You are Codex, an agent based on GPT-5"，并且删掉了 no-commit 规则和全部防止过度设计的指令——原来写在 prompt 里的行为策略，改成了 codex_git_commit 这类功能开关（feature flag，改配置就能开关的行为）（论文 §7.2.4）。
OpenCode：按模型家族发九份 prompt
OpenCode 按模型家族发 9 份 base prompt（按 model-id 子串匹配）——给 Claude 系模型的开头是"You are OpenCode, the best coding agent on the planet."。system prompt 刻意压到最多两条消息，以匹配缓存的计费槽位；同时针对 6 种提供方，把同一份缓存标记按各家的格式各包一次发出去（cache-dialect fanout）。底层用的是 Vercel AI SDK（现成的第三方模型接口库）——论文注明，这是研究的全部系统里唯一底层用第三方 SDK 的；它自己也写了一套替代品，藏在 flag 后面随时可切换（论文 §7.2.8）。
DeepSeek Harness：prompt 是历史里的一条消息
DSH 的 prompt 组装分四类注册：section（静态或动态文本）、context（运行时上下文）、tools provider（每次组装时评估哪些工具对模型可见）、variable。最独特的设计（有 2026-09-02 的设计记录）：系统提示词不放在请求参数里，而是作为聊天历史里的一条消息发给模型——第一步追加为第 0 号节点，文本变化时就地替换这条消息，前面的缓存不用重算（对缓存前缀友好），而且完全可以从日志重建（DSH 文档 subsystems/system-prompt）。

AGENTS.md：四家全吃的指令文件

prompt 组装里有一块事实标准已经统一：项目指令文件。四家怎么读它：

Harness指令文件机制
Codex原生主场：全局（~/.codex，AGENTS.override.md 优先）→ 从项目根到当前目录逐层拼接（每层最多一个文件，越靠近的越后加载、后加载的覆盖前面的），总量默认上限 32 KiB，支持多个候选文件名，每次启动重新读取、不缓存（官方文档 agents-md 页）
Claude CodeCLAUDE.md 三层 scope（managed/user/project）去重注入 + 自动记忆目录（官方 overview；论文 §9.7 的 claudemd/memdir 子系统）
OpenCode同时认 AGENTS.md / CLAUDE.md / CONTEXT.md；从当前目录向上逐级找，同层只认第一个命中的文件名；嵌套的 AGENTS.md 等到 read 工具碰到它的子目录才加载（懒加载）（论文 §9.7）
DeepSeek HarnessAGENTS.md 与 CLAUDE.md 两个都认（DSH 仓库自己根目录的 CLAUDE.md 就是 AGENTS.md 的一个链接）；指令以一条持久的 user 消息进入会话历史，模型的 write/edit 碰到相关路径后自动重新读取刷新（DSH 文档 + 仓库 packages/context/README）
这一节几乎每行都能看到"直接采用竞品格式"的痕迹——后面插件生态一节展开。
D3 · 工具系统

Function calling：工具数量、加载与改文件的方式

工具系统是 harness 与模型之间的接口。拆成三个子问题：给模型看多少工具、怎么给、怎么改文件。

工具面有多大
Claude Code：43 个带类型定义的工具（论文按 3 月快照统计）。Codex：25–30 个（论文）。OpenCode：官方文档列 13 个内置（bash/edit/write/read/grep/glob/lsp/apply_patch/skill/todowrite/webfetch/websearch/question——lsp 要开实验开关，另有 task 委派和 3 个隐藏系统 agent；论文按第一方工具的统计标准计 17 个）。DSH：默认启用约 30 余个（另有选择启用的 terminal、会话查询、agent-team、cordis 七件套等）；工具目录不是手写的文档，而是脚本把每个工具插件真实启动一遍、读它的结构定义（schema）自动生成的，CI 保证文档不缺。
按需加载
工具多了，prompt 就装不下。Claude Code 是 延迟加载（deferred loading）的发明者：标记 shouldDefer 的工具不放进初始 prompt，模型用一个"搜工具"的工具按需找它们，初始 prompt 约缩 40%；Codex 在互不知情的情况下独立做出了同款（用 BM25 关键词打分算法驱动的 tool_search）——论文拿它当"竞争特色只能领先几周"的证据（观察 + §14.5）。OpenCode 13 个工具，不需要；DSH 用 tools provider 每次组装时评估，并区分"拼写错误"与"有意隐藏"两种情况。
并发怎么切
Claude Code：isConcurrencySafe 默认 false——默认不并发（宁可慢、要安全），显式声明安全才并行。DSH：只有精确等于 true 才进并行组，其余排成先后顺序（exclusive）。两家不同的代码库给出的答案几乎逐字相同——互不知情，各自得出。
OpenCode 的按模型换面板
OpenCode 会按模型家族换工具集：GPT 系模型拿到 Codex 式的 apply_patch 工具，同时完全失去字符串替换编辑工具（论文 §8.3）——给哪个模型，就配哪套工具。

编辑契约：决定 SWE agent 改文件准确率的关键

论文把"怎么改文件"列为"决定 SWE agent 修改准确率的最重要因素之一"（观察 4）。四家的做法：

Harness编辑契约失败兜底
Claude Code精确唯一子串替换（找到唯一匹配的那段原文，替换它）+ Zod 结构校验失败时把相关上下文带回给模型重试
Codex自定义的补丁格式：用 Begin/End Patch 标记包裹修改，由 Lark 文法（一种语法解析工具）在应用前校验格式按补丁块（hunk）逐块重试
OpenCode按模型切换：字符串替换或 apply_patch；匹配失败时走 9 级逐步放宽的回退（先试精确匹配，一路放宽到忽略空白、模糊匹配，模糊度用编辑距离 Levenshtein 0.65 衡量），源码注释致谢 Cline 与 Gemini CLI区分"没找到"与"多处匹配"两种错误；每次编辑后附上 LSP 诊断（LSP 是代码分析服务，OpenCode 会自动下载约 25 个 LSP server）

四家的"独门工具"

  • Codex：code mode——模型直接写 V8 脚本，对 MCP 工具目录编程执行，论文的评价是"把工具调用变成可执行的代码"。

  • DSH：两个方向都激进——对内，PTC 模式的 run_code（模型写一段 TypeScript 函数体来串起其他工具调用；函数体里发起的每个子调用都会重新过一遍完整的权限检查流程；上篇榜单里 DSH 的 PTC 预设，在工具目录里的对应物就是它）；对外，cordis define、inspect×3、run、stop、undefine 七件套让模型在会话内动态定义、加载、热换、卸载插件，动态包还能注册新的模型可见工具（需要审批，跑在 vm 沙箱里）——"改自己"是它的产品能力。调用了不存在的工具会返回结构化错误（UNKNOWN_TOOL）且不终止本轮。
D4 · 记忆与上下文

上下文压缩：会话内的，和跨会话的

上下文快满时怎么办、跨会话记什么，是 2026 年上下文工程的两个核心问题。论文的判断：上下文压缩各家做法已经趋同；真正分出高下的，是记忆怎么写入（观察 5）。

Harness触发摘要策略独有细节
Claude Code窗口剩 13,000 token 缓冲时就触发先把图片剥掉 → 按对话轮次分组 → LLM 生成摘要 → 用 SystemCompactBoundary 标记分隔压缩后留 50,000 token 恢复预算（最多重读 5 个文件）；每个 skill 的内容截到 25K（论文 §9.5）
Codextoken 用量到上限就触发（本地端点上报的额度 + model_auto_compact_token_limit 配置，两路信号）摘要压缩有任务总 token 预算（rollout token budget，rollout 指一次任务运行的全过程记录）：余量会提醒，用完就中止——预算是硬约束（论文 §9.5/9.6）
OpenCode整个代码树没引入 tokenizer（精确切词计数的工具），干脆用字符数÷4 估算 token；输入额度减掉预留的输出额度就触发增量合并：把上一份摘要装进 previous-summary 块，交给一个隐藏的、所有工具都被禁用的压缩 agent 去合并——保留仍然成立的内容、删除已过时的，输出固定为五段式 Markdown保留最近 2 条用户消息原文；剪枝只在可回收 >20K 且保护最近 40K 时触发；每个项目另建一个影子 git 仓库（shadow git）逐步打快照，支持"会话 + 文件系统"整体回滚（论文 §9.5）
DeepSeek Harness四个触发入口：压力大时自动（每步前检查）、上下文溢出恢复时、空闲时手动、用户显式指定范围先剪枝后摘要：先按字符数（Unicode 码点）对超预算的工具结果掐头/留中/留尾剪掉，并写一条记账事件（其他组件看到这条事件就能扣掉对应的 token 数，不用维护全局状态），然后再摘要压缩是可选接缝，不属于循环主干；压缩只做一种改动：把摘要替换进上下文（replace）；替换区域边界保持工具调用/结果配对；超长内容转存到磁盘（spill），只返回一个不含内容本身的引用句柄（目录权限 0700、独占写、防符号链接）
论文 §9.5（触发参数、OpenCode 增量摘要、shadow git）；DSH 文档 subsystems/compaction、subsystems/spill。

真正的分水岭：记忆由谁维护

M
Codex 是研究的全部系统里第一个"长期记忆由 agent 而非代码维护"的系统（论文 §9.6 原话："the first system in the corpus whose long-term memory is maintained by an agent rather than by code"）。它的记忆系统在后台分两步跑：第一步，把每次任务记录（rollout）的内容用 LLM 提炼后存进 SQLite（后台任务带租约防止重复执行、失败重试有退避、写入前先把密钥脱敏）；第二步，由一个沙箱化的内部 subagent（不能审批、不能联网、只允许本地写文件）审阅工作区的改动（diff），把值得记的内容整合进 ~/.codex/memories/ 目录（由 git 管理版本）。新开会话时把记忆注入上下文，带引用来源追踪，并按使用频率排序。

其余三家对记忆的处理：Claude Code 是 CLAUDE.md 三层位置（managed/user/project）去重注入 + 自动记忆目录（写什么靠约定来管）；OpenCode 干脆没有独立的持久记忆系统——它的持久化就是会话系统本身（可恢复、可查询），加上 AGENTS.md 这类上下文文件约定；DSH 的方向是"会话引用"——在对话里提及另一个会话，那个会话的一份限定大小的只读快照就成为上下文，另有记忆 MCP 插件。论文观察到四种"记忆由谁写、怎么管"的模式正在分化：agent 维护（Codex）、人类审批（Gemini CLI 的 patch inbox）、模型直接写但有限制（Hermes 的字符上限快照；OpenHands、Claude Code 的上下文文件约定）、每回合前主动召回（OpenClaw）——并且 11 家没有一个用向量语义检索（embedding）当记忆的主存储，生产实现里最重的也只是 SQLite 全文检索（观察 5）。

DSH 的运行时硬规则："模型看得见的，日志里一定有"

DSH 把上下文工程变成了一条机器可以检查的硬规则（不变量）：凡是发给模型的内容，都必须能从会话日志重建出来（模型看得见 ⟺ 日志里有），运行时负责强制检查。日志只追加、不修改；日志格式升级换代时按代迁移（每升一代 vN→vN+1 配一个迁移脚本，已写入的日志绝不回头重写），配 SQLite 全文检索和查询结果缓存。压缩、fork、会话引用全部建立在这一层之上——这是把 OpenCode 的"日志本身就是任务清单"做到了极致。

D5 · 安全与权限

权限与沙箱：四种安全观

安全是各家投入差距最大的子系统——论文观察 6 的结论：造操作系统级沙箱是研究里代码成本最高的能力之一，而且要不要它纯属设计选择、跟系统规模无关（规模最大的 OpenCode 反而没有沙箱）。

Claude CodeCodexOpenCodeDeepSeek Harness
审批链三层：静态 hook 规则（最快）→ LLM 权限分类器（判断该允许、该问用户还是该拒绝）→ 用户对话框（最可靠）四层：Starlark 写的策略规则（Starlark 是一种小语言）→ 生命周期 hooks → Guardian 审批 agent → 操作系统级沙箱默认极少询问：项目内全放行，只对外部目录访问、.env 读取、疑似死循环时询问工具流水线里的 ask 检查环节 + fail-closed 审批（拿不到明确批准就当拒绝；结果只有固定的几种，程序异常也一律按拒绝）
命令粒度hook 在工具使用前（PreToolUse）做模式匹配前缀规则（prefix_rule）/ 联网规则（network_rule），每条规则可以自带测试样例——加载策略文件时先跑一遍，验证规则写对了没（论文原话："策略文件里的可执行测试用例"）懂语法：每条 bash 命令用 tree-sitter 解析成语法树再判断，"总是允许"的规则按参数个数限定——产出的是只授权 git commit * 这一种形式的规则，而不是整类命令全放行被调用的工具交出精确的参数列表（argv），沙箱包装后返回一个受限版命令；被拒时各后端报各自的错误码（bwrap 报 EROFS、Landlock 报 EACCES、Seatbelt 报 EPERM）
OS 沙箱可选开启（沙箱运行时 + worktree）三个平台都自带：Linux 用自带的 Bubblewrap（文件系统只读 + 断网）、macOS 用 Seatbelt、Windows 用受限令牌 + ACL没有（代码里名叫"sandbox"的模块实际是 git worktrees，不是安全沙箱）三个平台都留了接缝：后端清单和 Codex 同款（bwrap/Landlock、Seatbelt、Windows ACL 受限令牌），缺后端就报错——原则是"受限策略下绝不静默放行"
哲学一句话纵深防御：快的层糙一点、慢的层准一点策略写成代码，审批也交给 agent（Guardian 超时或输出格式不对就一律拒绝，带拒绝熔断）默认信任 + 用语法分析换取更细的授权粒度（v2 已反转成默认拒绝）一切按 fail-closed 处理（拿不到批准就当拒绝）；凭据只存引用、界面只显示脱敏后的名字；SAFETY.md 明说：未经安全审计、不算生产就绪，也不能当作不可信任务的唯一安全防线
论文 §10（CC 三层、Codex 四层、OpenCode 语法分析与参数个数（arity）字典——约 130 条由 LLM 生成的命令参数元数据字典、last-match-wins 规则链）；DSH 文档 subsystems/sandbox、subsystems/approval、SAFETY.md。
最优雅 vs 最重
论文称 Claude Code 的三层是"架构上最优雅的安全系统"；同时点出关键限制：后台运行/派生出去的 subagent 只走前两层，它们的权限提示一律按拒绝处理，拿不准的情形上报回父代理。每个并行 agent 各自维护独立的拒绝状态，防止一个 agent 的拒绝影响另一个。
OpenCode 的"工具可见性即权限"
OpenCode 对某个工具 deny "*" 的效果，不是拦截调用，而是把这个工具从模型能看到的列表里整个删掉——看不见，就等于不可用（论文 §10.9）。配合论文的另一个发现：plan mode（计划模式）只是一组权限规则加一条 system-reminder 提示，不是架构上的独立层（§11.9）——它的权限系统管的是"能看见什么"，不是"关在哪儿"。

四家的扩展哲学

Claude Code
hooks 是它的主要扩展面（4 月时还只有它有）；另有 skills、agent 定义、MCP。它做出来的东西（hook 事件名、.claude-plugin 插件格式）成了行业事实标准——"被模仿的参考系"就是这个意思。
Codex
有插件市场（来源支持 GitHub/git/URL，模型可以自己发起安装请求、在会话内走审批）；能自动识别并触发 skills；配置体系一直管到 MDM/企业托管（企业远程管设备的机制）——论文称它是"研究里最偏企业治理的配置模型"。
OpenCode
插件约等于"在约 20 个类型化的 hook 点上挂异步函数"，按固定顺序执行保证结果稳定；加自定义工具不需要插件——在 .opencode/tool/*.ts 里随便导出一个函数就算；另外能作为 ACP server 跑（opencode acp）。
DeepSeek Harness
扩展对它不是附加机制，是根本组织方式：一切皆插件（连 agent loop、system prompt 组装器都是）；Cordis 保证"注册即生效、卸载即全部撤销"；一个运行实例是 profile → bundle → patch 一层层叠出来的插件树，树上任何条目都能用自己的 patch 换掉（dump-config 可以打印整棵树）。连它的桌面应用（Electron）都不开网络端口，用 dsh-app:// 协议通信。
横向发现

两个零、一次从工具到平台的转变

Twin Absences：400 万行代码里的两个反直觉的零

论文最常被引用的发现（§13.2）：研究者把 11 个系统的依赖清单全部查了一遍，又在全部源码里全文搜索这些 agent 框架的名字——LangChain、LangGraph、LlamaIndex、AutoGen、CrewAI、Pydantic AI、Genkit、Haystack、Semantic Kernel、Google ADK、Smolagents、Swarm、Agno——一个都没搜到。几个注脚值得单独说：

连自家的都不用
Gemini CLI 不用 Google 自家的 Genkit 和 ADK。作者写明：他们本来预期至少能找到几个，还专门找过反例（把依赖复制进仓库、运行时动态加载、转译产物这些隐蔽形式），花了几周才接受"真的是零"。
两个"差点算"的例外
Hermes 源码里仅有的 "LangChain" 字样出现在打包 skill 的文档里（教用户怎么用向量库）；OpenCode 用的 Vercel AI SDK 是模型接口层、不是编排框架——所以它是唯一底层用第三方 SDK 的系统，而且自己另写了一套替代品藏在 flag 后面。
第二个零：代码不用向量检索
读代码这件事上，11 个系统里"向量库/embedding"关键词全部零命中。替代方案：ripgrep（快速文本搜索）、glob（按文件名模式找文件）、tree-sitter（语法解析）、LSP（代码分析服务）。唯一默认开 embedding 的是 OpenClaw 的记忆插件——而且只用于找回聊天记录，从不用于读代码；Hermes 反着选：会话检索刻意用普通文本搜索（SQLite FTS5），全程不用 LLM。
为什么
论文给的三条：代码自带大量确定性的结构信息（路径、LSP、类型），向量相似度算不出这些；代码分钟级变化，预先建好的索引很快过期；每个编码环境都自带几乎够用的检索工具（ripgrep/find）。结论句：生产 harness 能容纳的复杂度，和普通 LLM 应用根本不在一个量级。

从工具到平台：竞争单位变了

论文的主线论点：2026 上半年，coding harness 完成了从工具到平台的转向。证据到处都是：每家都发了 SDK（Claude Agent SDK、Codex SDK、OpenCode SDK——前三者见论文 §14.2；DSH 甚至有 Python SDK，打包原生运行时 wheel，普通运行连系统 Node.js 都不需要，DSH 文档）；插件市场与企业托管配置（MDM）齐备；出现了 Omnigent 这样的"编排器"（meta-harness）——它从上层调度 11 家厂商的 harness，自己一行编辑循环都不写；甚至有系统冒充某第一方 harness 的身份，去用它的订阅后端（论文列的 Harness Mimicry 模式）。结论句值得原样抄录：这个领域的竞争单位已经不再是 agent 循环本身，而是它周围的生态对接面。

下限有多低：90 行的最小可行 harness

论文附了一个约 90 行 Python 的最小可行 harness（minimum-viable-harness，§16.10）：一个 Model 接口、四个工具（bash/read/write/search_replace，替换时校验唯一性）、从根目录到当前目录逐层找 AGENTS.md、到阈值就压缩（保留最后 30% 原文）、成本与步数上限。它直接实现了 18 条设计建议中的 10 条，作者猜想它跑前沿模型可以追平 Mini-SWE-Agent 的 SWE-bench 数字——下限就是这么低。生产系统与这个下限的差距不在能不能过题，而在安全、恢复、成本治理与平台能力——这也解释了为什么本篇前面那些看似"多余"的子系统全都值钱。

对症归因：两大死因接口上的最严格设计

Harness-Bench 对失败案例的解剖给出了归因线索：失败轨迹的 36.4% 死于契约/格式（交付的东西不符合机器可校验的规格）、24.6% 死于工具/恢复（报错后没改方案、硬着头皮继续）——两个接口合计 61%。该论文同时声明结果只到"配置级"而非"因果级"，没法把分差归到某个具体机制。所以下面做的是对症归因：Codex 恰好在这两个最大死因的接口上，给出了四家里严格一端最完整的一套设计。四条机制按证据强度排序：

① 编辑契约：文法 + 重试
论文观察 4 把文件编辑策略列为"决定 SWE agent 修改准确率的最重要因素之一"。Codex 的自定义补丁格式由 Lark 文法（一种语法解析工具）校验（用 Begin/End Patch 标记包裹）：格式写错的补丁在解析阶段就被拦下，根本到不了文件系统；失败按补丁块（hunk）逐块重试，单块失败不拖垮整份补丁——正对 36.4% 的头号死因。
② 工具面克制 + 按需检索
工具只有 25–30 个（Claude Code 有 43 个），再配一个按关键词搜索的工具（tool_search，用 BM25 关键词打分算法），要用时再调出来——可选面小、误用概率低、选得准。这条和 Claude Code 互不知情地各自做出了同款（延迟加载的发明者与复现者互不知情），这种撞车本身就是"它值钱"的证据。
③ 失败显式返回：fail-closed 全家
24.6% 的死因是"报错没被当成反馈用上，硬着头皮继续错下去"。Codex 的解法是一整族"拿不准就拒绝"（fail-closed）：Guardian 审批 agent 超时或输出格式不对一律拒绝（带拒绝熔断）；Starlark 策略规则自带测试样例、加载时先校验。错误要么被显式拒绝、要么带着结构化的原因返回给模型——没有静默通过。
④ prompt 与模型配套维护
行为策略与提示词跟模型版本一起维护：提示词（base_instructions）按模型从服务器下发（models.json + ETag）、派子代理的工具分两代按模型元数据选择（multi_agents / multi_agents_v2）、行为规则做成功能开关（no-commit → codex_git_commit）。FrontierHarness 上拿非自家模型（K3）的第一，说明优势不完全是"自家模型配套调优"带来的。

再放一个对照：改文件这条路的宽容度上，OpenCode 站在另一端——9 级逐步放宽的重试（从精确匹配一路放宽到编辑距离 0.65 的模糊匹配），这是"支持多模型"的代价：弱模型也改得上文件，但改错位置的风险也高。论文的建议直接把这个权衡写成规则："前沿模型用精确唯一子串，弱模型配模糊级联"。Codex 站在严格的一端——在前沿模型的世界里，严格就是为准确率选的那一端。

先排除五个看似合理的解释
  1. 不是记忆。Codex 的 agent 自维护记忆是研究里第一个，但 FrontierHarness 每任务从 golden checkpoint 冷启动（环境快照还原，每次试验全新）——记忆在该榜完全不生效。至少在这个榜单里，它的优势来自"每一轮的执行质量"，不是跨会话积累。这反而让归因更干净。
  2. 不是缓存。88.0% 的中位缓存命中影响的是 $3.47 的价格，不是 66.7% 的分数——那是成本侧的变量。
  3. 不是"靠磨"。Harness-Bench 里它平均 5.0 轮（全场最少之一）、86.1K token（全场第三低，仅次于 NanoBot 68.7K 与 OpenClaw 82.1K——后者省了 token 却只拿 52.4 分，省 token 和干出活是两回事）；FrontierHarness 最难的状态机题上它跑了 187 轮、$5.97 通过（Pi 90 轮、$2.50）。平时不浪费、难题不放弃——韧性本身也有成本，只是花在了刀刃上。
  4. 不是"显著碾压"。单榜内 1–3 题的差距，在 30 题只跑一次的样本下属于噪声；而且本节的归因都是"配置级"的对照——Harness-Bench 自己明说，没法把分差归到某一个具体机制。这份清单的价值是排除法 + 对症，不是因果证明。
  5. 不是（也不全是）模型——但这一条排不掉。四个数据点里只有 FrontierHarness 把模型钉死成 K3；Harness-Bench 是 GPT-5.4 绑定、tbench 是原生组合，模型贡献混在里面。所以本节归因的对象是"执行层设计"，结论强度以 FrontierHarness 为基准——它至少证明了这套设计在非同厂模型上也成立。

上升到设计哲学，四条机制其实是同一句话：Codex 在模型与外部世界的每个接口上都用契约消灭不确定性——补丁先过语法校验、规则自带测试、审批拿不准就拒绝（fail-closed）、派子代理带 JSON 结构契约和带类型的记录。每一步要么明确成功、要么明确失败且可重试，没有静默通过的路径。准确率，就是这个哲学在"改文件"这个最高频动作上的体现；它和下一节画像中"平台与企业治理"的定位也是一致的——治理层就是它准确率的来源之一，不是额外补的东西。

落点

给初级 AI 工程师的六条

想自己攒 agent：从 90 行开始，别用框架。11 个生产 harness、400 万行代码，零框架依赖不是巧合——手写异步循环才是主流做法。要"全家桶"就直接用 harness SDK（Claude Agent SDK、Codex SDK 等），不要用编排框架拼。
别为代码建向量检索。ripgrep + glob + tree-sitter/LSP 就是生产答案；embedding 只在会话记忆里有先例。RAG 的收益在代码场景高度存疑，而且代码一变、预建索引几分钟内就过期，维护成本极高。
工具面：先只给一个 bash，超 15 个再做按需加载。CC 与 Codex 在互不知情的情况下各自做出同款方案，这个阈值可以当经验法则。改文件的方式跟模型档位匹配：前沿模型用精确唯一子串，弱模型配模糊级联。
压缩：固定缓冲阈值 + 保留原文尾巴 + 增量合并。不要每次从头重新摘要——把旧摘要喂回合并（OpenCode 模式）。把预算花在恢复上：压缩后给文件重读预算（Claude Code 的 50K），比省那点 token 划算。
多 agent：先证明真的有能并行的部分，再谈架构。约 15 倍 token 是入场费。一条务实的升级路径：单次委派 → 可恢复的子代理 → 脚本编排 → 常驻团队。团队层目前两家都标"实验、默认关"——这不是谦虚，是对 token 花费和协调开销的诚实。
选 harness 看设计取向，不看功能清单。深度绑定单厂生态 → Claude Code / Codex；要多提供商中立 + 轻量 → OpenCode；要"一切可替换"、Windows 同级支持、或想把别家 harness 当子代理调度 → DeepSeek Harness；企业治理与审计 → Codex 的 MDM 栈目前最重。功能会以周为单位被抄走，设计取向以年为单位不变。
