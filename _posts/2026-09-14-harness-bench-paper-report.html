论文解读 · Agent 评测

任务与模型池都钉死，换个"外壳"，Agent 平均分差 23.8 分

北京大学团队的 Harness-Bench 基准做了一次控制变量实验：固定 106 个任务、同样的预算和模型池，只换 Agent 的执行层，六个系统的平均综合分相差 23.8 分。Agent 系统的成败，不能只算模型的账。

论文：arXiv 2605.27922 北京大学 × 奇元科技 2026 年 5 月 5,194 条执行轨迹

背景

Harness 到底指什么

写 Agent 应用的人天天在用它，但很少有人把它当独立变量来看。论文给出了一个工程化的定义：

H
Harness（执行层）是包裹在模型外、把模型输出变成真实动作的系统层。你熟悉的 Claude Code、OpenAI Codex CLI、各类开源 Agent 框架，本质都是"模型 + 一套 Harness"。它负责：上下文怎么拼、工具怎么暴露和调用、工作区怎么访问、权限边界在哪、报错后怎么恢复、预算怎么控制、执行过程怎么留痕。
Agent = Model + Harness
论文 §3 的核心公式：Agent 的能力是"模型 × 执行层"的组合属性，不是模型单独的属性。

问题在于：行业里的评测要么只测模型（MMLU、SWE-bench 这类把执行抽象掉或固定死的基准），要么把整套 Agent 系统当黑盒对比。前者看不见执行层，后者分不清功劳算谁的。论文作者认为这是当前 Agent 评测的一个盲区（论文 §1–§2）。

Harness-Bench 的做法很直接——做一次严格的控制变量实验：把任务、沙箱初始状态、预算、超时、评估器全部钉死，只换两样东西：模型后端 × Harness 配置。

方法

这个基准怎么测：钉死一切，只换两样

被测对象是 6 个可配置的开源 Harness：OpenClaw、ZeroClaw、Hermes、Moltis、NullClaw、NanoBot，覆盖从"轻量个人助手"到"自托管系统控制运行时"的不同设计取向（论文附录 B.1）。8 个模型后端横跨开源与闭源：Claude Opus 4.6、Claude Sonnet 4.6、Gemini 3.1 Pro、Qwen 3.6-Plus、GLM-5.1、Kimi K2.5、GPT-5.4、DeepSeek V4-Flash（论文附录 B.2）。

任务侧是 106 个沙箱化离线任务，按 8 类真实工作流分布：软件工程 22 个、数据/BI/金融分析 14 个、工作区与工具操作 15 个、知识与证据检索 13 个、办公与商务沟通 12 个、垂直专业工作流 12 个、长程自治 11 个、SRE/DevOps 7 个（论文图 2）。每个任务要求产出可交付的最终产物（文件、报表、代码修复），而不是回答一句话。

任务入组要过四道人工审查（论文 §3.2）：

真实性
任务来自真实的 Agent 使用模式和常见用户请求，不是人造的玩具题。
可解性
只允许用沙箱内提供的资源完成，防止"任务本身就做不了"。
可验证性
成功与否可以用确定性脚本或明确评分规则自动判定。
防作弊完整性
Agent 无法通过读取隐藏答案、篡改受保护文件、绕过约束来骗分。

评分不是只看"做没做成"。每次运行记录四类证据——最终工作区状态、完整执行轨迹、用量统计、校验器输出（论文 §3.3）——然后按这个公式综合：

任务分 = 安全(0/1) × 完成度 × 过程分
过程分 =（稳健性 + 工具使用 + 一致性）÷ 3，由固定外部评审模型（claude-sonnet-4.6）按轨迹打分。安全项一票否决：越权访问、泄露密钥等违规直接归零（论文 §3.4）。

这个乘法设计刻意保守：拿高分要求"做完了、没违规、过程干净"三者同时成立。全部组合跑下来共 5,194 条执行轨迹（6×8×106 = 5,088 条主矩阵，加 Codex 单独的 106 条），这个规模足以支撑配置级的横向对比与失败模式归纳；论文将结果定位为固定协议下的诊断性测量。

两个反直觉的观察：

烧 Token 不等于出活。NullClaw 每任务烧掉 175.1K Token，是 NanoBot（68.7K）的 2.5 倍，分数反而低 11.8 分。Hermes 平均绕 22.6 轮，是 NanoBot 的 3 倍轮次，同样没换来更高分。执行层设计的差距，直接体现在成本效率上。

快也不等于好。OpenClaw 平均只走 5.0 轮、花 82.1K Token，是全场最省步骤的系统之一，但完成度只有 60%——省下的步骤没有换来交付质量。至于这是"主动收尾"还是"规划不足"，论文未做行为层面的归因，但数据摆在这里：轮次少只是现象，产物合格率才是本质。

工程化视角：这意味着什么
  1. 选型不能再只看模型跑分。可配置 Harness 之间的完成度差距达 21.6 个百分点（81.6 vs 60.0，同一批任务与模型池上的平均，论文表 2）。固定任务与模型池时，仅执行层配置不同就造成 23.8 分的跨度——"模型 + 框架"必须当整体来评，而不是先选模型再随手挑个框架。
  2. 成本优化的最大杠杆可能在执行层，不在模型。NanoBot 的成绩说明：一个把"工具暴露、上下文裁剪、恢复策略"设计得干净的执行层，可以同时提升分数并砍掉一半以上 Token。在按 Token 计费的生产环境，这是直接的成本项。
  3. 注意归因陷阱。论文的评分公式里"安全"一票否决——如果只盯完成度做 A/B 测试，你会漏掉越权操作这类生产事故源。评估指标结构本身就是论文的重要贡献：完成度、安全、过程质量三轴缺一不可。
发现 2

失败解剖：Agent 最常见的死法是"会做但交不出"

比排名更有价值的是失败分析。作者基于每条轨迹的 oracle 结果、过程备注与失败备注等结构化字段，把失败归为五类反复出现的症状（论文表 3，同一条轨迹可能命中多项）：

数据来源：论文表 3。比率 = 出现该症状的失败轨迹 ÷ 全部失败轨迹。两组条形图均按 0–100% 绝对刻度绘制，轨道中线为 50% 参考线，跨图可直接比较。

逐条翻译成工程语言：

契约 / 格式（36.4%）
模型理解了任务，但最终产物不符合机器可校验的规格：JSON 少个字段、账本缺一行、manifest 不完整。评审器认的是产物契约，不是"差不多做完了"。
工具 / 恢复（24.6%）
工具调用报错、命令被权限拦截之后，Agent 没有基于报错信息修正方案，而是原地打转或硬着头皮往下走。报错没有被当成反馈消费掉。
证据 / 落地（14.6%）
知识密集型任务里，来源覆盖不全就下了结论——断言没有证据链支撑，缺少可复核的验证步骤。
产物提交（11.1%）
推理过程看起来头头是道，但最后没有把结果落盘成要求的文件或工件。在执行类任务里，"想清楚了"不等于"交付了"。
状态 / 续跑（9.3%）
多轮或中断任务里，中途进度没有持久化，恢复后从错误状态继续，把前面做对的部分又做坏了。

前两类合计超过 60%。也就是说，大部分失败不是模型能力不够，而是模型推理与执行环境之间的接口没对齐。论文把这叫做执行对齐（execution alignment）问题，我们下一节展开。

工程化视角：这份失败清单可以直接当你团队的整改 backlog
  1. 契约失败（36.4%）→ 在 harness 里加输出校验闸门。让结构化输出先过 schema 校验再交付，不合格就地重试或报错，而不是把半成品扔给下游。这是清单上投入产出比最高的一项。
  2. 恢复失败（24.6%）→ 把工具报错显式回灌进上下文。好 Harness 的差别就在这里：报错信息是否以模型可消费的形式出现在下一轮提示里，是否附带了"常见错误码 → 建议动作"的引导。
  3. 证据失败（14.6%）→ 对知识类任务强制"引用即地址"。要求每条结论携带可点开验证的来源，缺引用的输出在网关层直接判不合格。
  4. 这三项都不是换模型能解决的。论文用数据确认了一个直觉：生产事故的多数来源在执行层设计，整改动作也应该优先落在执行层。
概念

执行对齐：为什么换个"外壳"分差这么大

Harness-Bench 最有解释力的概念是执行对齐（论文 §5.2）。一条轨迹上有四个必须保持对应的东西：

① 模型推理
Agent"以为"自己在做什么、做完了什么。
② 工作区状态
文件系统里实际发生了什么变化。
③ 工具反馈
工具调用返回的真实结果与报错。
④ 评估契约
评审器最终检查的产物规格。

失败的轨迹几乎都长一个样：这四者中的一个或多个脱钩了——工具反馈没有进入下一步行动、断言没有绑定证据、做了一半的状态没有被保存、想出来的结果没有落盘。模型输出的推理依然"看起来合理"，但它和真实世界对不上账。

论文的关键论点：Harness 的本职工作，就是维护这四个环节的对应关系。它隐式定义了"什么算待办、什么算已观察的证据、什么算可恢复的失败、什么算完成的交付"。这套表示做得越模糊，模型的合理推理就越容易漂移到评审条件之外；做得越清晰，问题在变成最终失败之前就能被拦住。这解释了发现 1 的 23.8 分差从哪来——差的 Harness 让同样的模型对不上账。

工程化视角：执行对齐如何指导架构设计
  • 把"账本"做成显式结构。待办事项、已验证证据、产物交付状态，用结构化状态（而非散落在对话里的文字）维护，每轮行动前先对账。这是执行对齐的工程化载体。
  • 可观测性不是可选项。Harness-Bench 每条轨迹记录完整 trace 才做得出失败分析（论文 §3.3）。生产系统同理：没有全量 trace，失败就只是"一个分数"，永远定位不到是哪一环脱的钩。
  • 对齐检查前移。与其在最终交付时发现 JSON 不合格，不如在每步工具调用后立即校验契约——把失败暴露在还能补救的位置。
发现 3

强模型更"皮实"，但没有任何模型能免疫差 Harness

论文定义了"Harness 依赖度"：同一模型在 6 个 Harness 上的得分方差（论文 §4.3、图 3）。规律清晰：模型越强，平均分越高、跨 Harness 方差越小。强模型对提示格式、工具接口、恢复策略的差异更宽容。

但注意方向性：这解释的是"谁更耐折腾"，而不是"谁不需要执行层"。论文在讨论里明确回答了这个问题——强模型可以省掉一些提示词层面的脚手架，但权限边界、状态持久化、可审计 trace、客观校验这些执行层职责，任何模型都替代不了（论文 §6）。

类别层面还有个实用发现（论文附录 C）：跨 Harness 方差最大的任务类别是数据/BI/金融分析、工作区操作、软件工程——凡是依赖结构化数据操作、工具链编排、中间状态跟踪的任务，执行层的差距就被放大；方差最小的是办公与商务沟通类，语言为主的任务对 Harness 不敏感。给你的直接启示：你的业务越偏"结构化执行"，Harness 的选型与打磨越值得投入。

工程化视角：把"Harness 依赖度"用起来
  1. 当模型选型的鲁棒性风险指标用。图 3 的规律是：越弱的后端，跨 Harness 方差越大。选一个方差大的模型，意味着框架升级、提示模板改动都会引起更大的表现波动——上线后要为这类模型预留更大的回归测试预算；预算紧的团队，宁可要一个"皮实"的后端。
  2. 按业务类别分配投入。附录 C 的类别方差给出了资源分配依据：结构化执行类业务（数据分析、工作区操作、软件工程）优先打磨执行层；语言主导类业务（办公沟通）优先投模型能力。用同样的方法在自己业务的任务集上算一遍类别方差，就是一份现成的投入优先级排序。
  3. 别指望强模型省掉执行层基建。论文 §6 的判断很清醒：强模型省掉的是提示词脚手架这类表层工程，权限边界、状态持久化、可审计 trace、客观校验这四项基建一样都不能少——它们由执行层负责，模型再强也替代不了。
落地

从 Demo 到生产：三个必须回答的问题

把论文结论翻译成接入生产系统前的检查清单。

Q1：接入生产系统，需要考虑哪些环节？
  • 输出契约校验：36.4% 的失败是格式与契约违规——这是第一优先级。所有交付物先过 schema 闸门再出网关。
  • 恢复策略：工具报错必须显式回灌并驱动计划修订，而不是静默吞掉。
  • 权限边界：论文的安全项一票否决值得照抄——越权访问、密钥泄露直接判零，不允许用完成度抵消。
  • 预算控制：表 2 显示各系统 Token 消耗相差 2.5 倍，生产环境必须为每任务设上限与告警。
  • 全程留痕：产物、trace、用量、校验结果四类证据全量落盘——这也是这套基准自己的记录设计（论文 §3.3）。
Q2：它对现有 LLM 应用架构有什么影响？
  • 能力归因方式改变：线上表现 = f(模型, Harness)。汇报系统指标时应注明整套配置，跨系统对比才有意义。
  • 回归测试对象改变：换 Harness 版本和换模型版本一样需要跑回归——论文显示执行层维度单独可带来 23.8 分的波动，模型维度的影响见图 3，两个维度都足以左右上线表现。
  • 评测要自建 harness 级基准：Harness-Bench 开源了任务清单与协议（GitHub 见文末），可以直接作为内部回归测试的底座，在你自己的业务任务上复用"钉死环境、换配置"的方法论。
  • 成本核算口径改变：Token 消耗不再只是模型的属性，更是执行层的属性。优化成本时先查执行层的浪费（无效轮次、重复上下文）。
Q3：Demo 到生产可用，主要差距在哪？
  • 评估维度：Demo 看的是单次演示成功率（≈完成度）；生产要求完成度 × 安全 × 过程质量三轴全过——这正是论文评分公式的结构。
  • 失败模式分布：上线前用表 3 的五类失败做一轮定向压测，契约/恢复/证据三类合计 75.6%（36.4 + 24.6 + 14.6），是返工概率最高的区域。
  • 过程可审计：Demo 只需要"结果对"；生产需要"每一步为什么这么做"可回放——trace 结构从第一天就要设计好，后补的成本极高。
  • 状态与续跑：真实系统会被中断、重试、并发操作。9.3% 的状态失败在演示里几乎不会暴露，在生产里天天发生。
边界

这份结论的适用边界

严谨起见，论文自己声明的三个局限（论文 §6）值得记住：

沙箱离线任务：可复现性是靠牺牲对在线服务、用户反馈、外部状态漂移的覆盖换来的。线上带真服务的系统，差异只会更难控制。
配置级而非因果级：测的是完整 Harness 配置，分差说明"配置影响很大"，但无法归因到具体某个机制（是提示模板还是恢复策略导致的差距）。
过程分依赖 LLM 评审：过程质量由 claude-sonnet-4.6 按规则打分，带主观成分。作者也强调这些分数是诊断信号，不是部署保证。

另外提醒一个容易过度解读的点：这是一份"描述性"测量，不是数学定理。23.8 分差是在这套任务、这些版本、这个预算设置下的观测值。它支持的核心判断是方向性的——执行层值得被单独评测和汇报——而不是断言某个 Harness 永远最强。
