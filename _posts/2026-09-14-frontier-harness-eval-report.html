榜单解读 · Harness 评测

同一个模型跑 9 个 Harness，分差 17 分，账单差 17 倍

Runta 公司发布的 FrontierHarness Eval v1.0 做了一次少见的工业级受控实验：把模型（Kimi K3）、任务、运行时全部钉死，让 Codex、Claude Code、OpenCode、DeepSeek Harness 等 9 个出厂态 Harness 同台。结论很扎心：通过率挤在 17 分里，成本却差了 17 倍。

榜单：frontierharness.org 运营方：Runta v1.0 · 2026-09-01 发布 30 任务 · 360 次试验

背景

这个榜测的是什么，为什么值得看

F
FrontierHarness Eval是 Runta（一家做 Agent 执行层的公司）运营的 Harness 排行榜。v1.0 覆盖软件开发与终端任务：9 个 Harness、12 种配置，跑 30 个任务共 360 次，每格只跑一次。它的独特之处是把模型、任务、运行时三个变量全部钉死，让被测对象只剩执行层本身，再把 9 个出厂态 Harness（含 Codex、Claude Code 这类闭源 CLI）拉进同一口径——受控程度与被测面都超出了此前同类研究的覆盖。

被测名单（榜单主页"Tested harnesses"，版本号一并钉死）：Codex v0.148.0、DeepSeek Harness v0.1.0-rc.8、Claude Code v2.1.237、Pi v0.84.2、Oh My Pi v17.4.0、Kimi Code v0.37.2、Exo Harness v0.1.0、OpenCode v1.18.19、Hermes v0.20.4。其中 DeepSeek Harness 是 DeepSeek 的官方 CLI 编码 Agent，榜单上以四种预设参赛——Creator、Standard、PTC（即其 code 模式）、Minimal——所以是 9 个 Harness、12 种配置。

本站上一篇解读的 Harness-Bench（arXiv 2605.27922）是它的学术对照组。两者的分工恰好互补：

工程化视角：为什么"出厂态横评"比"配置级横评"对你的选型更直接
  1. 你实际部署的就是出厂态。团队里没人会先魔改 Claude Code 的内部缓存策略再上线。学术基准测"配置空间的上限"，这个榜测的是你按下回车那一刻得到的东西。
  2. 闭源 CLI 第一次进了同口径对比。Harness-Bench 只能测开源可配置 Harness，把 Codex 之类的模型绑定系统单列参考系；这个榜让 9 个主流产品在同一模型下直接对撞。
  3. 榜单开源了评测协议（GitHub 见文末），意味着你可以拿自己内部的 Harness / 预设进去跑同样的 30 个任务，得到和业界对得上的数字。
方法

受控三件套：同一个模型、同一批任务、同一台"冰箱"

这份榜最值钱的地方不是排名，是评测卫生。三个设计决定值得逐条拆开看。

① 同一个模型：Kimi K3
选 K3 的理由是中立性——用 Claude 会偏袒 Claude Code 的原生环境，用 GPT 会偏袒 Codex。K3 由 Fireworks 统一供能，9 个 Harness 走同一个网关，网关同时讲 OpenAI Responses API 和 Anthropic Messages API 两种协议，每个 Harness 都用自己的母语对话同一份权重（Runta 博客）。Kimi Code 虽是同厂产品，但被迫走 Anthropic 协议接入（原生 provider 对网关 404），最后只并列第 7——厂商血统没有换来主场优势。
② 同一批任务：30 个，判分确定性
21 个 Terminal-Bench 任务 + 9 个 DeepSWE 任务，全部是真实仓库上的软件工程活。过不过由确定性 verifier 说了算，不用 LLM 评审；各 Harness 的首轮缓存读取按统一口径计价，成本可比（Runta 博客）。
③ 同一台"冰箱"：checkpoint 冷启动
所有 Harness 和任务环境被安装一次、拍成 golden checkpoint，360 次试验每次都是全新还原——vCPU、内存、磁盘大小、磁盘内容、内存状态逐项一致。没有任何一次试验继承上一次的文件残留、页缓存或装了一半的依赖（Runta 博客）。
附加规则：每格一次，绝不重试
重试天然是"热"的（上下文和缓存都温了），跑 N 次取最好会系统性美化成绩。每个配置 × 任务只跑一次，取原始结果（Runta 博客）。
最容易被忽略的一条评测纪律

正式评测之前，基准任务一个都不许跑。原因是隐式前缀缓存——推理服务自动缓存重复出现的提示前缀、命中部分按更低的缓存价计费，应用无需显式标记；一次调试运行就能把前缀"焐热"几个小时，后来者白捡便宜。Runta 的所有调试都在单独的 smoke 任务集上完成。这一条几乎没有任何内部评测团队在做——你上一次在公司基准上"先试跑一下看看通不通"，是什么时候？

发现 1

"能过题"和"便宜地过题"是两种能力

这张榜最能说明问题的一行对比：Claude Code 与 DSH Creator 同为 63.3%——都是 30 题过 19 题——但一个每任务 $18.34，一个 $3.28，差 5.6 倍。Runta 的原话：完成任务和便宜地完成任务，是两种独立的技能。

榜单网站还挂了一份"每成功任务成本"榜，OpenCode 以 $0.0615 排第一，看起来像性价比之王。但网站自己加了三条注记的第一条就是打脸：这个数只统计了它通过的 15 题，失败烧掉的钱被排除在外；把失败算回来，OpenCode 每任务是 $3.24，与其说是便宜，不如说是"没花的钱都在没做出来的题上"。

工程化视角：成本口径决定你被哪种幻觉骗
  1. 生产核算必须按"每任务（含失败）"。Agent 的钱大头烧在它做不出来的题上——DSH PTC 在一个任务上失败烧掉 $12.95，比六个通过该题的配置都贵。只看成功样本的成本，等于把账单里最大的部分裁掉再汇报。
  2. 选型先算"单位产出的钱"再算价格本身。$1.05 的 Exo 和 $18.34 的 Claude Code 都不是答案，$2.43 的 Pi 和 $3.47 的 Codex 才是分子分母同看的用法：先定你要的通过率下限，再比同通过率档位里谁便宜。
  3. 失败成本低本身是一种生产力。Exo "失败得便宜"（最难的题上 $1.46 止损离场），Runta 的评语是：要挂重试机制的话，你想重试的正是这种。对做 pipeline 的人，"可控放弃"是真实的设计优点，不是缺陷。
发现 2

缓存命中率不是成本——Claude Code 的 25% 之谜

榜单上 Claude Code 的中位缓存命中率 67.8%，只是 Codex（88.0%）的 1.3 倍差距，看着不算夸张。但 Runta 在博客里单独开了一章：按 token 加权，Claude Code 的缓存命中率只有 25.0%，而其余全部 Harness 落在 91.6%–99.1% 区间，全场 token 加权平均是 92.4%。中位数描述"典型的一次试验"，加权数才描述"你实际付的账单"——两个口径差了 2.7 倍，而普通排行榜根本不会把这两者对账给你看。

拆开看，25% 这个数主要是被一格拖垮的：Claude Code 通过的 19 个格子里，最重的 3 格占了它 88% 的 token 消耗；其中最重的一格（python-statemachine 状态机改写题）一个任务就吃掉 24.6M 输入 token、缓存命中仅 15.7%、花了 $64.36——单格占 Claude Code 全部 token 的 68%。所以"25%"更像是对一个异常大格的描述，不代表它的典型行为（Runta 博客）。

为什么同一份追加式对话，有的调用 100% 命中、有的颗粒无收？Runta 的归因很克制：Claude Code 围绕 Anthropic 模型的显式 cache-control 语义设计，而 K3 暴露的是隐式前缀缓存，同一套缓存策略未必能平移。他们明确写了："我们还不能把这个差距归因于 harness 本身"——$18.34 描述的是"Claude Code + K3"这个组合，不是 Claude Code 的孤立属性，分离 harness 与模型的贡献是 v1.1 计划的第一项。

工程化视角：两个口径，两种坑
  1. 看任何榜单先问统计口径。"中位数"回答典型情况，"加权"回答总账单。评测报告只给中位数时，最贵的长尾任务可能被藏起来——而长尾恰恰是生产事故和超支的所在地。
  2. 缓存命中是单价，不是账单。一次缓存全命中的 300 轮失败，比一次缓存全 miss 的短任务烧钱得多。Runta 的公式值得抄在工位上：你付的是步数和 token，缓存只改变单价。
  3. harness × model 是组合属性。把"为 A 家模型调优的 harness"接到"B 家模型的缓存"上，可能既贵又慢。跨厂组合（比如拿 Claude Code 跑第三方模型）上线前，务必在自己的任务上实测成本，不要沿用原生组合的经验值。
发现 3

同一个 Harness 的预设，差出半个 Harness

DeepSeek Harness 的四个预设同模型、同任务、同运行时对撞，结果：Creator 63.3%（$3.28）、Standard 60.0%（$3.46）、PTC 60.0%（$4.58）、Minimal 56.7%（$4.72）。预设之间差 6.6 个通过率点、1.4 倍成本——Runta 的评语是：这个差距已经追平很多"不同 Harness 之间"的差距。换句话说，光改预设就能抹掉半个榜单的排名。

两个佐证细节：PTC 预设在最难那道状态机题上花 $12.95 超时失败，比六个通过该题的配置都烧钱；Creator 预设在同一题上 $3.88 超时失败，而同门 Minimal 花到 $10.49 反而通过——工具与提示的配置同时影响了花钱节奏和最终结果（Runta 博客示例任务表）。

工程化视角：你的"内部 prompt 配置"也是预设
  1. 回归测试矩阵必须包含配置维度。很多团队给 Agent 改一版系统提示词、调一个工具清单就直接上线——按这份榜的数据，这类改动的波动量级和"换一个 Harness"相当，却常常连跑一遍回归都不做。
  2. 汇报结果必须带配置指纹。既然 Creator 和 Minimal 能差 6.6 分，那"我们上周 agent 通过率 60%"这句话在没有配置指纹时毫无信息量。至少要记录：prompt 版本、工具集、步数上限、温度这类可变项。
  3. 选预设就是选型的一半工作。评估一个新 Harness 时，不要只测默认档——把它的预设/配置空间都过一遍，你很可能在"次优预设"里找到比默认档更适合自己的点。
发现 4

钉死模型，测出来的也不是"纯 Harness"

一个必然的追问：Claude 模型与 Claude Code 同厂咬合演化、GPT 与 Codex 同理——把模型统一成 K3，凭什么就能测出"外壳本身"的差距？答案：测不出，Runta 也没打算测。

harness 的表现从来不是 harness 单方面决定的。厂商 harness 与自家模型同厂协同演化：Claude Code 围绕 Anthropic 模型的显式 cache-control 语义设计（发现 2 里那 25% 的出处），Codex 与 GPT 系列同为 OpenAI 出品，Kimi Code 与 K3 同厂。模型一换，同一份 harness 的缓存策略、工具协议、prompt 适配全部重新洗牌。所以"钉死模型"测出的从来不是 harness 的固有质量，而是 harness-model 组合在客场的表现——这正是 Runta 全程强调组合属性的原因。

它对绑定的处理分三层，没有一层是"抹平"：选型层，把模型选成无主之地——用 Claude 会偏袒 Claude Code、用 GPT 会偏袒 Codex，K3 让所有闭源 CLI 一起下客场（见方法节），这做到的是"公平地不适配"，而不是"适当地适配"；协议层，让每个 harness 说母语（双协议网关），别把适配失真混进 harness 层的差异；归因层，把组合属性写死进结论——$18.34 与 25% 缓存全程带着"Claude Code + K3"的标签，Runta 明言这些差距"不能归因于 harness 本身"。

那这份榜对谁仍然有用？两类人。跨厂组合用户：锁第三方模型、走网关、按成本路由的企业部署，用的本来就是"客场组合"，这份榜就是他们的原生场景；选型研究者：交互效应大，不代表主效应不存在——Pi 在 K3 客场仍拿 60.0% + $2.43/任务，它的省 token 工程不依赖某一家模型。反过来，用原生组合（Claude Code + Claude、Codex + GPT）的读者，这份榜的绝对数字参考有限——那是 Terminal-Bench 排行榜（社区提交、原生配置为主）回答的问题。

要真正把"harness 本身"与"组合效应"分开，统计学上的答案是因子实验：每个 harness × 每个模型都跑一遍，主效应与交互效应才能分开算。雏形已经存在：Terminal-Bench 论文做了 6 agent × 21 模型的矩阵（结论：模型换挡 +52%、scaffold 换挡 +17%），Harness-Bench 做了 6 harness × 8 模型的部分交叉，The Scaffold Effect 是 2 模型 × 3 harness 的小样本因子设计；FrontierHarness v1.1 计划补上这块。v1.0 不直接做的原因是成本：12 配置 × 1 模型 × 30 任务 = 360 次试验，换成 9 个模型就是 3240 次——先用单模型把评测卫生打磨好再扩矩阵，是合理的工程顺序，不是偷懒。

更深一层：矩阵做出来也只是快照。harness 一天能发两版还多（Don't Blame the LLM），模型一年数版，两边每次发版都可能重写一次组合的契合度。这类榜单没有"定论"读法，只有快照 + 归因边界。

工程化视角：三个口径问题，先问再用
  • 先问自己的部署形态。原生组合用户看社区榜（Terminal-Bench 排行榜），跨厂组合用户看钉死模型的受控榜（FrontierHarness）——两个榜回答两个不同的问题，谁也替代不了谁。
  • 把单模型榜单的排名读成"组合在客场的表现"。读成"harness 固有质量"的那一刻，你就已经踩进交互效应的坑。
  • 想彻底分离两者只有全矩阵一条路。而全矩阵的成本 = harness 数 × 模型数 × 任务数 × 重复次数，量级上去之前，"单模型受控榜 + 原生组合社区榜"互相校准是性价比最高的读法。
解剖

一道题的 12 张账单：pass/fail 看不见钱

这道题是整份榜单的缩影：Pi 和 Claude Code 产出同一个"通过"，价格差 26 倍（90 轮 vs 381 轮，98.2% vs 15.7% 缓存命中）；DSH PTC 挂了 $12.95 的账单，比六个通过者全部都贵。如果只看 pass/fail 一列，这些差异全部不可见——但它们会一分不少地出现在你的 API 月账单上。Runta 同时声明：这 26 倍价差同样属于"Claude Code + K3"这个完整组合，现有数据不能拆出 Claude Code 的孤立属性。

工程化视角：内部评测至少要记录这五列
  1. 结果、成本、轮次、缓存命中、耗时——Runta 每格都存这五项，本文才能做出上面这种对比。内部评测只记 pass/fail 的团队，等于主动放弃了成本归因能力。
  2. 给每类任务建"每通过一题的钱"基线。有了它，换 harness / 换模型 / 改 prompt 的每次决策都能折成金额对比，汇报时不再靠体感。

Terminal-Bench 排行榜数字为 2026-09-14 快照：2.0 版 137 条社区提交中 Codex CLI #4（82.2%）、Claude Code #47（58.0%）、OpenCode #60（51.7%）；当前 4.0 版仅收 Codex / Claude Code / Grok Build / mini-SWE-agent 四个 Agent。HAL 的 scaffold 为学术框架（SWE-Agent、smolagent 等），不含商业 CLI。✓ = 直接被测；△ = 以模型身份被测、跑在第三方 harness 上。

除了排行榜，2026 年还有一批论文在做"harness 效应"本身：The Scaffold Effect（arXiv 2607.22585）证明同模型换三个开源 harness，通过率差 0–8 个点、每解一题的 token 差最高 40 倍；UnderSpecBench（arXiv 2607.02294）专测 Claude Code、Codex、OpenCode 三家在 DevOps 任务上的越界行为；Don't Blame the LLM（arXiv 2607.03691）统计五个开源 harness 的发版演化、再固定模型追踪 Qwen Code CLI 的 35 个连续版本；Harness Engineering（arXiv 2609.00006）则直接解剖 11 个 harness 的源码。方向已经收敛：harness 是一个独立的、可测量的、值钱的工程变量。

工程化视角：看榜先问一句——它把什么钉死了
  • 想选 harness：看钉死模型的榜（FrontierHarness），那里 harness 是唯一变量。
  • 想选模型：看钉死 harness 的榜（Terminal-Bench 论文恰好给出反面结论——模型换挡 +52%、换 scaffold +17%，模型杠杆更大）。
  • 想算成本：只信同时报"结果 + 成本 + 轮次 + 缓存"的评测。只有 pass rate 的榜，对做预算的人约等于没有信息。
  • 想要全部：等 FrontierHarness v1.1 的 harness × model 全矩阵——那才是这个方向的终局形态。
落地

工程师怎么用这份榜：三个问题

Q1：我的场景该选谁？
  • 求稳求快上手：Codex——全场唯一 66.7%，且每任务 $3.47 贴近中位，Runta 给出的"安全默认"。
  • 批量、重复、成本敏感：Pi——60.0% + $2.43，同样 100 遍的活，账单差出几倍的场景选它。
  • 预算极紧 + 可以接受重试：Exo Harness——$1.05 的止损型设计，配外层重试逻辑用。
  • 在意单任务时延：DSH Minimal，5m 41s 全场最快；通过率比同门 Creator 低 6.6 个点（30 题单次样本，属打平档），按时延敏感度权衡。
  • 注意版本时效：以上结论全部绑定榜单页钉死的版本号（Codex v0.148.0、Claude Code v2.1.237 等）。这些产品迭代极快，选型前用它开源的协议在最新版上重跑一遍你的任务集。
Q2：看这类榜单最常见的三个坑？
  • 口径坑：中位数 vs 加权数（发现 2 的 2.7 倍缺口）、每任务 vs 每成功任务（OpenCode 的幸存者偏差）。看到任何成本数字，先问分母是什么。
  • 组合坑：$18.34 是"Claude Code + K3"的属性，不是 Claude Code 的。跨厂组合的实际成本必须实测。
  • 版本坑：Don't Blame the LLM 那篇显示 harness 一天能发两版还多，任何榜单数字的保质期以周计。
Q3：能拿它评测我们自己的内部 harness 吗？
能，而且门槛刻意做低了。评测协议与任务定义开源在 GitHub（frontier-harness-eval/eval），仓库里带一份 SKILL.md——把地址丢给你的 agent，它会引导你选 harness、模型、任务集，检查前置条件并启动评测，最后产出质量、token 用量、成本、时延报告；也可以按仓库的手工流程自己跑。团队内部 harness、甚至同一 harness 的不同 prompt 预设，都可以进同一套协议对比——正好把发现 3 的教训用起来。
边界

这份结论的适用边界

任务面窄：v1.0 只覆盖软件开发与终端任务，30 题（21 Terminal-Bench + 9 DeepSWE）。Runta 自己声明不能外推到其他类型的知识工作，v1.1 计划扩任务面并做 harness × model 全矩阵。
单格一次、无重测方差：每格只跑一次是刻意的（重试是"热"的），代价是没有 run-to-run 方差可报——63.3% 与 60.0% 之间的排序，在 30 题样本下应视为"打平档"，别过度解读名次。
出厂态、不调优：各 harness 按原样参赛，内部一律不改（包括 Claude Code 的缓存策略）。所以成本差异属于"完整 harness-model 配置"，不能拆账到单一组件——这也是 Runta 在 Claude Code 25% 缓存分析里反复强调的归因警告。
利益相关：Runta 是卖 Agent 执行层的商业公司，这份榜自带获客属性——榜单页挂着 $100 体验金。但协议、任务定义与数据开源在 GitHub，方法论透明可复现，这是它比一般厂商白皮书可信的地方。数字照用，动机自知。
